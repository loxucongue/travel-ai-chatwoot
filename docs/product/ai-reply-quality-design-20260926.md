# AI 回复质量：业务目标、诊断与结构设计

日期：2026-09-26。状态：设计草案，可用于业务评审；不是已实现或已验收的能力。

本轮问题是“语气不够台湾”和“回答总差半个层级”。目标不是继续增加提示词条款，而是建立独立、可比较、可追溯的回复质量工作流。保留现有 Chatwoot 接入、任务队列、知识发布、交付和人工接管体系。

## 1. 业务到底希望达到什么效果

建议定位：**像熟悉产品的台湾旅游顾问，在私聊中帮客户解决当前疑问，并在合适的时候推进下一步。** 这是一种表达和服务能力要求，不允许虚构真人身份、亲身经历或客户评价。

下表综合既有业务反馈与本轮诉求。具体风格范例、评分门槛仍需业务认可。

| 维度 | 希望客户感受到什么 | 可观察的验收标准 | 不合格表现 |
|---|---|---|---|
| 听懂当前问题 | “他知道我在问什么” | 回答当前对象，承接省略追问；复合问题逐项处理 | 问集合却介绍整条行程；“那回程呢”失去上下文 |
| 懂得取舍 | “刚好回答到我在意的点” | 先给答案；只补会影响本次选择的条件或解释 | 背整份产品资料；每条都追加卖点、免责或留资 |
| 台湾自然表达 | “像平常和顾问聊天” | 台湾繁体、自然语序与用词、长短合宜；严肃问题认真回应 | 简转繁后仍是大陆客服句式；机械加“喔～”；整段公文腔 |
| 有顾问判断 | “这段话有帮我做决定” | 明确顾虑时给有依据的针对性说明；信息不足时问一个关键问题 | 只复述资料；空泛说品质好；把猜测当成客户需求 |
| 连贯而不催促 | “不用重新讲一遍” | 记住人数、时间和拒绝；接受纠正；考虑时给予空间 | 反复问人数；日期未定就停止服务；拒绝 LINE 后继续索取 |
| 信息可信 | “已知的讲清楚，不知道的会处理” | 价格及条件正确；未知事项具体核对；不额外扩张核对范围 | 已知价格也反复说仅供参考；编余位或优惠；所有问题都转人工 |
| 说到做到 | “答应的资料或协助真的来了” | 索取资料对应实际交付；承诺核对对应人工任务；顾问手机通知另验收 | 只说已发送；生成任务就当作手机已经收到 |
| 节奏舒服 | “不用等很久，也不会被刷屏” | 单点问答简短；完整介绍有顺序，可被新消息打断 | 每次三大段；连续催问；旧行程继续发送 |

“每条多提供一点价值”不应成为硬规则。有时最好的回答就是一句清楚的答案；有时只答字面问题又会显得不懂顾虑。应判断补充内容是否帮助客户处理本轮问题，而不是按字数或关键词决定。

### 对照范例：先对齐什么叫“好”

以下是本次拟写的风格候选，不是实际模型输出，也不是业务已批准话术。产品事实示例沿用项目现有业务资料，实际执行仍以当时已发布知识为准。

| 场景 | 差半层的典型写法（示意） | 建议候选 | 真正要改进的地方 |
|---|---|---|---|
| 客户问“是在成都集合吗？” | “集合地点为林芝，成都为入藏函交付地点，请以实际安排为准。” | “是在林芝集合，第一天會安排接機。成都是交付入藏函的地方，跟集合地點不同喔。” | 直接纠正误解，解释两个地点的关系，不加无用免责 |
| 已确认 9 日、6 位，问每人费用 | “6人方案参考价格9980起，具体请专项顾问核实。” | “您們 6 位參加 9 日行程，每人是人民幣 9,980 元，以兩人一房安排。” | 已知条件下直接回答，不主动制造不确定性 |
| 客户说“我先跟家人讨论看看” | “好的，请留下联系方式，方便顾问跟进。” | “好，您先和家人討論。有想再了解的地方，隨時問我就可以了。” | 尊重节奏；系统也要延后主动跟进，不能只改语气 |
| 客户问“有去纳木错吗？” | “未包含，以下为本次行程特色……” | “這趟行程沒有安排納木錯喔。” | 接受一句就答完；不强加替代推荐 |
| 拒绝 LINE 后继续问住宿 | “没有LINE也可以留微信或电话。” | 直接回答本次住宿问题，使用该线路已发布住宿事实 | 联系偏好与继续咨询分开，不把每轮当作留资机会 |

是否使用“喔”、称呼“您”、数字空格等属于品牌偏好；不应用单一口头禅代替整体自然度。最终以业务认可的台湾表达为准。

## 2. 从当前代码能确认什么

### 2.1 已有基础应保留

- `decision_service.py` 统一决策入口，区分 V1/V2；已有知识版本与调用轨迹。
- V2 能读取已批准事实、素材和带客户原文证据的记忆，模型理解本轮语义，程序管理交付与状态。
- 已有事实、回复范围、人工任务必要性等检查；禁止用文字冒充实际附件发送。
- 既有业务报告已覆盖相当多产品边界，不能为了自然度丢弃这些约束。

### 2.2 当前最值得处理的结构问题

| 证据 | 对回复效果的影响 | 判断边界 |
|---|---|---|
| `config.py` 默认 `ai_engine_default="v1"`；`reception_rollout.py` 明确已有会话保留原引擎 | 改进 V2 不代表投诉会话会用到 V2 | 先核实具体样本的引擎、发布版本、模型和知识版本；本地状态不能代表当前生产 |
| `advisor_voice.py` 有繁体转换、禁词与 `.replace('比較','較')` | 字词合规可以通过，自然表达仍可能变差；“較”容易更书面 | 这是可确认的转换行为；它对当前差评贡献多大需回放对照 |
| 台湾表达合同同时夹带价格、医疗、任务与追问规则 | 表达、事实和动作职责混合，难以单独调优、定位退化 | 规则内容有价值，但不应全部堆在表达规范中 |
| V2 `runtime.py` 将业务提示、Skills、状态、运营指导和语气合同拼给同一生成过程 | 一次同时完成理解、决策、写作和动作声明；结果不好时难分是哪一步错 | 不意味着必须每层新增一次模型调用 |
| V1 表达合同要求回答后提供一项价值；V2 强调答完整即可结束 | 两条链路的“好回答”标准不同 | 需建立统一业务原则，并允许不同场景有不同答法 |
| V2 已有核验、两次生成式修复及最多一次确定性清理 | 能拦错，但最终话术可能被多次调整；缺少面向顾问风格的修改前后对照 | “审核导致退化”是待验证假设，不能仅凭架构断言 |
| 已有人工表达汇总，但原始语料混合模板、地区用词与旧承诺 | 学到的可能是历史群发习惯，而非业务希望的台湾顾问表达 | 汇总注明绝大多数人工归因是推断；不能视为台湾母语专家标注 |
| 历史评估以已知反馈、事实、动作和审核通过为主 | 回归通过不能证明新场景自然、得体，或业务愿意直接发送 | 9 月 21 日报告不是本次质量验收；需新盲测和业务评分 |

特别说明：“比較”本身不应被定义成地域错误。既有“不用比較”的要求可以保留为待确认的品牌偏好，但不建议全局机械替换成“較”。同样，“25–80 字”“只留一句限制”应是场景指导，不能导致漏答必要条件。

## 3. 如何把“差半个层级”定位清楚

对每个差评样本保留同一组证据：客户消息、相关上下文、客户已确认信息、实际使用的知识、引擎/模型/提示/知识版本、初稿、每次审核意见与修改、最终对外回复和交付结果。

业务补充两项即可：**哪里不满意；如果自己接待，会怎么回。** 开发侧再做归因，避免让顾问填写复杂技术表单。

| 归因 | 判断办法 | 应改哪一层 |
|---|---|---|
| 理解错 | 本轮实际问题与系统理解不同，或代词指错对象 | 上下文、客户状态和语义理解 |
| 信息错或缺 | 正确理解了问题，但没有拿到完整适用事实 | 知识结构、查询和适用条件 |
| 判断差 | 事实正确，却选错回答重点、过度转人工或追问 | 本轮回复计划 |
| 表达差 | 该回答的内容已正确，只是语序、措辞、节奏不自然 | 台湾表达生成 |
| 修坏了 | 初稿较自然，修复后漏意图、变僵硬 | 审核与修复边界 |
| 执行差 | 话术很好，但资料未到、重复发送或顾问未获提醒 | 交付与通知 |

对照实验先固定上下文与事实，再分别替换“回复计划”和“表达方式”；只有这样才能判断是否需要换模型。模型能力不足是可能原因，但目前没有本轮对照数据，不能把它直接当成结论。

## 4. 建议结构：让内容判断和语言表达可分开改进

目标数据流：

```text
客户消息 + 相关历史 + 已确认客户状态
                 ↓
本轮需求与回复计划 ← 已发布事实、适用条件、可用素材
                 ↓
台湾顾问表达 ← 经业务认可的场景范例
                 ↓
事实/内容完整性检查 + 动作检查 + 表达质量检查
                 ↓
有明确原因的局部修复（保留计划和事实）
                 ↓
现有交付执行器 → 客户消息 / 素材 / 人工任务与手机提醒
                 ↓
质量记录与顾问反馈
```

这是逻辑职责划分，先在现有后端内实现，不拆成多个服务，也不默认增加多个智能体。

### A. 事实、客户状态和风格素材分别管理

- **产品事实**：内容、来源、适用线路/人数/时间、例外和发布版本。只从已发布知识读取；历史顾问说过不等于当前事实。
- **客户状态**：明确说过什么、证据来自哪条消息、是否已纠正、什么尚未解决、拒绝和预约。推测的顾虑只能作待确认假设。
- **表达范例**：场景、客户问题与必要上下文、业务认可回复、好在哪里、不合适的写法。示例中的价格等不覆盖当前事实。
- **交付状态**：文字、图片和文件分别是否成功送达；人工任务是否建立、通知是否提交，手机实际收到不能由接口成功反推。

### B. 引入可检查的“本轮回复计划”

建议逐步从现有 `EvaluationDecision` 和 V2 回合状态中提取以下内部结构，先离线比较，不立即改变线上接口：

```json
{
  "current_need": "确认集合地点，并澄清成都与林芝的关系",
  "must_answer": ["集合城市", "第一天接机", "成都用途"],
  "fact_refs": ["由已发布知识实际返回的事实ID"],
  "necessary_conditions": [],
  "optional_help": null,
  "next_step": {"type": "none", "reason": "当前问题可完整回答，无需追问"},
  "delivery_intents": [],
  "style_scene": "clarify_misunderstanding"
}
```

计划描述“要表达什么、为什么现在需要”，不预先写一段僵硬标准答案，也不输出模型私有推理。`must_answer` 不是只能靠关键词校验；仍须语义确认完整回答。

`optional_help` 仅在能帮助本轮决策且有事实支持时使用；默认可以为空。`next_step` 明确区分无下一步、一个关键追问、资料交付、人工核对。不能为了显得服务周到自动新增任务。

### C. 台湾表达层只负责把正确内容说好

- 使用短而明确的品牌表达规范，配少量场景匹配范例；不把全套事实和历史修复规则重复放入语气提示。
- 以句子与对话动作学习：怎样承接误解、怎样拒绝不可能承诺、怎样停在合适位置，而不是统计用了几个“喔”。
- 表达层不能更改价格、条件、客户状态或新增服务承诺。写出“帮您确认”必须有相应动作依据。
- 简繁与术语检查作为兜底；逐项评估会改动语义、语气的替换，不再把全局换词作为主要风格方案。
- 单点问答、顾虑解释、完整介绍、资料说明、考虑/拒绝、人工承接分别设场景指引，不强制统一长度或句式。

### D. 审核区分“不能发”和“还不够好”

- **不能发**：事实错误、漏掉必要条件、无依据的承诺、违反客户拒绝、回复与实际动作不一致。必须修复或转入明确失败处理。
- **还不够好**：公文腔、重复口头禅、语序不自然、内容正确但不够利落。作为质量评分；不能仅因风格偏好反复重写，耗尽回复时间。
- 先保留现有事实审核，新增可观察的表达评分。是否减少审核调用要有离线证据，不先移除安全边界。
- 修复必须指出具体句子、问题类别和受影响事实；风格修复只改表达，业务修复回到计划层。每次修改后检查必要内容和动作是否仍一致。
- 记录初稿/终稿差异、修复次数、总耗时；为普通问题设明确调用预算。逻辑分层不意味着每轮固定新增两个模型调用，先测收益与时延。

### E. 代码落点与边界

| 现有位置 | 建议职责 |
|---|---|
| `decision_service.py` | 保留统一入口，记录完整实验版本，不放更多业务特例 |
| `reception_v2/runtime.py` | 保留编排，逐步提取回复计划与表达职责；先影子评估再接入 |
| `advisor_voice.py` | 收敛为表达规范与必要检测；价格、医疗等规则移回对应业务职责 |
| 已有知识发布、Skills、journey memory | 继续提供有版本的事实、能力与带证据状态 |
| 已有核验及修复模块 | 返回可分类的错误和评分，保留修改前后证据 |
| 现有演练场 | 增加同场景 A/B 盲评、顾问改写与问题分类，减少切换工具 |
| `live_reply.py`、交付与通知模块 | 继续负责真实发送、回执与接管；模型失败、历史读取失败等也须有明确兜底 |

模块名和字段均为设计方向，不表示这些新接口已经存在。优先新增小的内部契约，不并行再造整套 V3。

## 5. 怎样验收，避免又一次“测试都过了，但业务不满意”

### 样本与评分

建议首轮整理 30 条顾问认可的风格锚点、100 条未参与调优的单轮盲测、20 条完整对话。这是启动规模建议，不是已收集或已确认数量。

覆盖：初次咨询、明确单点、连续省略追问、复杂多问、纠正人数/线路、顾虑、拒绝留资、考虑、索图、缺资料、未知实时报价、人工接管。至少一部分故意换问法与对话顺序。

- 按完整会话划分调优集和盲测集；同一会话的改写不能跨集合。保留一组未暴露给开发调优的验收题。
- 业务盲看现状与候选回复，标记“可直接发送 / 小改后可发 / 需重写 / 不能发”，补一句原因。台湾自然度需要由业务认可、熟悉台湾沟通习惯的人评价，不能只由开发者或模型自评。
- 另评听懂问题、内容取舍、顾问帮助、自然表达、连续对话各 1–5 分。事实与动作错误独立列出，不让平均分掩盖。
- 分场景公布结果及失败例，不只报总体通过率。记录无法判断和未评审，不能当通过。

### 建议的首轮通过条件（待业务确认）

| 指标 | 建议门槛与口径 |
|---|---|
| 严重事实/承诺/客户拒绝错误 | 本轮验收集 0 条；这是有限样本门禁，不宣称线上零错误 |
| 可直接发送率 | 盲测至少 90%；100 条单轮与20条完整对话分别统计，不混合凑数 |
| 台湾自然度、答题完整度 | 各自至少 90% 样本达到 4/5；保留全部低分原因 |
| 必要资料交付、人工承诺对应任务 | 验收场景全部核对实际回执或模拟器状态；模拟和真实渠道分开报告 |
| 与现状相比 | 业务盲评候选胜出至少 60%，退步不超过 10%，其余平局；按场景检查是否集中退步 |
| 时延 | 同样模型与负载下记录端到端 P50/P95；普通问答 P95 不高于现状基线 10%，或由业务认可质量与耗时的取舍 |

转化率、有效留资率、顾问接管成本作为后续业务指标，需标记流量来源、广告、人群与活动变化；不能用一次离线盲评推导销售提升。

## 6. 最小实施顺序

1. **建立可信基线**：确认差评会话走的实际引擎/版本，冻结一组现状输出；收集业务改写，按上述六类归因。先发现最大的损失点。
2. **校准台湾风格**：从已有语料中去模板、去过期承诺，整理场景范例；评审“比較”等禁词及替换；相同内容比较表达方案。
3. **离线拆出回复计划**：在现有 V2 中做最小原型，对比计划质量、内容完整性与耗时；验证内容判断和表达是否能独立提升。
4. **对齐审核与质量目标**：检查初稿与终稿是否被修坏，限制风格修复的影响；保留事实及动作门禁。
5. **完整对话盲测后小范围发布**：保留现有引擎回退能力，按会话显式分配候选版本；监测失败、时延、人工接管和顾问手机通知。

本轮完成分析与版本管理准备，不执行模型批量付费评测、不修改接待策略、不切换生产会话。下一轮实现范围应由基线和业务范例决定，避免一边改标准一边宣布通过。
