# V3：单线路 Skill 接待

V3 是当前正式接待和演练共用的引擎，旧 V2 执行链已经移除。业务目标是承接两条西藏桃花线路的公域客户，完成配置开场、整套介绍、关联答疑、适时留资与顾问交接。演练使用模拟交付，正式环境使用 Chatwoot 适配器。

三个标准 Skill 目录位于 `backend/app/reception_v3/skills`：`tibet-reception`、`peach-9d-2027`、`peach-11d-2027`。每个 `SKILL.md` 含 YAML `name`、`description` 和执行方法。注册器启动时读取索引；加载线路时将当前后台事实、场景原话、完整 SOP、图片引用及顺序附入正文，不复制另一套可编辑数据。

每轮预加载通用接待和已知线路。模型通过原生 `load_skill` 工具读取其他线路的完整原文；识别到尚未加载的线路时，运行时补加载后继续本轮。两条启用线路的事实及当前可用官网服务事实已直接提供，`get_service_facts` 可返回完整记录。配置修改在下一次模型运行时读取，已经开始发送的介绍使用已保存的计划。

运行记录的 `loaded_skills` 保存真正加载的名称及内容摘要，`skill_tool_calls` 保存工具参数和结果摘要；底层 `logs` 保留每次模型 HTTP 轮次及最终话术、图片引用。索引出现一个名称不代表正文已经加载，正文加载也不等同于逐句采用。

同一个模型处理三个事件：客户消息、介绍完成、沉默到期。没有 V2 Flow 分类、话术审核、裁剪和反复改写。结构错误最多修正一次 JSON；模型最终文字直接交付，引用话术直接取原文。

系统提示词在 `reception_v3/prompt.py`，仅定义身份、工具加载和执行协议。通用 Skill 定义接待方法、留资和沉默，线路 Skill 承接产品原文与适用场景。共用原话的 `scenario`、线路的正反例、人数条件、使用说明及接待说明都随加载提供；不把旧版“回答两个主题就留资”的阈值传入 V3。

一条原话可以包含多个回答段落。模型针对单个问题选段时输出最终 `text`；只有完整原话适用才留空 `text` 并引用 `script_id`。`asset_keys` 是明确的本次交付选择，空数组表示不附图，引用话术不再隐式附带其图片。整套 SOP 仍使用配置内的全部图文和顺序。

当前传入模型的表达配置为语气与补充说明，留资配置为开关、渠道和资料前提，沉默配置为开关与间隔；开场和 SOP 间隔由交付层执行。旧版字数、图片数、已答主题数等参数不是 V3 的硬门槛。修改这些参数不能被解释为 V3 一定会截断文字或删除素材。

第一次消息先发送配置开场，按客户会话只执行一次；是否含「你好」不参与判断。模型随后承接广告线路或帮助选择。确认线路后用 `start_introduction` 引用整套配置，不让模型重打一遍。

交付队列按配置秒数发送；普通插话保存，整套介绍发完再统一回答。模型判断停止、改线或转人工时取消剩余介绍。介绍完成后一定产生新的模型事件，根据最新人数、日期、期间问题决定结尾的一个问题。没有固定尾问拼接。

默认按通用沉默间隔配置定时运行模型，不读取 V2 的独立间隔。模型可以指定 `next_check_minutes` 覆盖下一间隔，适合明确预约；`null` 使用配置。`stop_followup` 表示结束自动评估。从最后一条实际交付后计时；没有输出则从本次评估结束计时。到点可发送、继续等待或结束；拒绝主动联系和人工接管状态由服务端记录。

数据库保存会话、运行记录和消息；V3 状态放在 `controls.v3`，客户资料在会话 memory。正式和演练调度器隔离，模型与交付使用独立线程池，同一会话维持顺序。重启后延续确认未提交的消息；每次最多发送一条，进程停顿后不把欠下的间隔压成瞬间刷屏。

正式交接通过 live 适配器创建或复用 HandoffTask，再由通知发送器按当前顾问配置同步分配和内部提醒。演练交接只记录沙盒状态。接口接受、沙盒通过和真实手机/手表收到是不同证据，设备收件仍需单独验收。

邀请时机由通用 Skill 统一描述，线路话术提供原文，不另设一套触发条件。上一则邀请未回应时，紧接着的月份、人数或文件追问先答疑；后续咨询自然收尾时仍可再次邀请。只有客户明确说要和家人讨论时使用家庭讨论开头；长辈同行本身不构成这个场景。已提供有效联系方式或明确要求真人时交接。

验收重点：连续对话、两条线路顺序、介绍期间问题合并、介绍末尾问人数、已知人数不重复、改线与停止、留资交接、三分钟和五分钟计时、重启恢复与配置开场原文。
