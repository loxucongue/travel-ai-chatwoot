## 1. 文档目的

本文档定义基于 Chatwoot 的多渠道 AI 客服运营平台第一阶段产品需求，供产品、设计、开发、测试和业务团队统一范围与验收口径。

本文档重点回答：

1. 哪些客户消息应由 AI 自动处理。
2. 哪些场景必须停止 AI 并转交人工。
3. 主动 SOP 可以对哪些客户发送、何时发送、何时退出。
4. 自建平台与 Chatwoot 分别负责什么。
5. 如何管理账号、收件箱、会话和操作人员权限。
6. 如何统计 AI 接管、人工转接、客户留资和 SOP 效果。

本文档不定义旅游业务 AI 的具体提示词、知识库内容、行程推荐方法、报价算法和自然语言判断细节。这些能力通过独立 AI HTTP 接口接入，并在后续业务需求中定制。

## 2. 项目背景

旅游公司的客户来自 Facebook、Instagram、WhatsApp、LINE 等公域渠道。当前存在以下问题：

- 客户消息分散在多个渠道，客服无法统一处理。
- 重复咨询占用人工时间，首次响应速度不稳定。
- 方案介绍、报价跟进和留资提醒依赖人工记忆。
- 客服何时接管、AI 何时停止缺少明确机制。
- 缺少 AI 接管率、转人工原因、咨询卡点和留资转化数据。
- 后续需要面向不同账号、收件箱、团队配置不同策略和权限。

Chatwoot 已提供渠道授权、统一收件箱、联系人、会话、人工坐席、团队、标签和消息 API。本项目不重复建设渠道工作台，而是在 Chatwoot 之外增加 AI 编排、SOP、业务状态、权限和数据分析能力。

## 3. 产品定位

本产品是位于 Chatwoot 与企业 AI 系统之间的“AI 客服运营与控制平台”。

```text
客户渠道
  -> Chatwoot：渠道授权、消息收发、人工工作台
  -> AI 客服运营平台：接管控制、流程编排、SOP、权限、BI
  -> 企业 AI HTTP API：生成回复或返回业务动作
```

### 3.1 Chatwoot 的职责

- Facebook、Instagram 等渠道授权与消息收发。
- 保存联系人、会话和渠道消息。
- 为人工客服提供统一收件箱和回复界面。
- 提供会话历史、消息发送、标签、状态、团队和坐席 API。
- 向本平台推送 Webhook 事件。

### 3.2 自建平台的职责

- 决定一条消息是否允许触发 AI。
- 管理租户、收件箱、会话三级 AI 开关。
- 管理 AI 接管、暂停、人工接管、结束等状态。
- 调用企业 AI HTTP API，并将结果通过 Chatwoot 发回客户。
- 执行主动 SOP、频控、退出条件和发送前检查。
- 管理客户旅程阶段和留资结果。
- 管理用户角色和收件箱数据范围。
- 保存事件、决策、发送结果和操作日志，生成 BI。

### 3.3 企业 AI 系统的职责

- 根据本平台提供的客户消息和必要上下文生成建议回复。
- 根据后续定义的业务规则返回标准化动作，例如回复、转人工、不处理、更新客户阶段等。
- 返回可追踪的调用状态、耗时和错误信息。

## 4. 产品目标

### 4.1 第一阶段目标

- 跑通 Facebook Messenger 客户消息自动回复闭环。
- 支持 AI 开关和明确的人工接管机制。
- 支持已有会话的主动 SOP 跟进。
- 支持客户旅程阶段和联系方式留资记录。
- 支持基础运营后台、账号权限和核心 BI。
- 形成可扩展至 Instagram、WhatsApp、LINE 的统一模型。

### 4.2 业务目标

- 降低重复咨询对人工客服的占用。
- 缩短客户首次响应时间。
- 提升方案介绍和报价后的持续跟进能力。
- 提高客户邮箱、电话、WeChat 等私人联系方式获取率。
- 让人工优先处理投诉、复杂报价、高意向和已留资客户。
- 识别客户流失与转人工的主要卡点。

### 4.3 建议观察指标

MVP 上线后首月先建立基线，不在尚无历史数据时承诺不可靠的增长数字。建议观察：

- Webhook 有效接收率不低于 99.9%。
- 重复自动回复率低于 0.1%。
- AI 自动回复技术成功率不低于 99%。
- 符合条件的自动回复首响中位数不高于 10 秒。
- 人工接管状态下 AI 误回复数量为 0。
- SOP 违反阻止条件发送数量为 0。

留资率、转化率和 AI 独立解决率需在业务规则稳定后再设正式目标。

## 5. 非目标与明确边界

### 5.1 MVP 不包含

- 不从零开发替代 Chatwoot 的完整人工客服聊天工作台。
- 不在自建后台直接承担正式客户消息编辑与人工发送，人工回复仍在 Chatwoot 完成。
- 不实现复杂旅游报价引擎、订单系统或供应链系统。
- 不定义 AI 的具体旅游业务知识和回复内容。
- 不实现公域平台的无条件批量群发。
- 不实现完整 CRM，仅保存客服流程所需的联系人和留资字段。
- 不实现商户自助 OAuth 接入、计费、套餐和完整 SaaS 商业化能力。
- 不以 Chatwoot Captain AI 作为必要依赖。

### 5.2 渠道边界

- Facebook、Instagram、WhatsApp 等渠道均有消息窗口、营销发送和模板消息限制。
- `conversation.can_reply=false` 时，普通自动回复和普通主动消息不得发送。
- 即使 Chatwoot API 技术上接受请求，也不能视为渠道一定允许送达。
- WhatsApp 主动消息可能需要已审批模板；具体规则在接入该渠道时单独补充。
- 客户明确拒绝联系或退订后，所有主动触达必须停止。

### 5.3 数据边界

- Chatwoot Webhook 不是永久历史数据库，本平台必须保存必要事件。
- Chatwoot 历史消息可通过 API 拉取，但不能代替本平台的 AI 决策和 BI 事件记录。
- Chatwoot 标签允许人工修改，不能作为本平台状态的唯一真实来源。
- 联系方式属于敏感数据，必须按角色控制展示、导出和审计。

### 5.4 权限边界

- 自建平台权限只约束自建平台中的操作。
- Chatwoot 人工工作台仍受 Chatwoot 自身账号和角色权限控制。
- 持有 Chatwoot API Token 的人员可以绕过自建后台，因此 Token 只能由服务端托管，不得暴露给浏览器和普通操作人员。

## 6. 用户角色

### 6.1 超级管理员

典型人员：系统建设方或企业最高权限管理员。

主要诉求：

- 管理租户、Chatwoot 连接和服务端密钥。
- 管理全部收件箱、用户、角色和数据范围。
- 查看全部审计记录和系统异常。
- 控制全局 AI 与 SOP 能力。

### 6.2 运营管理员

典型人员：旅游公司客服运营负责人。

主要诉求：

- 查看全部被授权收件箱的运营情况。
- 配置收件箱 AI 开关、人工接管和 SOP。
- 查看客户阶段、转人工原因和留资漏斗。
- 处理异常任务和策略暂停。

### 6.3 客服主管

主要诉求：

- 查看所属团队和收件箱的会话。
- 分配待人工接管会话。
- 暂停或恢复指定会话的 AI。
- 查看团队处理效率、转人工和卡点数据。

### 6.4 人工客服/销售

主要诉求：

- 查看分配给本人或团队的人工接管会话。
- 快速打开 Chatwoot 回复客户。
- 标记会话处理完成、恢复 AI 或结束会话。
- 查看处理所需的客户阶段和联系方式。

### 6.5 BI 只读用户

主要诉求：

- 查看授权范围内的指标和趋势。
- 不允许修改 AI、SOP、标签、分配和客户数据。
- 是否允许导出由管理员单独授权。

## 7. 核心业务对象

### 7.1 租户

代表一个业务组织，对应一个或多个 Chatwoot 工作区。MVP 首期可按一个租户对应一个 Chatwoot `account_id` 实现。

关键属性：

- 租户名称。
- Chatwoot Account ID。
- Chatwoot 服务地址。
- 全局 AI 开关。
- 全局 SOP 开关。
- 时区和默认语言。
- 状态：启用、停用、连接异常。

### 7.2 收件箱

对应 Chatwoot Inbox，是渠道账号与业务策略的主要隔离单位。

关键属性：

- Chatwoot Inbox ID。
- 收件箱名称。
- 渠道类型。
- AI 自动回复开关。
- SOP 开关。
- 默认人工接管团队。
- 允许使用的 AI 配置引用。
- 阻止标签集合。
- 业务时间配置。

### 7.3 联系人

代表渠道中的客户。一个联系人可能有多次会话，后续也可能存在跨渠道身份合并需求。

MVP 关键属性：

- Chatwoot Contact ID。
- 渠道昵称、头像和来源。
- 邮箱、电话、WeChat 及其他联系方式。
- 是否已留资。
- 是否拒绝联系。
- 首次咨询时间和最后活动时间。

MVP 不自动合并不同渠道的同一自然人，避免错误合并。跨渠道统一客户 ID 作为后续能力。

### 7.4 会话

代表客户与某个收件箱的一段 Chatwoot Conversation。

会话同时存在三类状态：

1. Chatwoot 会话状态：`open/pending/snoozed/resolved`。
2. AI 控制状态：`ai_active/ai_paused/human_handoff/completed`。
3. 客户旅程阶段：`new/consulting/proposal/quoted/lead_captured/complaint/closed`。

三类状态解决不同问题，不能互相替代。

### 7.5 消息事件

消息事件记录客户入站消息、AI 出站消息、人工消息和私密备注的必要信息，用于幂等、追踪和 BI。

### 7.6 SOP

SOP 是面向符合条件的已有会话执行的定时跟进流程，包含进入条件、节点、等待时间、退出条件、频控和发送结果。

## 8. 核心状态定义

### 8.1 AI 控制状态

| 状态 | 说明 | 是否允许自动回复 | 是否允许 SOP |
|---|---|---:|---:|
| `ai_active` | AI 正常接管 | 是 | 取决于 SOP 条件 |
| `ai_paused` | 因全局、收件箱或会话开关暂停 | 否 | 否 |
| `human_handoff` | 已转人工，等待或正在人工处理 | 否 | 否 |
| `completed` | 本轮服务已完成 | 否 | 默认否 |

### 8.2 客户旅程阶段

| 阶段 | 含义 | 示例进入条件 |
|---|---|---|
| `new` | 新客户或新会话 | 首条有效入站消息 |
| `consulting` | 基础咨询中 | 已开始了解目的地、时间、人数等 |
| `proposal` | 已进入方案介绍 | 已发送或正在准备行程方案 |
| `quoted` | 已进入报价 | 已发送价格或客户询价 |
| `lead_captured` | 已取得有效私人联系方式 | 电话、邮箱、WeChat 至少一项有效 |
| `complaint` | 客诉或高风险问题 | 由规则、AI 或人工标记 |
| `closed` | 业务流程结束 | 无需继续跟进、拒绝联系或人工关闭 |

AI 如何识别阶段属于后续业务配置。本产品只负责接收、保存、展示和执行阶段相关控制。

### 8.3 人工接管状态规则

- 进入 `human_handoff` 后，即使客户继续发送消息，也不得自动恢复 AI。
- 只有具备权限的人员明确点击“恢复 AI”，会话才能回到 `ai_active`。
- 人工在 Chatwoot 发送消息时，MVP 默认不自动永久改变 AI 状态；是否触发自动暂停由配置决定。
- 推荐配置为：检测到人工坐席已分配或人工发出公开消息时，自动进入 `human_handoff`，避免人与 AI 同时回复。
- 人工接管完成后可选择“恢复 AI”“标记完成”或“保持人工”。

## 9. 端到端业务流程

### 9.1 自动回复主流程

1. 客户通过 Facebook Messenger 向主页发送消息。
2. Chatwoot 接收消息并创建或更新会话。
3. Chatwoot 向本平台 Webhook 地址推送 `message_created`。
4. 本平台立即校验事件格式、记录事件并返回成功，耗时操作进入异步队列。
5. 系统检查消息方向、私密属性、外部回声、可回复状态和消息幂等。
6. 系统检查租户、收件箱和会话 AI 开关。
7. 系统检查会话是否已人工接管、是否被分配人工、是否存在阻止标签。
8. 系统按需从 Chatwoot 拉取最近历史消息。
9. 系统调用企业 AI HTTP API。
10. 根据 AI 标准动作执行回复、不处理、转人工或更新状态。
11. 回复通过 Chatwoot Message API 发回客户。
12. 系统记录 AI 调用、发送结果、耗时和最终动作。

### 9.2 自动回复前置条件

一条消息只有同时满足以下条件才允许进入 AI：

- Webhook 事件为 `message_created`。
- `message_type=incoming`。
- `private=false`。
- `content_attributes.external_echo` 不为 `true`。
- `conversation.can_reply=true`。
- 消息 ID 或 `source_id` 未处理过。
- 租户全局 AI 开关开启。
- 当前收件箱 AI 开关开启。
- 当前会话状态为 `ai_active`。
- 会话未被分配给人工，或符合明确允许 AI 辅助的配置。
- 不存在 `人工接管/客诉/已留资/拒绝联系` 等阻止条件。
- 消息类型在当前版本支持范围内。

任意条件不满足时，不调用 AI、不向客户发送自动回复，但要记录跳过原因。

### 9.3 人工接管流程

人工接管可由以下入口触发：

- AI 返回转人工动作。
- 客户明确要求真人客服。
- 系统规则识别为投诉或高风险场景。
- AI 调用连续失败，超过降级阈值。
- 运营或客服在后台手动点击转人工。
- Chatwoot 中已分配人工或检测到人工公开回复。

标准接管动作：

1. 本地会话状态更新为 `human_handoff`。
2. 记录接管来源、原因、时间和优先级。
3. 读取 Chatwoot 当前标签。
4. 合并写入 `人工接管` 及业务标签，不能覆盖其他已有标签。
5. 根据配置分配 Chatwoot 团队或坐席。
6. 生成通知记录，并通过配置的通知渠道提醒员工。
7. 在人工队列展示，并提供打开 Chatwoot 会话入口。
8. 后续入站消息继续记录，但不触发 AI 和 SOP。

### 9.4 恢复 AI 流程

1. 客服完成当前人工处理。
2. 客服在本平台选择“恢复 AI”。
3. 系统要求确认当前会话没有客诉、拒绝联系等强阻止状态。
4. 系统将状态切回 `ai_active`。
5. 系统从 Chatwoot 标签中移除 `人工接管`，保留其他标签。
6. 是否取消团队/坐席分配由收件箱配置决定。
7. 系统记录操作人、操作时间和恢复原因。

恢复 AI 后不应立即补发历史消息。只有新的客户入站消息或合法的后续 SOP 到期时才继续处理。

### 9.5 主动 SOP 流程

1. 运营创建 SOP，设置进入条件、节点等待时间、退出条件和频控。
2. 符合条件的会话进入 SOP，生成独立执行实例。
3. 调度器扫描到期节点并锁定任务。
4. 发送前重新读取最新会话状态、标签、人工分配和渠道可回复状态。
5. 任一阻止条件命中则跳过、暂停或退出 SOP，并记录原因。
6. 允许发送时，系统生成节点消息并通过 Chatwoot API 发送。
7. 成功后推进下一节点；失败时执行有限重试。
8. 客户回复、转人工、已留资、拒绝联系或流程结束时退出 SOP。
9. 系统记录触达、回复和留资归因。

### 9.6 留资流程

1. 系统从 AI 标准动作或人工操作中接收联系方式更新。
2. 系统校验联系方式类型和基本格式。
3. 将联系方式保存到本地联系人记录。
4. 在允许的情况下同步到 Chatwoot Contact。
5. 将旅程阶段更新为 `lead_captured`。
6. 合并写入 Chatwoot `已留资` 标签。
7. 终止以获取联系方式为目标的 SOP。
8. 根据配置进入销售人工接管或后续跟进流程。

“客户在消息中出现疑似联系方式”不等同于“有效留资”。是否有效由后续 AI/规则或人工确认机制决定。

## 10. 业务场景清单

### SC-01 新客户首次咨询

前置条件：客户从 Facebook 首次发送消息，AI 开关均开启。

预期结果：

- 系统创建本地会话控制记录。
- AI 状态为 `ai_active`，旅程阶段为 `new` 或 `consulting`。
- 调用 AI 并通过 Chatwoot 回复。
- 记录首次响应时间和 AI 接管事实。

### SC-02 老客户继续已有会话

前置条件：Chatwoot 已有联系人和会话，状态允许回复。

预期结果：

- 使用同一 Chatwoot Conversation ID 关联历史。
- 拉取必要的最近消息作为上下文。
- 不依赖本平台是否保存了全部历史消息才能处理。

### SC-03 Chatwoot 出站消息回流

场景：人工或系统从 Chatwoot 发出消息，渠道再次将其作为外部回声推送。

预期结果：

- `message_type=outgoing` 或 `external_echo=true` 时禁止触发 AI。
- 消息可记录为出站事件，用于统计，不得形成回复循环。

### SC-04 客户要求人工

场景：客户明确表达“转人工”“我要真人”等意图。

预期结果：

- AI 或业务规则返回转人工动作。
- 会话进入 `human_handoff`。
- Chatwoot 增加 `人工接管` 标签并分配默认团队。
- 发送通知；是否给客户发送“正在转接”消息由业务配置决定。

### SC-05 客诉与高风险问题

场景：客户投诉、退款争议、重大行程异常或其他高风险内容。

预期结果：

- 会话阶段设为 `complaint`。
- 增加 `客诉` 和 `人工接管` 标签。
- 停止 AI 和全部 SOP。
- 进入高优先级人工队列并通知主管。

### SC-06 取得联系方式

场景：客户提供电话、邮箱或 WeChat。

预期结果：

- 保存经确认的联系方式。
- 阶段设为 `lead_captured`。
- 增加 `已留资` 标签。
- 退出留资型 SOP。
- 可按配置转销售团队，不再继续重复索取联系方式。

### SC-07 客户拒绝联系

场景：客户明确要求停止联系或不再发送消息。

预期结果：

- 标记 `拒绝联系`。
- 终止所有 SOP。
- 禁止后续主动消息。
- 自动回复是否发送最终确认消息由渠道规则和业务配置决定，最多一次。

### SC-08 方案发送后未回复

场景：客户已进入 `proposal`，在配置时间内没有新回复。

预期结果：

- 满足 SOP 人群条件时进入跟进流程。
- 节点到期前如果已转人工、已留资或客户已回复，则取消发送。
- 发送成功后记录节点、消息 ID 和归因窗口。

### SC-09 报价后跟进

场景：客户处于 `quoted` 阶段且超过设定等待时间。

预期结果：

- 仅在渠道允许且未人工接管时触达。
- 客户回复后退出当前等待节点，并回到正常消息处理。
- 不允许多个 SOP 在同一时间对同一会话重复发送。

### SC-10 人工正在处理时客户再次发消息

预期结果：

- 保存新消息并更新人工队列等待信息。
- 不触发 AI，不自动恢复。
- 可再次通知当前坐席，但应有通知频控。

### SC-11 人工处理后恢复 AI

预期结果：

- 必须由有权限用户明确操作。
- 移除人工阻止状态但保留客诉、已留资等其他业务标签。
- 不补发人工接管期间的旧消息。

### SC-12 租户全局关闭 AI

场景：管理员因维护、风险或活动策略关闭全局 AI。

预期结果：

- 所有收件箱停止新的 AI 调用和主动 SOP。
- Chatwoot 继续接收消息，人工工作台不受影响。
- 已在执行中的任务应在发送前再次检查开关并停止。

### SC-13 单个收件箱关闭 AI

预期结果：

- 只影响指定 Inbox ID。
- 其他收件箱正常运行。
- 后台清楚展示实际生效状态和上级全局开关状态。

### SC-14 单个会话暂停 AI

预期结果：

- 只影响指定 Conversation ID。
- 可填写暂停原因。
- 暂停期间不自动回复、不进入或执行 SOP。

### SC-15 Webhook 重复投递

预期结果：

- 通过 Chatwoot Message ID 或 `source_id` 幂等去重。
- 同一消息最多产生一次 AI 任务和一次客户回复。
- 重复事件记录为幂等命中，不计入有效入站数。

### SC-16 Webhook 乱序

预期结果：

- 事件按消息发生时间和 ID 保存。
- 发送前获取最新会话控制状态。
- 已进入人工接管后，即使较早的 AI 任务晚到，也不得发送。

### SC-17 AI 接口超时或失败

预期结果：

- 按配置执行有限重试，不无限阻塞 Webhook。
- 同一请求保持幂等。
- 超过阈值后记录失败，可转人工或保持静默，策略由配置决定。
- 不向客户泄露系统异常、堆栈或内部错误。

### SC-18 Chatwoot API 发送失败

预期结果：

- 保存回复内容与发送失败状态。
- 区分鉴权失败、渠道不可回复、限流和临时网络异常。
- 临时异常有限重试；确定不可回复时停止。
- 未确认发送成功前不能计入“AI 已回复”。

### SC-19 标签被人工修改

预期结果：

- Chatwoot 手工修改会话标签后，通过 `conversation_updated` Webhook 实时更新本地会话标签快照和最终 AI 状态。
- Chatwoot 手工修改联系人标签后，通过 `contact_updated` Webhook 更新本地联系人标签快照；事件字段不足时再调用 Contact Labels API 拉取完整列表。
- 会话标签控制当前会话是否允许 AI；联系人标签只承载 `拒绝联系`、`黑名单` 等跨会话强阻止事实，不能用联系人标签代替会话状态。
- Webhook 可能延迟或丢失，因此每次 AI/SOP 发送前仍需读取或校验最新状态，并定期执行标签对账。
- 写标签必须先读取并合并，避免覆盖人工标签。
- 本地核心状态不因未知标签被删除而自动失效。
- 标签与本地状态冲突时记录同步异常，按安全优先原则停止 AI。

### SC-20 Chatwoot Token 失效

预期结果：

- 所有依赖 Chatwoot API 的动作进入失败状态。
- 系统告警并在后台展示连接异常。
- 不继续盲目重试导致限流。
- 更新 Token 后支持人工重试未完成任务。

## 11. 功能需求

优先级定义：

- P0：MVP 上线必须具备。
- P1：MVP 应具备，必要时可在主链路稳定后补齐。
- P2：后续增强。

### 11.1 Chatwoot 连接管理

#### FR-CW-001 工作区连接配置（P0）

系统应支持配置：

- Chatwoot Base URL。
- Chatwoot Account ID。
- API Token，必须加密保存且前端不可回显明文。
- Webhook 接收地址和连接状态。

验收要求：

- 管理员可执行连接测试。
- 默认连接测试只验证账号、收件箱和会话的只读访问，不得向真实客户自动发送测试消息。
- 消息发送权限只能由管理员明确选择测试会话后人工验证，并在发送前二次确认。
- Token 失效时后台显示明确错误和最后成功时间。

#### FR-CW-002 收件箱同步（P0）

- 从 Chatwoot 同步收件箱 ID、名称和渠道类型。
- 可对每个收件箱独立启停 AI 与 SOP。
- 可配置默认转接团队。
- 不允许操作用户未授权的数据范围。

#### FR-CW-003 团队、坐席、标签同步（P0）

- 同步 Chatwoot 团队和坐席，用于人工分配。
- 同步可用标签，用于阻止规则和展示。
- 同步失败不能删除本地已有配置，应标记为过期或不可用。

#### FR-CW-004 Webhook 管理（P0）

- 提供固定 HTTPS Webhook 地址。
- MVP 必须处理 `message_created`。
- 支持记录接收时间、来源、事件类型、处理状态和错误。
- 原始载荷保存周期应可配置并考虑敏感信息。

### 11.2 消息接收与幂等

#### FR-MSG-001 消息有效性过滤（P0）

系统必须根据实际字段过滤：

```text
event = message_created
message_type = incoming
private = false
external_echo != true
conversation.can_reply = true
```

不满足条件的事件记录跳过原因，但不进入 AI。

#### FR-MSG-002 幂等去重（P0）

- 优先使用 Chatwoot Message ID 作为唯一键。
- `source_id` 作为渠道侧辅助唯一键。
- Webhook 重试、队列重试和服务重启都不能产生重复回复。
- AI 调用与 Chatwoot 发送分别具有幂等状态。

#### FR-MSG-003 历史消息读取（P0）

- 系统可按 Conversation ID 获取会话详情和历史消息。
- 默认只读取 AI 接口需要的最近上下文，不无限拉取。
- Chatwoot 当前 API 行为：`before` 最多 20 条，`after` 最多 100 条。
- 历史拉取失败时的处理策略可配置为不回复或转人工。

#### FR-MSG-004 消息类型支持（P0/P1）

P0：文本入站与文本出站。

P1：图片、文件等附件入站识别和出站附件发送。

不支持的消息类型：

- 不调用无法处理的 AI 能力。
- 可配置转人工或发送一次标准提示。
- 必须记录“不支持的消息类型”卡点。

### 11.3 AI 接管控制

#### FR-AI-001 三级开关（P0）

系统提供：

1. 租户全局 AI 开关。
2. 收件箱 AI 开关。
3. 会话 AI 开关/状态，由本地状态与 Chatwoot 会话标签共同决定。

只有三级均允许时才可调用 AI。界面应显示“本级配置”和“最终生效状态”，避免上级关闭后下级仍显示为开启造成误解。

Chatwoot Account 对应本平台租户连接，一个 Account Webhook 可接收该工作区事件；平台按 `account.id` 和 `inbox.id` 路由。Webhook 不按单个客服账号分别配置，客服账号只参与 Chatwoot 人工权限和本平台 RBAC 映射。

#### FR-AI-002 会话决策前检查（P0）

每次调用 AI 前必须检查：

- 最新 AI 控制状态。
- Chatwoot 当前分配和标签。
- 当前消息是否已处理。
- 当前会话是否允许回复。
- 是否存在更晚的人工接管操作。

#### FR-AI-003 企业 AI HTTP 接口配置（P0）

支持配置：

- 接口地址。
- 鉴权方式和服务端密钥。
- 超时时间。
- 最大重试次数。
- 当前启用版本或配置引用。
- 健康检查状态。

不在前端展示密钥明文。

#### FR-AI-004 标准动作契约（P0）

AI 接口至少支持返回以下动作类型：

- `reply`：回复客户。
- `handoff`：转人工。
- `no_action`：不处理。
- `update_stage`：更新客户旅程阶段。
- `capture_contact`：提交待确认或已确认联系方式。

具体 AI 如何做出动作不属于本 PRD。平台只校验动作是否合法并执行允许的动作。

#### FR-AI-005 回复发送（P0）

- 调用 Chatwoot Message API 发送 `outgoing`、`private=false` 消息。
- 发送前再次检查会话状态，避免排队期间人工已接管。
- Chatwoot 返回成功后只将消息标记为“已提交/已创建”，不能直接视为渠道送达。
- 保存 Chatwoot 返回的消息 ID、提交时间和状态，并通过 `message_updated` 或消息查询确认 `delivered/failed`。

#### FR-AI-006 AI 调用记录（P0）

至少记录：

- 关联会话和触发消息。
- 请求开始、结束和耗时。
- 调用状态和错误码。
- 返回动作类型。
- 是否执行成功。
- AI 配置或版本引用。

为减少敏感信息风险，完整请求和完整回复的保存范围、脱敏和保留周期必须可配置。

### 11.4 会话控制台

#### FR-CONV-001 会话列表（P0）

列表应支持：

- 按联系人、会话 ID 搜索。
- 按渠道、收件箱、AI 状态、旅程阶段、标签、团队、坐席筛选。
- 展示最后消息、最后活动时间和当前等待时间。
- 标识 AI 处理中、AI 暂停、人工接管、已留资、客诉等重要状态。

#### FR-CONV-002 会话详情（P0）

详情应展示：

- 联系人和渠道基本信息。
- Chatwoot Conversation ID 和打开 Chatwoot 的入口。
- 最近消息时间线。
- 当前 AI 控制状态及原因。
- 当前旅程阶段、标签、团队和坐席。
- 已获取联系方式。
- 最近 AI 动作和同步异常。

自建后台中的消息时间线主要用于运营判断，不取代 Chatwoot 正式聊天界面。

#### FR-CONV-003 手动暂停与恢复（P0）

- 有权限用户可暂停单个会话 AI，并填写原因。
- 有权限用户可明确恢复 AI。
- 所有操作写入审计日志。
- 恢复操作必须进行阻止条件检查。

#### FR-CONV-004 旅程阶段修改（P0）

- 有权限用户可手动修改旅程阶段。
- 系统记录修改前后值、操作人和原因。
- 手工修改优先级高于未执行的旧 AI 任务。

### 11.5 人工接管

#### FR-HO-001 转人工动作（P0）

支持 AI、规则、系统异常和人工四种来源。转接时必须保存：

- 接管原因分类。
- 原因说明。
- 优先级。
- 目标团队/坐席。
- 触发来源和时间。

#### FR-HO-002 Chatwoot 标签同步（P0）

- 写标签前读取当前标签。
- 对目标标签执行合并或移除后全量写回。
- 不得直接用单个新标签覆盖原标签数组。
- 同步失败时，本地仍保持 `human_handoff`，按照安全原则禁止 AI。

#### FR-HO-003 Chatwoot 分配（P0）

- 支持分配团队或坐席。
- 同时提交时以坐席为准，与 Chatwoot API 行为保持一致。
- 分配失败时保留人工队列任务并标记异常。

#### FR-HO-004 人工队列（P0）

支持：

- 待接管、处理中、已完成筛选。
- 按优先级、团队、等待时间和原因排序。
- 领取、重新分配、打开 Chatwoot、恢复 AI、标记完成。
- 显示等待超时提醒。

#### FR-HO-005 员工通知（P1）

- 支持配置通知渠道，例如邮件、企业微信、Slack 等。
- 通知包含客户、渠道、会话链接、接管原因、优先级和摘要。
- 相同会话短时间连续消息应合并或频控，避免通知轰炸。

### 11.6 标签与客户阶段

#### FR-TAG-001 系统标签约定（P0）

建议首期使用：

- `AI处理中`
- `人工接管`
- `客诉`
- `已留资`
- `拒绝联系`
- `报价中`

标签名称应可配置映射，避免企业已有同名或不同语言标签。

#### FR-TAG-002 阻止标签（P0）

每个收件箱可配置阻止 AI 和 SOP 的标签集合。默认阻止：

- 人工接管。
- 客诉。
- 已留资。
- 拒绝联系。

业务可决定“已留资”是完全停止 AI，还是仅停止留资型 SOP；MVP 默认按安全策略完全停止自动接管，人工恢复后才继续。

#### FR-TAG-003 自定义属性同步（P1）

- 支持将必要业务状态同步到 Chatwoot Conversation Custom Attributes。
- 更新时必须使用合并模式，避免覆盖 Chatwoot 其他属性。
- 本地数据库仍是 AI 控制状态的主数据源。

### 11.7 联系方式与客户资料

#### FR-LEAD-001 联系方式类型（P0）

至少支持：

- 邮箱。
- 电话。
- WeChat。
- 其他联系方式及备注。

#### FR-LEAD-002 联系方式状态（P0）

联系方式应区分：

- 待确认：系统识别到但尚未确认有效。
- 已确认：通过格式、业务规则或人工确认。
- 无效：格式错误或客户否认。

只有“已确认”可计入留资率。

#### FR-LEAD-003 隐私与脱敏（P0）

- 按角色控制联系方式可见范围。
- 客服可配置只显示部分脱敏内容。
- 查看完整联系方式、修改和导出必须记录审计。
- API 和日志不得无必要输出完整联系方式。

#### FR-LEAD-004 Chatwoot 联系人同步（P1）

- 邮箱、电话可同步至 Chatwoot Contact 对应字段。
- WeChat 等可同步至自定义属性。
- 同步失败不影响本地留资记录，但需显示同步状态。

### 11.8 SOP 触达

#### FR-SOP-001 SOP 列表（P0）

展示：

- 名称、状态和适用收件箱。
- 目标人群摘要。
- 节点数量。
- 累计进入、成功触达、回复率和留资率。
- 草稿、运行、暂停、归档状态。

#### FR-SOP-002 进入条件（P0）

可基于以下字段组合：

- 收件箱和渠道。
- 旅程阶段。
- Chatwoot 标签。
- AI 控制状态。
- 最后客户消息时间。
- 最后出站消息时间。
- 是否已留资。
- 是否拒绝联系。

MVP 使用结构化条件，不支持任意 SQL 或脚本。

#### FR-SOP-003 SOP 节点（P0）

节点至少包含：

- 节点顺序。
- 调度类型：相对时间、固定日期时间或指定周期时间。
- 相对等待时长、固定执行时间和租户时区。
- 消息内容来源或模板引用。
- 消息类型：文本、图片、音频、视频、文件或渠道支持的交互消息。
- 适用渠道。
- 发送失败处理。
- 节点后是否继续等待。

具体消息由固定模板还是 AI 生成属于业务配置，但发送前控制规则一致。

SOP 的调度、等待、分支、重试和退出由本平台执行，Chatwoot 只在任务到期时提供消息发送能力。首期渠道能力约束如下：

| 消息类型 | Facebook Messenger | Instagram DM | MVP 处理 |
|---|---|---|---|
| 文本 | 支持 | 支持 | P0 |
| 图片 | 支持 | 支持 | P0，使用稳定对象存储并以附件上传 |
| 音频 | 支持 | 支持 | P1 |
| 视频 | 支持 | 支持 | P1 |
| 文件 | 支持 | 不支持 | Facebook P1，Instagram 禁用 |
| 快捷回复 `input_select` | 当前源码支持 | 当前源码未实现 | Facebook P1，Instagram 退化为文本 |
| Cards/Form/Article | 不承诺原生稳定展示 | 不承诺原生稳定展示 | MVP 禁用 |

文本与多个附件在渠道侧可能被拆为多条消息，编辑器必须预览拆分结果。附件通过 `multipart/form-data` 的 `attachments[]` 上传，不接受把临时 URL 直接作为附件 JSON。

#### FR-SOP-004 退出条件（P0）

默认退出条件：

- 客户产生新的入站回复。
- 会话进入人工接管。
- 会话进入客诉。
- 已取得目标联系方式。
- 客户拒绝联系。
- 会话已结束。
- 收件箱或全局 SOP 被关闭。

#### FR-SOP-005 频控（P0）

- 同一会话同一时间只允许一个发送任务执行。
- 支持单会话每日最大主动消息数。
- 支持同一联系人跨会话的每日最大主动消息数。
- 支持最小消息间隔。
- 频控命中必须记录原因，不得静默丢弃。

#### FR-SOP-006 发送前最终检查（P0）

发送前必须重新检查：

- SOP、租户和收件箱开关。
- 当前会话 AI/人工状态。
- 最新标签和人工分配。
- 是否收到更新的客户回复。
- 是否已留资或拒绝联系。
- 渠道是否允许回复。
- 是否仍处于渠道允许的自动化发送窗口。
- 当前节点消息类型、文件 MIME 和大小是否被目标渠道支持。
- 频控是否通过。

#### FR-SOP-007 SOP 版本（P1）

- 运行中的 SOP 修改后生成新版本。
- 已进入旧版本的实例按产品配置继续旧版本或迁移。
- 历史指标必须保留对应版本，不能因修改模板而失去解释能力。

### 11.9 数据分析

#### FR-BI-001 运营总览（P0）

展示：

- 有效入站会话数。
- AI 接管率。
- 待人工接管数和超时数。
- 留资率。
- AI/Chatwoot/SOP 异常数。
- AI 与人工消息趋势。
- 客户旅程漏斗。

#### FR-BI-002 AI 表现（P0）

展示：

- AI 接管会话数。
- AI 实际回复会话数。
- AI 独立解决率。
- 人工转接率。
- AI 调用成功率和响应耗时。
- 跳过原因和失败原因。

#### FR-BI-003 转人工与卡点（P0）

支持按以下维度查看：

- 客户要求人工。
- 需要人工报价。
- 客诉/高风险。
- 不支持的消息类型。
- AI 接口异常。
- Chatwoot 发送异常。
- 渠道不可回复。
- 其他业务原因。

#### FR-BI-004 留资漏斗（P0）

展示：

- 有效咨询。
- 进入方案介绍。
- 进入报价。
- 成功留资。
- 转销售人工跟进。

支持按日期、渠道、收件箱、团队和 SOP 筛选。

#### FR-BI-005 SOP 效果（P0）

展示：

- 进入人数/会话数。
- 计划任务数。
- 成功触达数。
- 跳过与失败数。
- 触达后回复率。
- 触达后留资率。
- 各节点流失和退出原因。

#### FR-BI-006 数据追溯（P1）

核心指标应可追溯到会话或事件明细。只读用户是否可查看联系人明细由数据权限决定。

### 11.10 用户、角色与数据范围

#### FR-RBAC-001 用户管理（P0）

- 创建、停用和恢复后台用户。
- 分配一个或多个角色。
- 配置可访问租户、收件箱和团队范围。
- 停用用户后立即撤销后台访问。

#### FR-RBAC-002 角色权限（P0）

至少提供：

- 超级管理员。
- 运营管理员。
- 客服主管。
- 客服/销售。
- BI 只读。

支持控制查看、配置、接管、恢复、导出和密钥管理权限。

#### FR-RBAC-003 数据范围（P0）

## 14. 标签与状态冲突规则

### 14.1 安全优先级

当多个状态冲突时，按以下优先级决定是否允许自动发送：

```text
拒绝联系 / 客诉
  > 人工接管
  > 全局或收件箱关闭
  > 会话暂停
  > 已留资策略
  > AI 正常接管
```

高优先级阻止条件不能被低优先级开关覆盖。

### 14.2 示例

- 会话 AI 开关开启，但标签为 `人工接管`：禁止 AI。
- 收件箱 AI 开启，但全局 AI 关闭：禁止 AI。
- 会话状态为 `ai_active`，但 Chatwoot 已分配人工：默认禁止 AI并同步为人工接管。
- 已留资但运营希望继续售后 AI：必须通过独立业务策略明确允许，不能直接删除留资事实。
- 标签同步失败：保持本地阻止状态，不允许 AI 冒险回复。

## 15. SOP 产品规则

### 15.1 SOP 与自动回复的区别

| 项目 | 自动回复 | SOP 主动触达 |
|---|---|---|
| 触发方式 | 客户新消息 | 时间或阶段条件到期 |
| 是否必须有新入站消息 | 是 | 否 |
| 发送前渠道检查 | 必须 | 必须，要求更严格 |
| 退出条件 | 当前消息处理完成 | 回复、转人工、留资、退订等 |
| 主要风险 | 重复回复、与人工冲突 | 违规主动触达、频率过高 |

“SOP 不需要当前时刻出现新入站消息”不等于可以无限制主动发送。Facebook 和 Instagram 不能由企业创建第一条会话，必须先存在客户发起的会话；自动化消息默认限制在客户最后入站后的 24 小时窗口内。Human Agent 延长窗口只适用于真实人工处理，不得用于 AI/SOP 自动营销。

### 15.2 并发规则

- 同一会话同一时刻只能执行一个客户可见的出站动作。
- 客户新消息到达时，优先处理新消息并取消未发送的到期 SOP 任务。
- 人工接管动作优先于所有未发送 AI/SOP 任务。
- 已经向 Chatwoot 成功提交的消息不能通过本平台假设撤回。

### 15.3 归因规则

SOP 回复和留资归因必须配置时间窗口，例如发送后 24 小时。若期间有多个 SOP 节点：

- 默认归因给最近一次成功触达节点。
- 不成功送达的节点不参与归因。
- 人工消息和其他营销活动可能影响结果，BI 中应标明这是运营归因而非严格因果关系。

## 16. BI 指标口径

### 16.1 基础定义

| 指标 | 定义 |
|---|---|
| 有效入站消息 | 通过 incoming、非私密、非 echo 和幂等检查的客户消息 |
| 有效入站会话 | 统计周期内至少有一条有效入站消息的去重会话 |
| AI 接管会话 | 统计周期内至少产生一次有效 AI 调用的会话 |
| AI 已回复会话 | 至少有一条 AI 消息被 Chatwoot 确认发送的会话 |
| 人工接管会话 | 至少进入一次 `human_handoff` 的会话 |
| 成功留资会话 | 至少新增一种“已确认”联系方式的会话 |

### 16.2 核心公式

- AI 接管率 = AI 接管会话 / 有效入站会话。
- AI 独立解决率 = 未转人工且完成的 AI 接管会话 / AI 接管会话。
- 人工转接率 = 人工接管会话 / AI 接管会话。
- 留资率 = 成功留资会话 / 有效咨询会话。
- AI 留资贡献率 = AI 接管期间成功留资会话 / 全部成功留资会话。
- SOP 触达成功率 = 成功发送节点数 / 实际尝试发送节点数。
- SOP 回复率 = 归因窗口内产生客户回复的触达会话 / 成功触达会话。
- SOP 留资率 = 归因窗口内成功留资会话 / 成功触达会话。

### 16.3 时间与去重

- 默认按租户时区统计。
- 会话指标按 Conversation ID 去重。
- 联系人指标按 Chatwoot Contact ID 去重。
- 跨渠道同一自然人在 MVP 中仍按不同联系人统计。
- 指标页面必须显示日期范围、筛选条件和去重单位。

## 17. 异常与降级策略

| 异常 | 默认处理 | 是否自动重试 | 是否转人工 |
|---|---|---:|---:|
| Webhook 格式错误 | 记录并拒绝处理 | 否 | 否 |
| Webhook 重复 | 幂等跳过 | 否 | 否 |
| 历史消息拉取失败 | 停止本次 AI | 有限 | 可配置 |
| AI 超时/5xx | 保持消息待处理 | 有限 | 超阈值可转 |
| AI 返回非法动作 | 不执行，记录错误 | 否 | 可配置 |
| Chatwoot 鉴权失败 | 暂停发送并告警 | 否 | 否 |
| Chatwoot 限流/临时 5xx | 延迟重试 | 有限 | 否 |
| `can_reply=false` | 不发送 | 否 | 可进入运营异常 |
| 标签同步失败 | 本地保持阻止 | 有限 | 已转人工则继续人工 |
| 团队分配失败 | 保留人工队列 | 有限 | 是 |
| 通知失败 | 不影响人工状态 | 有限 | 已转人工 |
| 队列积压 | 告警，发送前重检状态 | 否 | 视时效配置 |

所有重试必须带幂等键。不能用“重试”作为绕过最新开关和人工状态检查的方式。

## 18. 非功能需求

### 18.1 性能

- Webhook 接口应快速完成校验和入队，目标 3 秒内返回 2xx。
- AI 和 Chatwoot 调用均异步执行，不阻塞 Webhook。
- 会话列表常用筛选在正常数据量下目标 2 秒内返回。
- BI 聚合查询目标 5 秒内返回；复杂明细允许异步导出。

### 18.2 可用性

- Webhook 接收和任务执行分离，服务重启不丢已入库任务。
- 核心任务具有明确的待处理、处理中、成功、失败、终止状态。
- 队列消费者可水平扩展，但同一会话出站动作需要串行控制。

### 18.3 安全

- 所有外部接口必须使用 HTTPS。
- Chatwoot Token、AI Token 和通知密钥必须加密保存。
- 密钥不得进入前端、普通日志和 BI。
- 后端对每个请求执行租户和数据范围校验。
- 敏感字段按角色脱敏。
- 管理操作和敏感数据访问写审计日志。
- 建议支持 Webhook 来源校验、随机路径密钥或签名机制；Chatwoot 实际可用的验签方式需在实施时确认。

### 18.4 隐私与保留

- 原始 Webhook、消息正文、AI 请求响应和联系方式分别配置保留周期。
- 业务不需要的字段不长期复制。
- 日志中的客户文本和联系方式应支持脱敏。
- 客户删除、数据导出和保留政策根据企业合规要求另行确认。

### 18.5 可观测性

- 每条 Webhook、AI Run、Chatwoot 发送和 SOP Execution 使用关联追踪 ID。
- 监控成功率、耗时、队列积压、重试和死信任务。
- 告警应包含租户、收件箱、会话、任务类型和错误分类，但不直接暴露完整敏感内容。

## 20. 通知规则

### 20.1 需要通知的事件

- P1 客诉或高风险人工接管。
- 普通人工接管进入队列。
- 人工队列超过 SLA。
- Chatwoot Token 失效。
- AI 服务连续失败超过阈值。
- Webhook 长时间无消息但渠道有活动迹象。
- SOP 大量失败或被渠道拒绝。

### 20.2 通知频控

- 同一会话相同原因在配置时间内只发送一次通知。
- 新的更高优先级事件可突破频控。
- 通知失败不回滚人工接管状态。
- 通知记录可查看发送状态和重试情况。

## 21. MVP 验收标准

### 21.1 自动回复

1. 客户发送合法文本消息后，Webhook 能正确入库并异步处理。
2. 合格消息触发一次 AI 请求，并通过 Chatwoot 发送一次回复。
3. 重复 Webhook、服务重启和队列重试不产生重复回复。
4. outgoing、private、external echo 消息不触发 AI。
5. `can_reply=false` 时不发送普通自动消息。
6. 租户、收件箱、会话任一级关闭时不触发 AI。

### 21.2 人工接管

1. 转人工后本地状态、Chatwoot 标签、团队分配和人工队列一致。
2. 人工状态下客户继续发消息不触发 AI。
3. 人工明确恢复后，只有新消息才能继续触发 AI。
4. 标签写入不覆盖人工已有的其他标签。
5. 分配或标签同步失败时仍保持 AI 阻止状态。

### 21.3 SOP

1. 到期任务只执行一次。
2. 发送前重新检查最新状态。
3. 客户已回复、已转人工、已留资、已退订时不发送。
4. 渠道不可回复时不强行发送。
5. 节点成功、失败、跳过和退出均有可追踪记录。
6. 频控可阻止短时间重复触达。

### 21.4 权限

1. 用户只能查看授权的租户、收件箱、团队和会话。
2. 前端隐藏和后端授权结果一致。
3. API Token 和其他密钥不出现在浏览器网络响应中。
4. 关键操作和敏感数据访问均有审计记录。

### 21.5 BI

1. 指标可以按日期、渠道、收件箱和团队筛选。
2. AI 接管、人工转接、成功留资和 SOP 触达口径符合本文定义。
3. Webhook 重复不增加有效消息或会话数。
4. 发送失败不计入成功回复或成功触达。
5. 核心指标能追溯到事件或会话明细。

## 24. 待业务确认项

以下事项不会阻塞产品原型，但会影响开发配置和验收：

1. 获取联系方式后，是立即转销售人工，还是允许 AI 继续服务。
2. “已留资”是否默认完全停止 AI，还是只退出留资型 SOP。
3. 人工在 Chatwoot 发出任意公开消息后，是否自动永久转人工。
4. 人工完成后由谁有权恢复 AI，是否需要主管审批。
5. 客诉、高风险、退款、复杂报价等接管原因的正式分类。
6. 人工队列的优先级和 SLA 时间。
7. 员工通知使用邮件、企业微信、Slack 或其他渠道。
8. 电话、邮箱、WeChat 的有效性确认方式。
9. SOP 单客户每日发送上限和最小消息间隔。
10. 消息正文、AI 请求响应和联系方式的保留周期。
11. BI 中“完成会话”和“有效咨询”的正式业务定义。
12. Facebook/Instagram 主动触达的具体合规文案与范围。

在上述事项未确认前，系统应采用安全默认值：停止优先、人工优先、少发优先、敏感数据少展示优先。
