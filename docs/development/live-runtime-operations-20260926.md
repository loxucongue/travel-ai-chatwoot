# 正式接待运行与发布说明（2026-09-26）

本说明对应本次可靠性改造后的源码。此前架构审查见 [审查报告](architecture-review-20260926.md)。本次没有更新生产部署、生产通知设置或向客户发送消息。

## 运行结构

- API：`app.main:app`，提供登录、业务接口和健康检查。
- 正式接待：从 `backend` 目录运行 `python -m app.live_reply_worker`，每个数据库/主机仅运行一个实例。
- 该进程内，主循环负责 Relay 拉取、消息镜像、任务调度；受限线程池负责客户回复和 SOP；独立维护线程负责转人工超时、内部通知、回执检查和 SOP 补查。
- 同一会话的回复和 SOP 共用一个执行名额，不会在本调度器中同时运行。不同会话最多并行 2 个任务，可用 `LIVE_REPLY_CONCURRENCY=1..4` 调整。
- 单机文件锁仍然必要。SQL 原子领取仅能防同一个任务重复执行，不能替代跨会话任务的调度约束。不要多启动正式进程或旧 `worker_main` 来扩容，也不要跨主机共享 SQLite。
- 演练继续使用原有 evaluation/playground 入口；演练不消费对外通知。

这次并行的是会话任务，不是同一客户的消息分段。分段等待仍在该会话任务内保留，但不再阻塞消息接收、内部通知和其他执行名额。没有改动模型提示词、报价事实、线路资料或默认接待范围。

## 顾问通知

入口：系统设置 → 顾问通知。

两种渠道择一：

1. Chatwoot 手机提醒：选择实际接收顾问，填写已建立的通知 AgentBot ID，再启用。发送内容固定为私密备注，包含顾问提及和 `ai-notification:<id>` 标记。程序核对顾问属于目标收件箱，并检查响应中的私密标志及机器人身份。
2. Webhook：保留原来的 URL、加密 HMAC 密钥和事件选择；增加稳定的 `Idempotency-Key`。接收端应按该键去重。

本次没有自动修改已保存的通知渠道或凭据。旧配置缺省仍按 Webhook 解释，无数据库迁移。手机接收需要 Chatwoot App 的通知授权和提及通知偏好；服务端提交成功不能等同于 iPhone 或 Apple Watch 已显示。

默认事件是 `handoff.created` 和 `handoff.overdue`。客户普通新消息继续由 Chatwoot 的分配/新消息通知负责，这次没有额外给每条客户消息重复发备注。

两个发送开关的边界：

- `APP_PROFILE`、`OUTBOUND_MODE`、`CHATWOOT_WRITE_ENABLED` 是环境级权限，关闭时不派发通知。
- 后台“全局停发”控制客户消息。严格为 JSON 布尔值 `private=true` 的内部备注不受这个客户消息开关影响；公有消息和附件仍被阻止。
- 关闭“顾问通知”会暂停已排队的提醒，保留站内通知和队列；重新启用后继续处理。启用前应考虑积压提醒是否仍需要处理。

通知状态：

| 状态 | 含义与处理 |
|---|---|
| pending / retry | 等待发送或重试；Webhook 最多尝试 5 次 |
| delivered | 通知接口已确认成功，不代表设备已展示 |
| dead | 配置无效或重试耗尽，检查配置和错误码 |
| submission_unknown | 已记录发送意图，但无法确定接口结果；不自动重复投递 |

遇到 `submission_unknown`，根据通知 ID 到对应 Chatwoot 会话检查私密备注中的标记，先核实结果，不能直接重置队列来重发。本轮未新增不确定通知的自动远端对账或人工重试界面；健康检查会把这些记录列为需处理问题。

## 过期消息与人工状态

保留约 5 分钟的自动回复新鲜度限制。激活时间之前的历史消息不自动重放；激活后过期、在接待范围内且未被更新消息或公开回复覆盖的消息，会建立高优先级人工任务。

- Relay 积压到达：保存消息，建立人工兜底，不根据旧消息自动发回复。
- 回复任务排队至过期：发送前检查阻止回复，建立人工兜底。
- 模型临时故障且输入已过期：不再遗漏人工任务。
- 已有人工任务会复用；内部通知产生的 Webhook 不会把本地人工状态重新改为 AI 接待。

兜底依赖本地已观察到的消息和控制。离线恢复时可能仍有人工已处理但尚未同步的情况，所以任务说明要求顾问先检查，再跟进。

## 健康检查

| 接口 | 用途 |
|---|---|
| `GET /v1/health` | API 与数据库存活检查，适合 liveness |
| `GET /v1/health/ready` | 公开精简 readiness，异常返回 HTTP 503，不泄露业务详情 |
| `GET /v1/health/details` | 登录后查看各进程心跳、队列数量、最老等待时间及失败原因 |

正式模式检查 `live-reply-worker`、`live-maintenance-worker`；启用 Relay 时还检查 `live-relay-worker` 的成功轮询心跳。演练进程的心跳不能替代正式进程。

默认心跳过期阈值为 120 秒，可用 `WORKER_STALE_SECONDS` 调整。队列等待达到 300 秒、死信事件、失败或结果不确定的通知会使状态降级。正常停发会显示 `customer_sending_paused=true`，不单独作为进程故障。

`reactive_live_configured` 表示配置和客户发送开关允许接待；`reactive_live_enabled` 还要求健康条件通过。降级状态不会自动终止进程。不要把 readiness 503 当作无限重启进程的依据。

## 发布与回滚

1. 先在待发布副本运行测试并构建前端，核对改动清单与文件摘要。
2. 使用同一版本的完整 `backend/app` 和 `frontend/dist`。新增模块包括 `chatwoot_service.py`、`conversation_mirror.py`、`notification_dispatch.py`、`runtime_health.py`；不能继续只复制旧入口文件。
3. 发布前保存现有源码/构建产物与数据库的可恢复备份。停下旧正式进程，等待正在发送的任务退出，再替换代码和重启；不要让两个版本同时消费同一库。
4. 本次无表结构变更。保留既有 `.env`、连接密钥、接待白名单、资料批准与模型版本约束；新增并发设置可先用 `1`，验证后再设为 `2`。
5. 检查 readiness、内部通知设置，再用已授权测试会话验收转人工通知和人工接管后零自动发送。设备提醒须由实际手机确认。
6. 回滚时恢复整个旧版本并重启旧入口；`submission_unknown` 不应因回滚而重置或重发。
