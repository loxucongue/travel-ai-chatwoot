# V2 业务闭环开发与验收方案

日期：2026-09-20。依据：同日架构业务复核、原始 V2 共存方案、AI.docx、AI(1).docx、AI(2).docx。本文是下一轮开发与测试的执行依据，不代表整改已经完成。

目标：完成现有 V2 未达标项，使新客接待、单点追问、线路切换、资料交付、留资交接及沉默跟进在同一套状态与交付记录上闭环。保留现有发送保护、任务租约、幂等、素材回执和 V1 流程；重点修改 V2 及必要的共享边界，不做无边界重写。

“全部达标”指冻结版本在已列明的业务要求和扩展验收集中全部满足通过条件，不表示可以证明未来任何输入都不会出错。缺少批准附件、事实来源或真实渠道证据时必须列为未完成，不能以降级处理成功冒充原要求完成。

**执行边界与业务解释**

- 开发测试使用隔离数据库、模拟渠道、虚拟时钟；真实模型测试仅允许访问指定模型服务，阻断客户消息、真实交接通知和生产写入。继续遵守不向真实客户发测试消息的要求。
- AI(2) 优先覆盖冲突项：行程图先于风景照片；普通首次沉默评估约60秒。其他旧要求继续保留。
- 区分“完整介绍”和“单点问题”：客户要求完整资料时组织品牌、行程、酒店、车辆和适当互动；问集合、费用或年龄时只解决该问题，不强制重走介绍流程。
- 公司4–10人定位与特定6人报价、车型容量分别建模；不能混成一条通用人数规则。
- 已确认的业务报名条件按其适用对象表达；不扩写为必然审批通过、不会高反或其他无依据保证。宗教景点描述文化特色，不保证祈愿效果。
- 不删除渠道窗口保护来实现隔日唤醒。客户约定的联系时间无法自动发送时，生成可追踪人工待办或明确结束自动任务，不能提前打扰或显示自动发送成功。

**目标执行链路**

客户消息/到期事件 → 读取有证据的客户事实与历史交付 → 主 Agent 语义理解并按需调用 Skills/事实/素材工具 → 输出完整的本轮事件和回复计划 → 服务端验证状态事件与交付义务 → 核验事实和业务约束 → 持久化有序交付计划 → 模拟或受控执行器执行 → 回执更新已提供内容与下一步任务。

语义判断由模型结合上下文完成；服务端负责权限、证据、时间、事实范围及动作一致性。关键词可辅助检索，不能作为唯一的业务场景入口。默认不额外增加一条固定的“理解模型”串行调用；在主 Agent 的结构化结果中表达本轮理解，只有缺失、歧义或矛盾时才限次修复。

**阶段0：先建立完整需求账本和可重复基线**

工作：重新核对三份原文及全部截图、产品批准数据、旧复核未解决项；每条原子要求分配编号，记录来源位置、适用线路/客户、冲突处理、现状、修改位置、测试编号和证据文件。完整介绍、后续问答、主动跟进分开记录。

先将当前已发现的错误做成失败用例：问集合被标考虑、第二唤醒越窗、最后节点defer丢失、后台配置不生效、漏报行程意图、价格优惠漏检、已答内容重复、自然问法无候选。保留失败基线，不靠放松断言消除失败。

交付：需求账本、覆盖矩阵、当前失败证据、隔离测试环境。后续每一阶段都维护同一份账本，不再另起“通过若干项”的独立结论。

**阶段1：状态与记忆闭环**

主要位置：reception_v2/runtime.py、journey_state_machine.py、journey_memory.py、decision_contract.py、decision_service.py，以及必要的模型/迁移和交付提交入口。

1. 将客户事实、本轮话题、联系偏好、待办义务拆开表示。单一 journey_stage 仅作为兼容展示/投影，不承担所有决策依据。例如“需要考虑”不能抹掉选定线路，“明确拒绝主动联系”不能因换线路自动清除。
2. 主 Agent 必须输出事件列表，含来源消息标识、原文证据、适用线路及事件类型：选择/比较线路、提出问题、请求材料、讨论考虑、约定联系、拒绝主动联系、提供联系方式、要求人工等。缺失与空事件列表不能等同；缺字段或事件与动作冲突进入修复/保守处理。
3. 服务端按事件与前置条件更新状态。问集合、问价格不得仅凭模型阶段标签进入考虑；比较两条线路不得直接改绑定；留资成功必须基于有效联系方式；人工处理中必须有真实持久化交接任务。
4. 问题记录包含已回答部分、未知部分、答案引用、交付状态。用“答案已提供”与“客户明确确认解决”区分不同证据强度；不能把模型自认为回答完当成客户已认可。
5. 客户原话事实可在验证后持久化；“资料已交付、解释已提供”只能由相应交付回执提交。生成失败、发送失败、结果未知都不得提前标完成。
6. V2状态独立版本化存储，优先复用已有客户事实与交付表，不复制整套会话。迁移旧会话时只导入可信事实、交付、拒绝及人工状态；不确定进度暂停主动推进，保留正常回答能力。
7. V2回退V1只投影已验证事实、线路和交付记录；保留拒绝与人工状态，不直接把V2推断阶段传给V1。检查切换中迟到结果不能写回。

通过条件：状态关键用例全部通过；单点问答不会无证据进入考虑/留资/人工终态；多轮补充、更正、否定和改线均保留正确事实；失败发送不产生虚假的完成记录。

**阶段2：沉默与约定联系调度**

主要位置：proactive_policy.py、journey_memory.py、reception_config.py、live_sop.py、automation_service.py、相关任务模型。提取共用的纯计划函数，线上与演练保留各自执行器，避免再复制两套时间语义。

1. 区分普通沉默、考虑中、约定联系、等待人工核实、明确拒绝。普通首次在本轮最后一项成功交付后约60秒评估，客户新消息立即使旧周期失效；配置界面明确该计时基点，60秒到期不承诺60秒收件。
2. 首期V2建议默认普通间隔为[1,120]分钟，第二项从上一次成功跟进计算；每天最多2次、连续2次无回应结束本轮。此默认替换不可执行的[1,1440]，仅经本方案隔离验收后才进入发布配置；不是延长或放宽渠道窗口。
3. 无明确时间的“先考虑/与家人讨论”不进入分钟级跟进，保留原方案至少24小时后复评原则；若届时渠道不可用则结束自动周期并记录原因，不偷偷压缩等待时间。只有有明确后续事项时建立人工待办，避免无意义任务堆积。
4. 有约定时间时存储绝对时间、时区、来源原话及解析依据。只给模糊时间且会影响执行时做一次必要澄清。时间未到不联系；到期超出可发送条件则记录人工处理需求，不能声称已自动安排发送。
5. defer 重新安排当前待办评估，不增加成功触达次数，不消耗后继节点。限制最大复评次数与存活期，避免无限延后。stop 结束本轮任务；明确拒绝另行持久化，并限制相关渠道主动联系。
6. 候选来自已批准事实/素材和实际已提供内容，并参考未回答问题及客户关注点；不因词面未命中就直接拒绝模型评估。沉默时不能凭空新增客户偏好。候选为空则停止，不能为凑次数编造内容。
7. 每次生成前及交付前检查最新消息、版本、人工状态、联系时段、频次、渠道窗口和已交付记录。配置发布时提示无法执行的时间计划；运行时再次计算可执行性。

通过条件：虚拟时间验证首次、第二次、跨日、时区、约定时间、窗口边界、最后节点defer、连续defer、新消息、人工接管和明确拒绝；无越窗发送、无静默丢任务、无重复触达计数。模拟客户已收到的事实不再作为新价值重复营销。

**阶段3：事实、Skills与运营配置统一**

主要位置：有效route-packages、decision_knowledge.py、reception_v2/tools.py、route_profiles.py、skill_registry.py、各Skill、reception_policy_views.py、AiReceptionStrategy.tsx。

1. 明确有效产品数据来源和覆盖优先级；每条事实含来源、版本、对象、条件、例外及未知项。不同版本冲突不能静默混用。
2. 补齐价格“起”、报价人数、团期、包含不含、多人优惠存在但未知金额；按线路补齐酒店地区例外、希尔顿/绒布顺序、独立卫浴和供氧、2025车辆/VIP/制氧；加入文化跟进内容、铁路出藏、林芝集合/成都交函、年龄条件及小费限制。
3. 主题检索返回回答所需的主事实和必要限定。例如价格必须拿到适用条件及优惠事实，但客户只问价格时不必机械列完团期和全部行程。多问题输入允许多个主题，不能只取第一个关键词。
4. 新增线路由注册表读取产品能力和Skill元数据，移除主流程中的两线路硬编码；工具枚举与候选从注册表生成。用第三条测试线路验证不修改核心运行逻辑即可接入，不作为真实销售产品发布。
5. 主提示词保留通用原则；产品边界和表达组织放入线路Skill；考虑、留资、停止等通用行为统一维护。Skill只指导行为，价格和实时信息仍来自事实工具。
6. 定义V2支持的运营配置：开场、语气、自定义指导、长度、素材上限、路由、留资、沉默间隔/时段/频次。接入对应执行链路；界面标明适用引擎和发布版本，不支持项不能伪装生效。运营指导不能覆盖已批准事实及发送保护。
7. 发布包锁定代码、Skill、产品数据、模型标识/参数与配置摘要。已绑定会话按明确迁移策略使用版本；发送禁用等紧急保护始终实时读取。模型供应商不可固定的隐含变化记录为复现限制。

通过条件：每个配置具有“修改前后行为确实不同”的测试；报价、酒店等工具事实完备；事实更新、快照、缓存和回滚不串版本；第三线路测试通过；V1现有场景回归无意外变化。必要的共享事实纠错单独列明对V1的影响。

**阶段4：资料交付与人工交接闭环**

主要位置：runtime.py、decision_contract.py、delivery_plan.py、route_reply.py、live_reply.py、material_library.py、lead_capture.py及沙盒执行器。

1. 将请求行程/重发/完整介绍形成独立交付义务。最终回复的可选delivery_intent不能作为唯一依据；义务必须对应计划项、可信历史交付或明确的人工处理任务。主Agent漏字段、声称有附件但计划为空、只写介绍未处理请求，都要被校验阻断并限次修复。
2. 建立完整介绍计划：简短品牌定位→对应线路行程图→精简卖点→相关酒店图文→车辆图文→一个有必要的互动问题。风景照片在行程图之后；11日绒布排在希尔顿后。每项保持1–2秒配置间隔并可被新消息打断，不在单点追问中执行整个计划。
3. 完整介绍按多个受控交付项组织，不通过放宽单条回复长度或图片上限倾倒全部内容。客户已提供人数/日期时，结尾问题不能重复索取已知信息。
4. 客户明确未收到/要求重发才允许重发；切线路选择新线路资料。送达未知先核对，不盲目重发；部分失败只恢复未完成项。客户打断后先解决新问题，再判断是否需要继续旧资料，不自动恢复过期内容。
5. 高反注意事项先查找已批准且可交付的现有附件。存在则接入留资后交付；不存在则制作待审资料草案及对应任务，但不得把草案冒充已批准附件或自行宣告该业务项通过。
6. 人工交接包含已知客户事实、待核实问题、资料交付状态及来源。任务创建、模拟通知、认领、状态更新、停止AI营销都要测试。未知特殊安排必须有任务，不能只回复“我帮您确认”。

通过条件：两条线路完整介绍、单点无多余素材、漏字段、重发、切线、失败/未知送达、打断恢复全部通过；交接可追踪。缺少批准附件时该项持续标记阻塞，不能用“已转人工”替代“已提供附件”验收。

**阶段5：速度优化与失败处理**

在效果基线通过后优化，避免把取消核验当提速。收集理解/工具、生成、核验、重写和排队耗时；预载已绑定线路需要的少量资料，消除重复取数，同版本只读结果合理缓存，独立查询可合并或并行。无产品承诺的确定性简短承接可走经过测试的快捷路径。

设总回合预算并向各调用传递剩余时间，取消迟到结果；超时不得写入已回答/已交付状态。限次修复失败后给出有据的简短失败承接或建立人工待办，不自动切到V1再发送一份答案。

本计划性能验收目标：固定模型/配置与可比负载，至少100次普通问答采样，最终可交付答案P50≤8秒、P95≤15秒；复杂跨线路/重写场景单列统计，目标P95≤30秒，总回合预算30秒。超时与失败计入整体失败率，不能从统计中删除以美化速度；统计冷/热缓存及排队时间。多图实际完成时间另计，不能与首条可交付回复混算。上述是待验证目标，不是当前能力承诺；未达到则性能项未通过。

同一问题集与输入快照对照V1/V2，分别记录正确性、完整性、耗时、调用量和费用。保持必要事实核验，不向渠道流式发送未经核验的半成品。

**阶段6：统一验收与修复循环**

测试资产覆盖所有需求编号，最低规模用于防止再次只测少数原句，不替代逐项覆盖：至少80个单轮/边界场景、20条多轮旅程、10类执行故障/竞争场景。必要时按需求增加，不为凑数量复制同类问题。

| 测试层 | 方法 | 必须检查的结果 |
|---|---|---|
| 确定性规则 | 单元/属性及边界测试 | 事件证据、状态转换、时间、版本、交付义务、去重、不确定送达 |
| 执行闭环 | 隔离数据库+实际worker+模拟渠道+虚拟时钟 | 实际持久化、消息顺序、回执、任务延后、取消、人工交接；不手动把计划直接标为收到 |
| 真实模型 | 原反馈原句及复述、省略、否定、多问题、繁简表达 | 回复事实与限定、相关性、状态、素材、下一步一致；记录所有失败 |
| 多轮业务 | 同一新客跨阶段连续执行 | 不丢上下文、不重复问、改线、不误停、按约定跟进、正确交接 |
| 运营与兼容 | 配置发布、重启、V1/V2切换及回滚 | 配置实际生效，旧任务失效，V1不被V2推断状态污染 |
| 性能 | 同一冻结版本固定问题集 | 最终答案延迟、失败率、调用量及费用，不以首字代替最终可用答案 |

关键路径每个真实模型场景至少5次；其他模型场景至少3次。固定验收集与预先保留的扩展集分开，改写样本在评测前登记，不能看完输出再降低预期。关键失败立即加入回归；修复后重新跑受影响集合，最终冻结版本完整跑一次验收并保留所有重复结果，不拼接不同版本各自最好的一次。

所有硬性业务要求在规定验收集中必须通过，任何状态、事实、隐私/拒绝、素材或交接关键失败都阻止通过。自然表达按“直接回答、信息恰当、台湾表达、无重复催问、下一步自然”五项记录原文评审，每项至少4/5；明确禁词等用确定性检查，不能全由生成模型给自己打分。评分只补充硬条件，不能以高平均分抵消某个业务缺陷。

验收脚本输出非零退出码表示失败；每个问题保留输入、完整历史、配置、计划、回执、输出、评分、错误与版本。核验状态采用必需/通过/失败/不适用，事实回复必须通过；确定性承接等可说明不适用，不能把空值统一算通过。

代表性连续旅程必须覆盖：新客询问→9/11日选择或比较→索要行程→报价及优惠→酒店/高反→日期未定→提供人数→切线→讨论考虑→约定联系→到期→客户回复→留联系方式→人工核实。另分支覆盖不留联系方式、拒绝联系、资料未收到、附件缺失、多人报价、年龄64/65/75/76、不同证件、天气、小费、纳木错、微信非付款、无随团医生及客户打断。

**完成、发布与外部依赖**

每阶段结束提交实现说明、通过/失败用例和需求账本状态；没有必要每阶段再请用户批准例行实现。下一轮开发按0→1→2→3→4→5→6连续推进，修复和测试穿插，最后统一验收。

完成代码和隔离测试不等于生产验证完成。发布前生成候选版本、迁移检查、回滚说明、配置差异、批准素材清单及逐项证据；确认本地候选与待部署版本一致。当前方案不把生产自动发送或真实通知当成测试手段，也不自动打开发送开关。真实渠道收件和真人认领如未实际验证，单列为未验证，不写成全量上线通过。

外部依赖需尽早排查：批准的高反附件及其他缺失事实、模型服务可用性、独立测试渠道/账号。能从已有资料恢复的自行恢复；需业务批准或真实系统配合的列出具体缺口与已准备好的材料，同时继续其余独立工作。不得伪造批准或用修改验收标准绕过阻塞。

最终交付给用户的是一张逐项结果表：业务原问题→根因→实际改造→本次输出示例→扩展场景→测试证据→是否达标/剩余依赖；另附性能对照、架构变化、V1兼容结论和发布状态。不能只交测试总数或“已优化完成”。
