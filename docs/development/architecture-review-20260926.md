# 架构审查与评价（2026-09-26）

## 结论

项目已经具备较完整的旅游 AI 接待业务能力，发送安全和业务回归投入较多；但后台任务调度、通知闭环、运行健康判断和模块边界尚未达到同样的成熟度。适合继续建设为单公司使用的模块化单体，不能仅凭现有测试数量就认定已经具备稳定的大规模广告接待能力。

当前只有一个顾问，不代表只会有一个客户同时咨询。首先需要解决的是多客户排队和无人知晓的异常，而不是引入微服务或更复杂的 Agent 框架。

## 范围与证据

- 审查本地 FastAPI 后端、React 前端、Cloudflare 中继、数据模型、主要 Worker、V1/V2 决策与交付链路、权限和发布约定。
- 对 Chatwoot 作为外部系统的调用边界进行审查，未审计整个上游 Chatwoot 源码和第三方依赖。
- 未连接生产服务器核对部署文件，不能把本地代码判断等同于生产配置证明。
- 本次未修改业务代码、通知配置或正式服务，也未发送客户消息。
- 统计：backend/app 下 99 个 Python 文件、29,049 行；frontend/src 下 30 个 TS/TSX 文件、4,202 行（不含 CSS）；backend/tests 下 93 个 Python 文件、22,955 行；四个业务模型文件合计声明 55 张表。数量用于说明维护规模，不代表质量评分或测试覆盖率。

## 实际架构

核心链路：Chatwoot Cloud 接收客户消息 → Cloudflare Worker/D1 暂存 Webhook → 本地或部署主机上的进程拉取 → SQLite 消息镜像与任务 → AI 决策 → 发送前检查 → Chatwoot API → 渠道回执。

| 模块 | 职责 | 评价 |
|---|---|---|
| Chatwoot Cloud | 渠道授权、消息收发、会话、顾问工作台和手机端 | 合理复用成熟系统，不必自己再造聊天客户端 |
| cloudflare-relay | 接收事件、持久化、租约、确认、重试、清理 | 避免接待主机必须开放公网入站，具备事件缓冲能力 |
| FastAPI | 登录权限、配置、会话控制、资料、演练和运营接口 | 技术选型合适，路由层业务职责过重 |
| live_reply_worker | 正式消息观察、回复生成、发送、主动跟进及回执补查 | 单实例执行简化了一致性，但任务之间互相阻塞 |
| evaluation_worker / playground_worker | 回放、演练、模拟旅程 | 与客户发送隔离方向正确，但应明确任务归属 |
| V1/V2 决策 | 理解需求、工具/事实选择、生成、审核、决策协议 | V2 以当前问题为中心合理；仍共享大量旧协议及业务规则 |
| SQLite / SQLAlchemy | 会话镜像、业务状态、任务、出站账本、审核记录 | 对当前规模可以继续用；进程扩容前应重看任务认领和锁 |
| React | 业务操作、配置、演练、交接和统计 | 使用查询缓存与页面拆包；用户流程自动化测试偏少 |

这是“单体业务应用 + 多个进程 + 外部服务”的结构，不是微服务，也不需要为了架构名称进行重写。

## 做得较好的部分

1. **模型生成与实际执行有边界。** 决策先形成结构化结果，资料、会话状态、授权范围和发送由程序检查，未把模型文本直接当成可执行承诺。
2. **重视发送结果的不确定性。** 出站记录先保存，发送异常进入 submission_unknown，避免超时后盲目重发。回执有单向推进和失败暂停处理。参见 [live_reply.py](../../backend/app/live_reply.py#L476)、[delivery_status.py](../../backend/app/delivery_status.py#L23)。
3. **演练和正式执行有隔离。** 独立任务、环境标记、只读 Chatwoot 客户端、运行模式检查和全局停发控制，降低误发风险。演练成功仍不能替代正式渠道验收。
4. **多轮接待有事实和交付依据。** 已有客户原话证据、线路快照、素材批准和哈希、实际交付记录、版本切换检查，能减少改线与换资料后的状态混乱。
5. **权限基础有实质实现。** 密码哈希、会话摘要、HttpOnly Cookie、CSRF、后端角色和 Inbox 范围检查、审计均有代码。前端更换身份时隔离查询缓存也有针对性测试。未因此宣称通过完整安全审计。

## 主要发现与优先级

### P1：正式模式没有执行通知投递和人工任务超时检查

证据：

- [operations.py:55](../../backend/app/operations.py#L55) 创建本地通知，并可排入 NotificationDelivery；[operations.py:66](../../backend/app/operations.py#L66) 创建人工任务并暂停 AI。
- process_notification_delivery 和 process_handoff_overdue 仅由 [worker_main.py:711](../../backend/app/worker_main.py#L711) 的旧进程主循环调用。
- 同一旧进程在 live_reply 模式下直接拒绝启动，见 [worker_main.py:681](../../backend/app/worker_main.py#L681)。
- [live_reply_worker.py](../../backend/app/live_reply_worker.py) 的正式循环没有调用这两个消费者。

影响：使用项目正式回复模式时，转人工任务可以落库，但配置好的外部通知可能无人消费，超时升级也不会由该正式进程产生。若没有额外部署代码之外的消费者，这条链路不闭合。

9 月 26 日单次接口测试证明了机器人私有备注 + @顾问能产生 Chatwoot 通知，但这是独立测试脚本，不是 ensure_handoff 已自动接通的证据；手机实收仍需用户确认。

建议：把人工任务分配、Chatwoot 内部提醒、外部投递和超时升级纳入明确的运营任务消费者。对当前单顾问，明确固定负责人即可，不必先做复杂排班。使用独立机器人身份，避免顾问账号自己 @自己。内部提醒和客户公开发送应有各自明确的权限及开关。

### P1：单个客户的慢处理会阻塞其他会话，五分钟门槛缺少补偿闭环

证据：

- [live_reply_worker.py:101](../../backend/app/live_reply_worker.py#L101) 每轮取一个任务，随后同步执行 process_job；在其返回前，主循环不会继续拉取中继事件。
- [live_reply.py:846](../../backend/app/live_reply.py#L846) 多段资料通过同步等待实现间隔，仍占用同一执行进程。
- [reception_v2/budget.py:24](../../backend/app/reception_v2/budget.py#L24) 为一次模型处理设置 30 秒预算。这是模型预算，不是整个任务总耗时，也不意味着每个任务实际耗时 30 秒。
- [live_reply.py:93](../../backend/app/live_reply.py#L93) 定义五分钟新鲜度；mirror_event 和 guard 都检查新鲜度。过期消息会保留镜像，但不会正常进入或继续原自动回复任务，相关路径未自动创建“消息过期未接待”的人工待办。

影响：广告同时带来多个客户时，前面的慢模型、网络与多段发送会拉长后续排队。停机恢复或积压超过门槛后，部分消息可能只被归档而没有自动接待或专门的漏接提醒。这里没有做压测，不能给出最大容量数字。

建议：将收事件与模型执行分离；同一会话保持串行，不同会话采用有限并发；资料间隔改为到期任务调度；过期事件转人工待办而不是重新自动补发。不能直接启动多个现有 live_reply_worker：当前依赖进程文件锁，任务认领机制也需一起调整。

### P1：健康检查不能可靠反映正式接待进程是否正常

证据：[api.py:922](../../backend/app/api.py#L922) 取所有 Worker 中最新的一条心跳，不指定 live-reply-worker，也不判断过期；reactive_live_enabled 仅依据运行配置计算。

隔离复现：正式进程心跳设为两小时前、演练进程心跳设为当前；在内存中设定正式模式后，接口仍返回 status=ok、worker_type=playground-worker、reactive_live_enabled=true。仅使用隔离内存数据库，没有启动正式进程或网络调用。证据见 [health.json](../../output/architecture-review-20260926-health.json)。

建议：区分 API 存活与业务就绪；分别展示接收、回复、通知、演练进程心跳及过期状态。至少加入最老待处理任务年龄、死信数量和通知失败数。不能用一个总绿色状态代替全部接待能力。

### P2：模块边界与文件职责需要收拢

- automation_api.py 2,208 行，automation_service.py 1,671 行，live_reply.py 1,347 行，V2 runtime.py 1,153 行。
- live_reply.process_job 为 441 行，process_automation_run 为 389 行，run_v2_agent 为 376 行。
- live_reply、live_sop、worker_main 均从 app.api 导入公共辅助函数，后台执行依赖 HTTP 路由层。
- V2 和通用 model_gateway 从 deepseek_evaluation 导入生产协议及底层模型调用；“演练”模块事实上承担基础设施职责。

影响：修改一次接口、协议或业务策略需要检查多个执行入口，单个函数难以独立验证，文件名也无法可靠解释依赖方向。

建议：渐进提取 Chatwoot 网关、模型传输和决策协议、会话控制、交付执行、人工交接。路由和进程入口只负责输入与编排；先消除执行层向 API 层的反向依赖，再处理长函数。不要只把一个长文件切成多个互相依赖的短文件。

### P2：业务规则已外置一部分，但通用引擎仍包含大量具体产品纠正规则

V2 已有线路 Skill、路线数据和服务事实，这是可扩展的基础；但 [runtime.py:91](../../backend/app/reception_v2/runtime.py#L91) 的 SYSTEM_PROMPT 及追加段仍写有台湾年龄证明、成都交函、具体报价语气等产品规则，reply_scope、task_scope 等审核节点也包含具体场景解释。

影响：新增线路或调整政策时，只改一份线路 JSON 或 Skill 不一定够。生成器与审核器的旧规则可能不一致；频繁追加纠正规则还会增加提示长度和理解冲突。

建议：区分通用执行规则、旅行社政策、线路事实和表达风格。价格与资格条件只从已批准事实读取，生成和审核使用同一政策版本。保留现有反例作为行为回归，不把每次失败都变成主提示词永久新增的一段。

### P2：测试投入很多，但正式业务闭环与环境可复现性仍有缺口

- 后端有大量业务和故障回归，值得保留；不能根据测试行数推断覆盖率。
- frontend 的 npm test 当前只运行一个查询缓存隔离测试，不能代表配置、开关、转人工等页面流程已自动覆盖。
- 本次全量后端回归执行到约 34% 后停止，未完成，不能报告全量通过。
- 其中失败已单独复现：测试要求 ADVISOR_VOICE_VERSION=v14，源码已经为 v15，见 [test_advisor_voice_assets.py:118](../../backend/tests/test_advisor_voice_assets.py#L118) 和 [advisor_voice.py:22](../../backend/app/advisor_voice.py#L22)。这是测试版本断言过时，不等于已证明客户话术错误。
- 测试首次启动在 conftest fixture 运行之前就被本地 live_sop 配置阻断；必须在启动 pytest 之前显式设置安全环境。当前 fixture 的安全设置时点不足以完全隔离导入时配置。

建议：提供不依赖开发机 .env 的统一测试入口；把版本号断言与行为断言分开；补上真实执行模式下的任务调度、通知消费和业务就绪测试。关键页面保留少量端到端回归。渠道和手机实测是另一层验收，不应伪装成单元测试已覆盖。

### P2：发布与启动约定仍偏人工化

- 当前工作目录没有 Git 元数据，发布文档也明确依赖文件摘要与覆盖包。
- 已有备份、回滚、素材哈希和代码指纹机制，不能说完全没有版本管理。
- Python 依赖大多使用版本区间，未找到独立锁定文件；前端与中继有 package-lock.json。
- README 的默认入口仍强调离线模式和历史 Tunnel，而后来文档描述 Relay、正式回复模式和服务器部署；启动命令、当前有效模式与任务消费者需要一个权威说明。

建议：把代码、依赖锁、迁移、配置模板、知识及素材清单组成可重建发布物。建立可追踪的版本库并先排除凭据、真实数据库、日志、客户资料和构建产物。保留现有哈希机制用于发布验证。

## 当前适用边界

数据库存在 Tenant，不等于已经实现多租户 SaaS。User 没有直接租户归属，部分连接与配置通过首条记录或全局键获取，例如 api.get_connection 和 operations.setting_value。对于当前单公司部署，这可以接受；如果以后同时服务多个旅游公司，必须重新设计并验证租户隔离，不能只增加一个 tenant_id 参数。

SQLite 目前不是首要问题。现有 WAL、短事务、网络调用前提交以及单实例执行约束适合低到中等负载试运行。是否迁移数据库，应由并发写入、任务延迟、可用性和备份恢复要求决定；不能用换数据库替代任务调度修复。

没有证据支持现在立即引入微服务、Kubernetes、复杂消息平台或全新 Agent 框架。V1 保留作回退有价值，但应有冻结范围和退出条件，避免长期双向增加功能。

## 建议实施顺序与验收标准

1. **补齐接待闭环。** 转人工时有明确负责人、交接摘要、内部通知及失败状态；过期未接待消息进入人工待办；通知消费者在正式模式下运行。
2. **建立可信运行状态。** 停止正式进程时，健康接口能明确报出回复能力不可用；演练心跳不能掩盖它。展示队列年龄和失败原因。
3. **分开观察与执行。** 慢模型期间仍能及时接收新消息和控制事件；同会话不并发发送，多会话不会无限串行阻塞。以模拟慢模型和多会话测试验证，再做受控压测。
4. **整理模块与业务规则。** 先提取公共网关和协议，再统一执行接口；逐步收拢政策及事实来源。优先保持现有行为，不大规模重写。
5. **固定发布和回归入口。** 干净环境可重复安装、迁移、运行关键回归；消除过时测试并建立受控渠道验收记录。
