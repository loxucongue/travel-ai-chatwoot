## 结论

系统已具备较完整的 AI 接待与演练基础，但当前不宜将“测试通过”等同于“具备生产放量条件”。本次确认 9 项缺陷：3 项 P1、5 项 P2、1 项 P3，集中在身份切换、权限隔离、人工接管并发和迁移一致性。建议先修复 P1，再完成 P2 回归，随后评估扩大真实接待范围。

这不是对整个 Chatwoot 上游源码和全部业务规则逐行审计后的安全认证。审查覆盖自研后端的身份认证、运营 API、消息与任务链路、模型规划与事实核验、知识抓取边界、迁移，以及前端认证/缓存、Cloudflare 中继。Chatwoot 目录仅检查开发约定和集成背景，未运行其 Rails/Vue 测试，也无法在无 Git 历史的情况下识别所有本地定制。

## 已确认的问题

### 1. [P1] 通知接口绕过 Inbox 数据权限

位置：[ops_api.py:1044](../../backend/app/ops_api.py#L1044)、[operations.py:59](../../backend/app/operations.py#L59)。

`ensure_handoff` 创建的通知通过 `create_notification` 保存为 `user_id=None`，正文包含接管理由。通知列表仅判断 user_id 是否为空或等于当前用户，没有按关联会话的 Inbox 授权过滤。标记已读接口也没有这层过滤。

复现：给一个无任何 Inbox 授权的 agent 登录；受限会话详情返回 404，但 `/v1/notifications` 返回 200，并包含该会话的 `RESTRICTED_CUSTOMER_DETAIL`。

影响：会话接口本身的权限正确，仍无法阻止客户上下文经通知旁路泄漏。接管理由若包含联系方式或客户诉求，也会被带出。

建议：通知明确关联本地会话主键，列表与读写操作复用会话权限过滤；非会话系统通知另外定义受众。验收应同时覆盖“看不到会话”和“看不到其通知”。

### 2. [P1] 重置密码后旧登录会话仍然有效

位置：[ops_api.py:282](../../backend/app/ops_api.py#L282)、[api.py:200](../../backend/app/api.py#L200)、[auth.py:14](../../backend/app/auth.py#L14)。

管理员重置密码只更新密码哈希和 `must_change_password`。认证依赖只检查会话是否被撤销、过期以及用户是否启用。重置过程没有撤销该用户已有的 AppSession。自主改密也没有撤销其他会话。

复现：agent 先登录，管理员重置该 agent 密码；旧客户端再次访问 `/v1/auth/me` 仍返回 200。

影响：管理员用改密处理账号失陷时，持有旧 Cookie 的访问者仍可使用原会话，直到过期或账号被停用。

建议：管理员重置密码与撤销该用户所有会话放在同一事务；自主改密至少撤销其他会话，并明确当前会话是否轮换。

### 3. [P1] 切换账号保留前一账号的前端数据缓存

位置：[auth.tsx:46](../../frontend/src/auth.tsx#L46)、[main.tsx:9](../../frontend/src/main.tsx#L9)、[Conversations.tsx:129](../../frontend/src/pages/Conversations.tsx#L129)。

QueryClient 在应用根部长期存在。退出仅清除用户状态与 CSRF Token，没有清理查询缓存；会话等查询键没有用户身份。同一页面退出管理员再登录受限账号时，组件会复用相同键对应的旧数据。

复现：按项目实际键与 `staleTime=5000` 设置管理员会话缓存，再创建新 QueryObserver，立即得到前一用户的受限会话数据，且 `isStale=false`。这验证了缓存机制；未执行浏览器完整登录流程。

影响：共享浏览器或轮班电脑切换账号后可能展示上一账号客户数据；后端拒绝后续请求不能撤回已经显示的数据。

建议：身份切换时取消在途查询并清空身份相关缓存，查询键加入用户身份；验证登出期间在途响应不能重新填入旧数据。

### 4. [P2] 首次强制改密只由前端执行

位置：[auth.py:14](../../backend/app/auth.py#L14)、[App.tsx:39](../../frontend/src/App.tsx#L39)。

前端通过 `must_change_password` 显示改密页，后端认证依赖没有阻止此状态的用户调用业务 API。

复现：使用管理员重置后的临时密码登录，`must_change_password=true`；未改密直接请求 `/v1/notifications` 仍返回 200。

影响：用户可以长期绕过“临时密码仅用于首次改密”的预期。该问题与旧会话未撤销是两个独立缺陷。

建议：后端将此状态限制在读取本人身份、获取 CSRF、改密、退出等必要接口，其他业务接口返回明确错误。

### 5. [P2] 人工接管版本检查不能防止并发覆盖

位置：[ops_api.py:449](../../backend/app/ops_api.py#L449)。

`claim_for` 对内存对象比较 version，随后调用远端分配，再无条件提交本地更新。没有以旧版本为条件执行原子更新，也没有预占状态或互斥机制。

复现：两个 Session 都先读取 version=1。第一个领取成功后，第二个仍持有旧对象，也使用 expected_version=1 领取成功；两次响应 version 均为 2，mock 记录两次分配 `[101, 102]`。

影响：两名坐席都可能认为领取成功；最后提交者覆盖前者，并可能造成远程与本地负责人不一致。

建议：在外部调用前通过条件更新预占操作，冲突返回 409；外部调用完成后进行状态确认，并明确失败补偿。仅把远程调用放在普通事务里不能解决这个问题。

### 6. [P2] 迁移缺失客服绑定唯一约束，测试建表掩盖差异

位置：[a12f0c9d7e31_operations_platform.py:18](../../backend/alembic/versions/a12f0c9d7e31_operations_platform.py#L18)、[models.py:63](../../backend/app/models.py#L63)、[conftest.py:25](../../backend/tests/conftest.py#L25)。

模型声明 `User.chatwoot_agent_id` 唯一，但迁移仅添加普通列。正常安装使用迁移，单元测试使用 `Base.metadata.create_all`，得到的数据库约束不同。

复现：全新临时库 upgrade head 成功后，alembic check 报告需要添加唯一约束；直接插入两个相同 chatwoot_agent_id=777 的用户成功，计数为 2。

影响：实际数据库允许多个平台用户绑定同一 Chatwoot 客服，破坏身份映射约定；依赖 IntegrityError 返回冲突的代码无法按设计工作。

建议：新增迁移，先检测已有重复绑定再建立唯一约束；增加从空库迁移到 head 的一致性检查，保留部分基于真实迁移建库的集成测试。

### 7. [P2] 留资、成交统计未应用会话权限和 Inbox 筛选

位置：[ops_api.py:992](../../backend/app/ops_api.py#L992)。

overview 先按权限和指定 Inbox 筛选 conversations，但 lead_ids / conversion_ids 独立查询全表 LabelEvent，未限制到授权会话集合。

复现：无任何 Inbox 授权的 supervisor 获取 overview，返回 `conversations=0`、`leads=1`；这条留资记录属于无权访问的会话。

影响：泄露范围外汇总数据，并让指定 Inbox 的经营指标与漏斗口径失真。

建议：统计统一经过相同的授权范围和 Inbox 条件；另外明确会话活跃时间与转化发生时间的口径，避免简单修补后产生新的漏数。

### 8. [P2] 广播通知已读状态由所有用户共享

位置：[ops_api.py:1053](../../backend/app/ops_api.py#L1053)、[models.py:307](../../backend/app/models.py#L307)。

广播通知只有一条记录和一个 read_at，任何可访问用户标记已读都会修改同一字段。

复现：agent 标记广播通知已读后，管理员重新查询立即看到 read_at 已设置，尽管管理员尚未阅读。

影响：一名坐席的操作清除其他人的未读提示，降低人工接管提醒的可靠性。修复列表权限本身不会修复该状态模型。

建议：维护 notification_id + user_id 的阅读回执，或按收件人生成通知实例；“团队已处理”应与“本人已读”分开。

### 9. [P3] README 的测试命令无法收集完整测试集

位置：[README.md:82](../../README.md#L82)。

根目录执行文档命令时，4 个测试模块无法从 `scripts` 导入 backend/scripts 下的验收脚本。改从 backend 目录运行后，完整测试集通过。

影响：新环境按文档验收失败，也容易让自动化验证因启动目录不同产生不一致结果。

建议：先修正文档命令，后续把被测试脚本模块组织为明确的包；确保 CI 从约定入口运行。

## 架构评价

值得保留的设计：

- Chatwoot 负责渠道收发、自研平台负责决策和运营，责任边界清楚。
- 实发客户端有运行配置与数据库总开关；读取总开关失败时默认拒绝发送。
- live_reply 发送前重新检查远程会话、标签、人工介入和触发消息；发送前持久化 submission_unknown，避免把网络不确定性直接当成可安全重试。
- 模型理解、代码规划、话术生成、事实核验分层，关键动作并非完全依赖提示词自律。
- 演练有独立会话环境、任务版本检查及独立 Worker；知识版本和来源指纹有助于追踪验收对象。
- 已有相当规模的回归测试。本次发现更说明需要补足跨模块、权限负例、迁移及并发验证，而非单纯增加测试数量。

需要控制的工程风险，尚未归为本次已复现缺陷：

- 多套发送实现并存：legacy worker、live_reply、controlled_delivery。安全检查与异常语义容易随演进分叉；应明确唯一受支持的生产入口，再逐步收敛共享边界。
- live_reply_worker 串行完成模型调用；SOP 与回执处理放在无实时任务的分支。持续负载下可能延迟跟进与回执，需测队列等待时间、端到端延迟和饥饿情况。不能仅根据现有代码判断容量是否足够。
- automation_api / automation_service / live_reply 等文件承担多种职责，部分代码高度压缩。建议围绕权限查询、任务状态机、发送边界拆分，避免全局重写。
- API 中存在全量读取再在 Python 过滤、切片和逐条查询的模式，例如 handoffs。随着镜像历史增长，应做真实规模下的查询分析，再下推筛选与分页。
- 默认配置允许公开的开发密钥作为加密密钥来源，生产启动没有强制拒绝该配置。未检查真实密钥值，不能据此断言现有环境正在使用默认密钥；部署入口仍应增加校验。
- 网站抓取有 URL、IP、重定向与大小检查，但 DNS 校验结果未绑定实际连接。若开放给不可信编辑者，应进一步验证 DNS 重绑定与代理环境边界；本次没有进行网络攻击复现。
- 根目录没有 Git 元数据；后端依赖未发现锁文件；旧架构文档与近期运行方式存在演进差异。无法从此快照证明可复现发布与回滚能力已经建立。
- 单租户业务假设仍广泛存在，例如读取首个 Tenant、全局 AppSetting。若以后做 SaaS 多租户，应单独设计隔离边界，不能因模型有 tenant_id 就认定已支持多租户。

## 建议的处理顺序

1. 先处理通知越权、会话撤销、前端缓存隔离，加入不同角色与不同 Inbox 的负例验证。
2. 接着处理人工接管并发、迁移约束、强制改密、统计过滤与通知回执；每项补充此次触发条件对应的回归。
3. 固化从空库迁移、后端测试、前端构建、中继检查的统一验证入口，修正文档。
4. 在隔离环境验证模型超时、新消息打断、停发开关、进程崩溃、发送结果未知、持续队列负载，再据实决定真实接待放量范围。

本次交付仅为审查报告，未修改业务源码。构建与测试产生了常规本地输出。
