共同设计原则

  • 接待权限由频道开关、人工接管、加私訊、拒联等确定；客户意向标签只影响合格内容的选择，不能扩大AI接待权限。
  • 已确认事实限定可说和可发内容；AI负责理解客户和组织回复，最终日期、价格、图片适用范围仍由产品数据核对。
  • 在现有会话状态、素材库、分配和通知队列上增补，第一版不引入新的代理编排系统或另一套素材库。
  • 推荐、已接受、已拒绝和临时忙分开记录，并保留原消息；业务改口后更新，不能凭陈旧摘要继续追。
  • 第一版先改善跟进相关性与回应承接，保留现有每日限次、夜间顺延和七天截止；更积极不自动等于多发消息。
  • 标签和渠道回执是可观测记录；洗單回仅代表跟进后出现回应，不能证明因果或直接等同成交意向。

逐项开发与验收

L1 3—4月桃花优先与防止来回切线

涉及板块：AI接待策略/线路分流、会话偏好与推荐状态、团期核对、介绍发送队列

开发步骤

  • 将三月和四月归入同一春季推荐入口；先核对当前年份的已公布团期及客户硬限制。
  • 保存推荐线路、推荐中/已接受/已拒绝、日期或天数冲突、客户原消息；客户明确改变意愿才重开推荐。
  • 复用林芝候选中推荐与选线分开的机制，整理成适用于已启用产品的规则；切线时取消旧图文，保留人数和日期。

验收表现

  • 三月中先说明已公布桃花日期；固定3/15、4月底或只能8天不编造桃花团。
  • 已接受后问酒店/人数不会切回常规线；明确不要桃花后不反复推。
  • 想去珠峰可对应桃花+珠峰11日；不上珠峰不能兜底推含珠峰线。

先讨论清楚

  • 推荐后何时可以直接发完整行程，何时必须等明确确认？建议只有明确接受或广告已经选定才启动整套介绍。
  • 硬日期/天数优先于营销推荐；例外产品及未公布年份如何交顾问核对。
H01 林芝入藏、不上珠峰8日独立路线

涉及板块：独立线路包、线路识别/切换、报价与季节规则、介绍与跟进

开发步骤

  • 保留已开发线路包及18张素材，完成已准备的13个真实模型场景，不重新开发整条线路。
  • 担心高反仅记录顾虑；明确不要珠峰才推荐替代，明确接受才切线；换线后重新核价。
  • 先独立验收，再与L1做跨产品联测；冬季销售文字与价格口径未统一前保留顾问核对。

验收表现

  • 广告直入不误认成拉萨珠峰8日或桃花9日；问高反不自动改线。
  • 接受替代后旧图文停止，已知人数和月份保留，发送新线地图和对应价格。
  • 候选资料中的停售时段与冬季冲突不会被另一条8日价格覆盖。

先讨论清楚

  • 业务确认林芝8日冬季能否销售及对应报价资料。
  • 与桃花9日的推荐顺序、8天硬限制和客户确认方式。
L2 有上下文的个性化沉默跟进

涉及板块：会话信息提炼、沉默跟进决策、候选素材筛选、回复验收

开发步骤

  • 保存长期偏好、尚未解决的顾虑、短期状态和各自原消息；短期状态有到期时间。
  • 先筛选与当前线路、季节、拒绝项相符的内容，再让AI决定这一轮解决什么问题、是否适合发图。
  • 第一版覆盖不想拼陌生人、景点去过、时间未定、临时忙四类；保留现有每日限次及七天截止。

验收表现

  • #334不想与陌生人拼团：承接独团条件或时间安排，不机械发无关下午茶。
  • 客户说在开车：当下不催促；隔天不再假定仍开车。
  • 明确拒绝某线路/停止联系后，相关旧素材和跟进不会继续。

先讨论清楚

  • 第一批顾虑清单与各自允许使用的话术/素材。
  • 临时忙默认有效多久；客户给明确方便时间时是否替换普通节点。
L3 洗單回标签及回应后的强化承接

涉及板块：发送/回复事件关联、业务标签、客户信息提取、回应策略

开发步骤

  • 关联成功发送的跟进轮次和之后的客户回应，记录来源轮次、素材及回复时间，重复回调只处理一次。
  • 复用标签同步链路添加洗單回；不能直接复用现有customer.returned，因为它只按两次客户消息间隔30分钟判定。
  • 建议标签保留为历史经历，当前轮的承接状态单独保存；文字、点赞、图片可区分回应类型，不一律提高意向等级。
  • 客户说3—4位时解释3人可拼团、4人可独团的差异；给一至两个相关优势和一个推进问题，不猜成确定4人。

验收表现

  • 只有计划未实际发送、发送失败、系统消息或重复事件不误打洗單回。
  • 给人数后不只再问月份，也能围绕人数说明利益点。
  • 纯点赞不变成确认报名；人工/加私訊等控制规则仍然优先。

先讨论清楚

  • 跟进后多久内的回应算洗單回；是否含初始选项、点赞和图片。
  • 标签是否长期保留、是否允许人工添加；建议人工添加仅表示关注，不伪造系统归因记录。
  • 积极承接是否只改内容；建议第一版不增加每日主动发送次数。
L4 业务可维护的沉默跟进素材

涉及板块：素材管理页面、素材适用规则、跟进筛选与发送检查、预览与版本记录

开发步骤

  • 在现有素材库上增加明确的业务配置：适用线路/季节/主题、必需标签、排除标签、启停及优先级。
  • 第一版规则保持简单：必需标签全部满足，排除标签任一命中即排除；不开放任意复杂表达式。
  • 规则先产生合格素材候选，AI再按顾虑选内容；接待控制标签继续有最高优先级。
  • 下架时阻止新计划，发送前再次核对待发内容；提供会话预览，显示命中/排除原因。

验收表现

  • 业务停用一张素材后，它不会继续从待发队列发出。
  • 不上珠峰线路不收到珠峰住宿宣传；不符合标签条件不会进入候选。
  • 能预览指定客户为什么会收到这张图，修改有记录且能恢复。

先讨论清楚

  • 谁能编辑、谁能批准启用；标签由谁维护。
  • 素材顺序与AI选择的优先级；下架后的待发文字是否一并取消。
L5 指定问答场景图库

涉及板块：问答场景配置、素材库、接待决策、图片发送与去重

开发步骤

  • 第一版只做4—6人车辆、绒布旅馆厕所/住宿优势两类；每类绑定允许使用的事实和图片。
  • 结合客户当前线路、人数、车型和住宿季节匹配；无配置命中则只回答已知文字。
  • 优先选尚未发送的合适图片；业务确需随机时，只在合格且未发过的图片之间随机。
  • 与L4共享素材数据和启停逻辑，避免维护两份图库；检索已有图片不必每次运行视觉识别。

验收表现

  • 问车辆发对应车型，问厕所发对应住宿图片。
  • 冬季实际改住山下时，不把绒布照片说成本次入住。
  • 图片优势描述有事实来源，不虚构库存或把条件说成保证。

先讨论清楚

  • 两类场景的图片、适用线路/车型、季节和批准话术。
  • 每次发几张；已发过后客户再次索图是否允许重发。
H02 通用图片理解及其他表情、二维码识别

涉及板块：图片接收与下载、视觉模型输入、语义分类、旧决策取消与人工交接

开发步骤

  • 先验证已部署但未启用的内联图片链路；已核验点赞走本地识别，其他图片使用经测试的视觉能力。
  • 按表情/业务问题/联系方式/无法判断分场景；不因单纯收到图片就转人工。
  • 处理期间若客户又选线路，旧图片回合失效；原生消息反应需先取得真实事件样本，不能当作普通图片猜结构。

验收表现

  • 蓝色点赞以外的表情、酒店图、行程截图、二维码、模糊图、混合附件逐项验。
  • 图片紧接选线不会让过时判断转人工；未知图片不编内容。
  • 记录识别准确情况、调用失败和回复延迟，不能仅看接口返回成功。

先讨论清楚

  • 首批需要覆盖的图片类型与实际样本；视觉模型测试费用。
  • 看不清时的追问方式和必须转顾问的具体业务场景。
L8 多个新频道同时启用AI

涉及板块：收件箱设置、接待权限、图片与消息适配、30分钟跟进和标签同步

开发步骤

  • 将现有单一live_reply_inbox_id运行限制调整为明确允许的收件箱集合，保留已有逐频道AI开关。
  • 统一各入口的频道权限检查，避免普通回复和人工30分钟唤醒采用不同范围。
  • 按提供的Inbox清单逐频道验收；新接入频道默认不开AI。第一版不自动合并跨频道客户状态。

验收表现

  • A开启、B关闭：B的新消息、ai标签和到期任务都不能触发AI。
  • A能正常收图、切标签、交接和按规则跟进；跨频道不串线路或顾问。

先讨论清楚

  • 实际Inbox ID、各频道用途、要启用的范围。
  • 同一客户跨频道是否共享资料和归属；各渠道支持的发送方式与回执范围。
L6 顾问分单与限制转派

涉及板块：顾问分配设置、事件规则、顾问可接单与频道权限、分配同步和审计

开发步骤

  • 已有固定分配、轮询、事件优先级，以及按频道、线路、人数、天数筛选的规则；先逐条映射业务需求，能配置的先配置验证。
  • 第一版建议保留已有顾问归属，无归属的新交接在可接单且有频道权限的人中轮询，未匹配时走明确的兜底。
  • 业务确认班次、负载、离线/超时等确有必要后再补缺口；AI只提取客情，最终归属由规则决定。
  • 禁止客服转派单独核对实际Chatwoot版本和权限能力；事后自动改回不能等同于真正禁止转派。

验收表现

  • 相同事件重放不重复分单；可看到命中规则、候选顾问和最终原因。
  • 已有负责人时不被新的客户消息抢走；管理员授权改派按明确例外处理。

先讨论清楚

  • 客户归属优先级、轮询名单、兜底顾问、接单超时怎么办。
  • 是否真的要禁止转派，谁可例外；班次/负载是否属于首版必需。
L7 顾问企业微信或QQ邮箱通知

涉及板块：顾问身份映射、通知设置、发送队列与重试、结果展示

开发步骤

  • 复用已有内部通知/通用Webhook队列，先接一种明确渠道，再考虑第二种。
  • 维护Chatwoot顾问ID到企业微信身份或邮箱的对应关系；通知包含客户、场景、简短原因和会话入口。
  • 通知绑定分配事件版本，发送前复核当前归属；实现去重、重试和失败可见性，管理员可补发。

验收表现

  • A被分配时只通知A；重试不重复轰炸，发送前改派后不通知旧顾问。
  • 能区分渠道接受、实际送达/阅读；只展示渠道确实提供的回执。

先讨论清楚

  • 先企业微信还是QQ邮箱；企业微信应用/机器人或邮件发送服务及收件人。
  • 通知事件、时段和超时升级方式；外发测试只使用明确授权的测试收件人。
