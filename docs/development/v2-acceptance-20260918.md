# V2 第一轮效果验收记录

日期：2026-09-18。仅本地评测，无 Chatwoot 发送或部署。

## 本次范围

扩展现有 evaluate_reception_v2_preview.py，支持 --engine v1/v2、记录实际总耗时、模型与逐样本落盘。使用同一套三个演练输入与同一模型 deepseek-v4-flash，分别执行两版决策入口。样本包含价格、带历史的考虑表达和线路比较；不是历史客户旅程回放，也不是人工盲评。两版运行时间部分重叠，样本数量和负载控制不足以计算稳定的性能提升。

| 场景 | V1 总耗时 | V2 总耗时 | 本轮观察 |
| --- | ---: | ---: | --- |
| 9 日价格 | 6203 ms | 24890 ms | V2 回答较聚焦，但调用 5 次；明确线路问题被归为 route_selection |
| 和家人讨论 | 2828 ms | 156 ms | V2 固定短承接、不追加产品介绍；V1 继续介绍景点 |
| 两线比较 | 3719 ms | 18360 ms | 两版都回答区别；V2 出现“天数较紧、节奏较松”的含混表达 |

原始结果：output/v2-acceptance-20260918/v1.json 和 v2.json。

## 检查发现与修复

- 修复候选事实编号与内容组、素材编号混比的问题：从已确认文字交付或主题覆盖的内容组映射到事实编号，再排除沉默候选。单独发过图片不视为已发送文字事实。
- 没有明确关注主题时不再默认允许所有候选。
- V2 定向测试 23 passed，其中包含真实内容组到事实编号映射的回归。

## 尚未兑现的架构能力

- decision_contract 目前只在 trace 中，发送与调度仍读取 EvaluationDecision；不是强制执行合同。
- Flow 是关键词启发式，有误分类；Skill 索引、允许加载清单和实际预载 trace 尚未统一。
- 历史主题不等于未解决问题；当前 unresolved_topics 不能作为问题仍未解决的证据。
- 沉默候选没有在模型返回后进行完整强制约束；此次去重修复不等于端到端不重复保证。

## 下一轮优先级

1. 统一 Flow 路由、预载和工具清单；明确线路提问直接使用对应线路，比较仍可读取双方。
2. 接通执行合同及生成后沉默约束，覆盖延期、停止、人工、线路保留和候选外回复。
3. 建立包含实际发送回执的多轮隔离回放，接入真实历史样本和盲评表，再扩大至计划的 100 轮。
4. 用相同负载重测事实问答延迟，拆分工具、生成、核验和重写耗时。

## 2026-09-18 后续修正

客户明确说出“9 日价格”或“11 日价格”时，Flow 路由现在识别为对应线路的 `route_detail`，不再先走线路目录；对应线路 Skill 预载，事实工具直接查询。9 日价格样本从约 24.9 秒降至约 16.2 秒，工具调用从目录加事实两轮降为事实一轮。回复仍比本轮 V1 约 6.2 秒慢，说明剩余耗时来自模型生成、事实核验或重写，尚未达到速度门槛。

随后增加了服务端事实预取：明确线路和主题的事实型问题在模型调用前读取事实，并注入只读上下文，模型不再重复调用事实工具。9 日价格样本约 12.8 秒、模型请求 2 次、事实工具调用 0 次，仍保留事实核验；全程 `outbound=false`，没有 Chatwoot 发送。

本轮增加耗时拆分后，同一只读样本约 14.4 秒，其中模型请求约 9.1 秒、事实核验约 5.2 秒、重写 0 秒。结果说明剩余主要瓶颈在第二次模型核验，而不是事实工具；下一轮应评估核验输入压缩、核验结果缓存和窄场景本地预检，不能直接取消事实核验。

已增加有界的只读核验缓存，并将核验 JSON 输出上限从 650 收紧到 400 token。冷启动的 9 日价格样本约 13.2 秒，其中模型请求约 7.8 秒、事实核验约 5.4 秒；缓存对重复回复和重试有效，但不会降低首次冷启动延迟。下一轮继续做核验输入压缩和窄场景本地预检。

结论：暂不满足 V2 上线效果门槛。不能用现有单元测试数代替回复质量与速度证据。
