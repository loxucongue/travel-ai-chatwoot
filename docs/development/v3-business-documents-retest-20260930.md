# 三份业务文档的 V3 回复效果复测

日期：2026-09-30。结论：**尚不能满足全部业务要求。主要缺口是已有通用资料没有接入、原话与事实口径冲突，以及模型在长对话中没有稳定执行简短回答和留资时机。不是继续增加审核器才能解决。**

本次依据 AI.docx、AI(1).docx、AI(2).docx 的文字建议与截图，复用原验收的 B01–B37 编号。旧 V2 测试不能作为当前 V3 的通过证明。后续“官网第一、二条线路原文优先”“介绍完成后集中答疑”等明确要求优先于旧文档；冲突单列。

## 已经定位的原因

### 已有答案没有进入 V3

客户问：“有隨團醫師嗎？不舒服會怎麼處理？”实际答：

> 隨團醫師這一項我們的資料目前沒有列，這點需要顧問幫您確認清楚。

项目的 `data/knowledge/china2go/service-knowledge/service-knowledge.json` 已有 `service.medical_support`、`service.medical_logistics` 及 `tour_doctor_service` 完整原话，说明没有随队医师、导游协助正规就医。原始官网快照也保存了依据。

但 V3 的 `service.py` 当前只调用 `active_web_facts()` 取得数据库中的官网知识，`runtime.py` 将这批内容交给模型；本轮实际输入只有 31 条官网事实，缺少上述答案。当前后端没有读取这份旧服务知识 JSON 的引用。**文件存在不等于模型读到，也不是本轮模型忽略了一条已经加载的医师事实。**

这个错误还污染后续对话：AI 把“有没有随团医师”当成未解决事项，反复说要顾问确认，并用它作为第二次索要 LINE 的理由。

处理建议：把这几条已存在的通用事实和简短原话迁入 V3 实际加载的通用知识／通用话术；保留来源。不用业务重新写一遍，也不用把整篇医疗文章塞进提示词。迁入后核对真实输入，再重跑医师 → 考虑 → 沉默的完整链路。

### 源资料相互冲突

- 75 岁：AI(2) 第 21 段明确“65–75歲都可以參加”并需健康证明；当前 `age_75_entry_claim` 写“75歲以上…申請不下來”。本轮模型对“媽媽剛好75歲”实际答“恐怕沒辦法一起進西藏”。**按业务文档不合格；按后来官网原文优先能解释其来源，但不能把两套口径都写成满足。**
- 64 岁：正确否定“最低65岁”，却进一步说“没有最低年龄限制”“64岁不用准备健康证明”。已知“65岁以上需证明”不能据此推出所有其他年龄的文件豁免或儿童报名条件。这是推论错误，不只是75岁的来源冲突。
- 固定 SOP 的希尔顿介绍仍只写“除了地區條件有限以外”，未列出波密／珠峰；通用 Skill 已列出具体例外。模型问答能回答波密不是希尔顿，确定性发送的 SOP 却不会被 Skill 自动修正。
- 团型 4–10 与当前 4–6、先希尔顿与官网先绒布、旧“比較”禁词与官网原文，均是旧新口径冲突。车辆 SOP 本轮已是“航空座椅車”，不能继续沿用旧报告说它仍写“航空母車”。

处理建议：在当前生效配置中统一一份答案，尤其年龄的“含 75／超过 75”。固定 SOP 的具体例外直接修配置原文，不增加发送后改写。此处是产品报名口径核对，不是对现实入藏或个人健康资格作认证。

### 有事实也可能错误推论

客户问：“如果湊到6位有多人優惠嗎？”模型答：

> 限量升級4-6人小團價格不變～所以湊到6位不會有另外的多人折扣喔。

“小团升级不加价”推不出“没有另外的多人折扣”。旧业务文档第 88 段又明确提到多人优惠。当前通用 Skill 已写“没有折扣数字，不代表没有优惠”，本轮仍答错，因此不能把问题全部归为没有提示。

处理建议：补充当前有效的多人优惠事实和一条完整答复，区分团费、小团升级、独立成团报价和额外折扣。具体折扣未知就保留待确认部分，不能擅自说没有。把该案例保留为长对话验收，不能仅增加一句禁令后宣称解决。

### 原话选择与表达仍不稳定

- 高反回答虽提到 9 日不上珠峰、林芝进入，但接着复述氧气浓度、车辆设备、医师和资料，仍明显偏长。
- 红景天、丹木斯没有输出个人剂量或提前天数，但重复“不能替医师决定”等话，未达到文档要求的简洁承接。
- 介绍完成后同一轮既问家人是否有长辈／小孩，又问 LINE，违反一个必要尾问的目标。
- 出现“您们”“团费”混入繁体文案；单問车座位仍顺带介绍制氧机。
- 顾客只问能否代订机票，回答又追问出发机场，主动进入查航班准备。应先回答服务能力，再看客户是否委托。
- “我把这点列给顾问确认”等文案，不一定对应实际人工任务；本轮仍有此类表达，不能把文案当成已执行。
- A 的客户只问64岁，模型却套用“您先和家人讨论，时间还不用急着决定”的留资原话；客户尚未说要考虑，也已给三月底。说明已经有话术，但适用场景选择仍会出错。

处理建议：优先把文档中的短答整理成少量高频场景原话：高反、用药、座椅、集合、机票服务、多人优惠；写清适用问题和可以删掉的衔接。通用 Skill 只保留统一的表达与推进方法，不再堆重复规则。是否有效用同一长对话验证。

## 最小改进顺序

1. 接上现成但未进入 V3 的通用服务事实与原话，先修随团医师／就医协助及简短用药答复。
2. 在生效数据源统一酒店例外、75 岁边界、多人优惠。固定 SOP、场景话术、线路事实保持相同口径。
3. 用少量完整话术示例解决短答、一个尾问和留资理由；错误未知事项不能成为留资理由。
4. 修订后复跑同一批关联对话，检查错误是否消失且没有新增漏答。保持一个主模型，不增加后置审核和关键词改写。

只补线路事实不能解决全部问题。线路独有的信息放线路资料；医师、用药咨询、交函等共享内容放通用知识和话术；真的未知的房内配置、非成都交函、实时折扣需要业务提供。已给过的答案应由我们接入，不能继续要求业务重复提供。

## 沉默和最终结果

四组均完成并停止测试，客户输入分别为 N 13轮、E 12轮、A 7轮、B 3轮，共35条。没有任务执行异常，不等于业务答案全部正确。37项要求中有来源冲突、部分符合、已有证据以及本轮未重测的分支，不将它们合并成一个误导性的通过率。

开场四组逐字及图片哈希均与配置匹配，均仅发一次。完整介绍四组均与配置的正文、附件和顺序一致：9日16项，11日20项。配置间隔2秒，实测中位约2.03–2.04秒，最大2.85秒；模型与调度耗时另计，不能说每项到达严格不超过2秒。

N 普通沉默真实观察 **520.40秒**：

1. 最后一条回答在北京时间17:22:10.804；三分钟计划到期17:25:10.804，实际消息17:25:19.830，晚约9.03秒，包含模型等待。
2. 实际内容为：“您先和家人討論，時間還不用急著決定。隨團醫師和途中就醫怎麼協助這兩點還需要顧問幫您確認清楚，方便留一下您的 LINE ID 嗎？”
3. 这是第三次邀请LINE，前两次在介绍后和索取PDF后。形式上与顾虑有关，但“医师待确认”本来已有资料，这条不能判为内容准确的唤醒。第一次错误答案、第二次留资、沉默提醒和最终交接均受到同一缺口影响。
4. 再五分钟计划17:30:19.830，模型17:30:25.591完成，选择wait，未重复消息；配置两次间隔已耗尽，没有下一次计时。模型reason说“保留后续评估”与实际没有下一节点不一致，客户不可见但诊断说明不能据此声称还会继续。
5. 之后客户说不用LINE、用Email；AI只问信箱，收到实际邮箱后handoff=true，停止计时。**交接动作符合，交接内容仍带错误待确认事项，不能算整段业务全通过。**

E 拒绝后真实观察 **310.46秒**：没有主动消息、没有沉默模型调用；客户回来问11日是否有纳木错，仍正常回答并保留拒绝状态。此项符合受测要求。

生产沉默 `enabled=true`、`live_enabled=false`、间隔 `[1,120]`；本轮的 `[3,5]` 只在隔离测试库。测试结束生产真实出站仍为45，接待配置原始值哈希不变。不能把沙盒触达写成正式客户已被主动唤醒。
