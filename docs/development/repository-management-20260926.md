# 代码仓库管理与初次导入范围

日期：2026-09-26。

## 初次导入

仓库用于保存当前前后端、Relay、迁移、测试、运维脚本、产品知识与项目文档。此前工作目录没有 Git 历史，本次首次提交是当前工作目录快照，不是旧版本历史恢复，也不能证明该快照已部署到生产。

回复质量设计入口：[业务目标与结构设计](../product/ai-reply-quality-design-20260926.md)。本轮没有修改 AI 回复运行逻辑。

## 代码与运行资料分离

- 提交 `backend`、`frontend`、`cloudflare-relay`、`scripts` 中的源码与依赖声明，以及 `docs` 和 `data/knowledge` 的业务知识资料。
- 不提交真实环境文件、凭据、数据库、客户回放数据、日志、依赖目录、构建输出、临时目录及历史压缩备份。
- `backend/.env.example` 和前端 demo/production 环境文件经检查仅含占位值、开关与服务地址，不包含部署密钥。配置中已有域名及非密钥资源 ID 保留；换部署环境时需调整。
- 原始历史客户评估数据位于本地运行资料中；`data/evaluation/chatwoot_customer_journeys` 同样排除。私有仓库也不作为客户聊天或生产数据库的备份位置。

新检出的仓库不包含客户历史、演练数据库、实际上传附件或生产加密设置。历史客户回放功能及依赖本地数据的测试，需要另行恢复经授权的数据集；不能将旧工作区的全量测试结果当作空环境复现结果。日常单元测试应逐步改为自带合成样本，业务盲测集则单独控制访问。

## 后续改动方式

建议 `main` 保存经检查的基线，回复质量改造使用 `feat/reply-quality` 分支。每次提交关联业务场景、版本与验证结果，避免把代码修复、运营知识发布和实际生产切流混为同一件事。

首批任务顺序：

1. 冻结现状及差评样本的实际版本，记录初稿、修复和终稿。
2. 整理业务认可的台湾表达范例与独立盲测集。
3. 在离线演练中拆出本轮回复计划与表达职责。
4. 验证质量、时延和交付，再小范围切换会话。

本轮导入前检查了候选文件中的常见令牌/私钥格式、疑似硬编码凭据，以及与本地密钥值的重复；发现的候选经复核为测试占位或变量引用。此类检查不能证明任意未来新增文件都无敏感信息，后续提交仍需看差异。

本轮只改文档与 Git 忽略规则，验证提交范围、文档链接及远端状态；没有重新运行应用全量测试或调用模型评测。
