模型自主接待：架构方向与真实测试

China2Go · 2026年11月1日 · 独立测试、未上线

结论：可以减少互相冲突的规则，但不能用“顾问身份＋更多思考”直接替换现有接待。

本轮实现4个隔离试验版本，测试覆盖15个不同场景，记录225次实际模型调用。 相关回归244项通过；真实效果没有全部达标，试验开关默认关闭，并限制只能在禁止外发的evaluation环境使用。

费用¥4.5610，低于本轮自行设定的新增¥10上限；全部调用与原账本对账，无未结预留。没有向客户发送消息，没有部署或推送主分支，rujing2代码未修改。

本轮实际改了什么

部分实现边界
主模型统一负责接待试验分支绕过额外的选线语义调用，由同一个模型选择动作并生成答复。仅客户接待主流程；既有顾问跟进、定时跟进保护保留。没有增加关键词表或新政策分类器。
一份顾问工作说明顾问目标、可信事实、沟通分寸集中维护，不同时注入整套通用SOP、线路SOP和发送前提醒。不是要求输出推理过程；只记录简短依据。业务条件与执行字段依然需要清楚。
产品与话术分开读取当前线路事实，比较时由模型调用资料工具；价目模板独立读取。事实继续来自现行资料，不把顾问聊天中的单次承诺推广到所有线路。
记忆可追溯新资料写入附客户原话来源，实际选线沿用执行层审计。有来源不代表语义正确；本试验还暴露了来源字段增加协议负担的问题。
思考投入对照同模型分别测试low和high，high增加输出余量；价格、权限、队列继续用现有执行校验。high没有消除编造服务或错误动作。接口能力见官方说明。

结果要分开看

同一批6组、15步对照：常规路径41次模型调用；精简协议low为31次，high为26次。 系统指令及预载资料的平均字符量约78,914 → 21,911，但这不是总输入token数。high平均非空答复约113字，常规约76字，反而更长。 本组费用约¥0.612 → ¥0.757；缓存和随机输出不同，不能据此承诺长期省钱或更快。

该15步三组程序断言都通过，人工复核仍发现未经确认的用餐服务、过多日期提醒和不必要转荐。说明格式、报价和流程检查通过，不等于自然沟通质量通过。

最终版具体表现判断
已报价/人数档位：2人与3人同价，5人报¥12,580；完整新客流程最后9日报¥10,780。这些样本正确，不能代表所有价格边界已回归。
只比较9日与11日：独立读取资料后未再附整份报价；“桃花9日”简称能结合上一轮选项接住。方向有价值。转荐、选线和资料阅读仍需更清楚的协议分工。
考虑后轻邀、拒绝后保持当前渠道、次日等待、客户回来答餐食。最终补充场景4步通过；邀请理由仍提及名额更新，缺少明确能力依据。不能只凭contact_invitation标记认可文案。
“先锁1月7日两间房”没有交顾问，反而报价并解释房差；常规路径在同场景正确静默交接。发布阻断项。试验不能替换当前生产。
反复出现“导游带大家用餐/推荐餐厅”等当前快照未确认的安排。常规路径和试验版都有，不能把它只归因于本次改动。需要业务确认事实、提高来源约束的可用性。
常规路径把“我没有说不去，只是了解安排”记成want；试验版没有这样记，但一次明确改9日未写独立avoid字段。前者是未经明确表达的偏好推断；后者仅为字段诊断，当前切线正确，后续影响尚未补测。不要将两者混成“错选线路”。
完整流程试验版介绍后已邀请一次，收尾没有再次邀请；常规路径在收尾首次邀请。原“收尾必须邀请”断言对前者误报，已复核；试验版首次邀请偏早、后续重复团期，仍不如常规路径的节奏。

从整体设计看，下一步要改接口，不是继续补例句

层次建议的职责避免的维护问题
主模型统一理解真实对话、选择资料工具、判断答疑/建议/邀请/澄清，并形成答复。不在外层叠意图分类、补救分类、关键词规则，多个节点分别下结论。
资料工具产品事实、现行价目、素材、顾问方法分别读取，保留线路、日期、来源和版本。不同8日线路混用；历史顾问承诺变成全公司政策；读价格被误当推荐。
执行协议明确区分讨论对象、客户已选路线和模型推荐；把通知顾问、发送答复等动作与实际能力绑定。当前跨线价格需借用recommend字段，handoff又要求messages为空，容易在“答已知、交未知”场景产生冲突。
程序执行价格计算、来源ID、人工权限、队列幂等、真实发送及库存工具权限校验。不靠客户字词判断模糊语义，也不因模型写“我帮您保留”就假定发生了预订。
评估检查整段对话是否解答、真实、恰当推进、尊重偏好；允许不同合理措辞和行动。不机械规定每轮必须问一个问题、必须不发、必须填写某个偏好字段。

本轮保留隔离试验和回归样例，暂不切换生产。未来应逐项验证工具和接口变化，保留当前表现较好的业务约束；并以完整对话复测决定是否替换，不能同时删掉大量约束后只看短问答。

顾问Excel如何融入

237条待审核资料仍未自动作为事实启用。应拆成两类：

  • 产品事实：绑定适用线路、季节、对象、来源、有效期，由业务审核后进入现有知识配置。具体酒店、房价、退款、额外服务不能仅凭一条顾问聊天确认。
  • 接待方法：提炼顾问解决什么疑虑、为什么给这项解释、何时留出空间；保留正反例和适用边界，作为模型可参考的方法，而不是“出现词X就执行动作Y”。

持续循环：真实交接案例 → 形成待审经验/事实 → 业务审核 → 与常规方案做连续对话对照 → 小范围启用 → 查看误答、误交接、客户回话与顾问纠正 → 更新或回滚版本。 自动采集、业务审核配置页及自动上线流程本轮尚未实现；没有将模型微调或转化率提升列为已完成。
