# 完整假期与西藏行程：实现及验证（2026-11-01）

状态：**已于2026-11-01 12:41（北京时间）部署并核验**。发布前使用线上只读配置快照做隔离测试，没有向真实客户发送测试消息，也没有修改线上配置或客户状态。

## 业务效果

拼团客户明确包含出发地往返时，按已确认业务资料预留行程前后各一天，产品 N 天需要至少 N+2 天完整假期。日期按首尾均包含计算。包团按实际起讫地及航班核对，不直接套拼团预留，也不保证免预留。仅说可出发日期不扣天；范围不明先问。已完成的交通段不重复计算。

真实模型最终复测的原始案例回复：

> 這條9天行程連同台灣往返，建議要留11天。您說的4/3–4/11含頭尾是9天，還差2天。
> 因為要經成都轉機，建議前後在成都各住一晚。假期有機會多留兩天嗎？

同一连续会话中，客户改为4/3–4/13后，模型重新计算，查询4/4这一入团日期，答复4/12拉萨送机、4/13回台。后续客户问早班机原因，才读取详细交通知识并解释航班延误及入藏函衔接。

## 一次回复怎么运转

1. 现有语义理解模型同时读取近期客户原话与已确认团型，返回 `travel_time`：本轮是查出发日、核完整假期、核包团实际衔接、澄清范围，还是解释交通。时间字段附客户原话证据；代码只校验引用来自客户，不用关键词或正则判断日期含义。
2. 主模型读取业务知识和上述解释。前后预留建议、包团例外、不同国家适用范围来自知识与模型指引，不在日期函数中按国家、路线名或客户措辞分支。
3. 需要核算时，模型调用通用 `calculate_travel_window`，给出产品天数、前后预留及日期/总天数。工具只做参数检查、首尾日期算术、差额和可入团窗口计算。
4. 时间放得下且要查团期时，模型用返回的可入团日期范围查询现有 `get_departure_quote`。这与“哪几天可以出门”不同，更不等于有余位或航班已经接好。
5. 模型自行写短答，必要时用 `interrupt=true` 暂停介绍。没有增加根据回复文字删句、替换答案或强行拼接固定回复的后处理。现有发送、权限、金额模板和分句机制沿用。
6. 完整假期保存在 `profile.holiday_window`；不会用它覆盖表示产品天数的 `trip_days`。客户纠正为“可出发日范围”时，模型清除旧完整假期记录。

详细交通原因放在服务事实的 `details` 中。主模型首次收到的是摘要，追问时通过 `get_service_facts` 读取详细内容。普通问题仍可以直接答，不要求每轮谈时间。
