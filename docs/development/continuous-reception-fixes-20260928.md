# 连续接待修复与发布验收

## 修复范围

- 首条消息先识别线路、人数和实际问题，再发送后台配置的开场；已选线路不再重复询问选线。
- 未提供人数时先询问人数；确认人数后按线路资料顺序发送整套介绍，保留各段间隔。
- 介绍期间普通问题排队，整套发完集中回答；停止、改线、人工请求立即处理。
- 联系同意与预约时间分开；实际联系方式不再因缺少预约时间而失败。
- PDF、车辆等组合资料按全部有效素材解析，避免被当前主题过滤掉。
- 可选展示字段错误不再吞掉有效正文；已讲完的线路不会因为普通追问重新整套发送。
- 留资不重复催问；沉默围绕当前关注点，缺少相关新价值时不发送。

未增加话术审核模型。介绍期间的短模型调用只判断新消息应排队还是立即中断，不改写回复。

## 发布前证据

- 后端全量：1443 通过，52 跳过；最终定向回归：79 通过。
- 前端测试及生产构建通过。
- 两条线路连续真实模型演练共 21 条客户消息，无失败运行；覆盖介绍中插问、联系方式交接与组合资料。
- 测试出站记录为 0。真实渠道、手机设备送达不在本次隔离测试结论内。

## 发布后计划

使用已部署代码、生产配置只读副本和隔离数据库，执行六段长对话、三种介绍中断，以及真实等待 3 分钟和 5 分钟的沉默测试。脚本为 `backend/scripts/verify_continuous_reception.py`。只允许模型 HTTP 调用；不复制真实客户对话，不向 Chatwoot 发送消息。测试专用触达时段和沉默间隔不修改生产设置。
