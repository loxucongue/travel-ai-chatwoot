# SOP 轮次、标签与本地测试说明

更新：2026-08-26。适用于本地演练版本，不代表真实客户实发已验收。

## 1. 本次修复后的规则

| 场景 | 结果 |
| --- | --- |
| 同一客户、同一策略，已有进行中轮次 | 不创建第二个轮次，跨会话、发布版本和重复请求同样去重 |
| 从未入组，新增匹配的会话标签 | 自动创建第 1 轮 |
| 首次客户消息触发策略 | 只在已知的首次公开客户入站消息时入组，不是每条消息入组 |
| 本轮完成、取消、阻断后再次打入组标签 | 不自动开启新轮次 |
| 结束后移除退出标签、关闭再打开 AI、发布新版本 | 均不自动恢复旧轮次或新建轮次 |
| 操作员明确选择“重新入组” | 新建下一轮，保留上一轮记录，从新的入组时间排期 |
| 重复提交相同重新入组请求 | 返回同一个轮次，不重排计划、不清空运行中的消息 |

客户身份使用本地 Chatwoot Contact ID 与租户组合；无联系人时回退到会话 ID。纯模拟客户以隔离会话为身份。实时观察与隔离演练分开计算，避免测试干扰真实观察。

数据库使用轮次唯一键、请求幂等键和“仅一个 active 轮次”的部分唯一索引共同保护，而不是依赖 AI generation 去重。

## 2. 入组事件与退出标签

### 入组方式

- **手工选择客户**：操作员选择适用 Inbox 中的会话，首次入组或明确重新入组。
- **指定会话标签新增**：运行中的已发布版本监听 `conversation_created/conversation_updated`，匹配本次新增标签，任意一个入组标签命中即可。
- **首次客户消息**：公开 incoming 消息，不包括系统活动、私密便笺和 outgoing/echo；老账号已有历史客户消息时，不会再次命中“首次”。

这里的标签是 **Chatwoot 会话标签**。不是 Facebook 的 Message Tags，也不是给联系人资料加的 Contact 标签。

发布策略不会扫描所有已有标签并自动补入组。首次入组测试应在发布以后新增标签。已经有该标签、但从未入组的客户可手工首次入组，或先移除再新增该标签。已结束过的客户仍必须明确重新入组。

### 退出方式

业务退出标签是 OR 关系：当前会话命中其中任意一个，本轮剩余内容组取消。例如只配置 `报价已确认`、`无需跟进`，任一个出现即退出。

以下安全保护不由业务退出标签输入框决定：

- 客户再次发送公开消息，包括附件消息。
- 人工接管、投诉、拒绝联系、黑名单、留资、成交等固定或映射的阻断标签。
- 有待处理/已领取的人工任务、AI/Inbox/Account 开关关闭。
- 渠道当前不可回复、未知或过期的自动消息窗口。

普通标签新增/移除、重复的无变化事件不会取消 SOP。退出后删除退出标签，也不会复活原轮次。

超过 5 分钟的旧入站 Webhook 只补充历史上下文，不开启新的自动回复、不用其旧会话快照覆盖当前控制状态，也不取消刚开始的新轮次。历史导入不会产生自动入组。

## 3. 时间起点与内容组

**本轮入组时间**是默认起点，适合老客户再次跟进；**客户首次进入**指此联系人在该 Inbox 中最早同步到的公开入站消息时间，不是 Facebook 好友添加、关注粉专或导入本系统的时间。

| 配置 | 含义 |
| --- | --- |
| 相对分钟 10 / 20 | 起点后第 10 / 20 分钟 |
| 第 N 天 10:00 | 上海时区的自然日；第 1 天为起点当天，第 2 天为次日 |
| 上一组发送后 10 分钟 | 上一组全部内容模拟确认完成后，再等待 10 分钟 |

每组可按顺序配置文字、图片和视频，本地上传与预览，不依赖 OSS。前一组未成功确认，后续组不会继续发送。素材不存在时拦截，不以占位文字冒充图片。

同轮的 10 分钟、20 分钟、上一组后 10 分钟可连续执行。**跨轮次、其他 SOP 与唤醒**共享联系人频控，默认至少间隔 24 小时，从最近一次内容组模拟确认时间计算。重新入组不绕过频控。

联系时段为上海时间 09:00–21:00；过期宽限最多 15 分钟。当前实现不会把夜间到期节点自动顺延到第二天，而是记录跳过原因。

第 2、3 天的节点是合法排期，不等于 Facebook 允许发送。如果初次客户发言在 10:00，次日 10:00 已超出本系统预留 5 分钟的自动消息窗口。客户再回复又会结束旧 SOP，因此不能把多日营销计划当作无条件持续群发。

## 4. 一个老 Facebook 账号如何测试

### A. 纯本地模拟，最快且不影响客户

1. 打开 [SOP 配置](http://127.0.0.1:4175/#/sops)，建立仅用于测试的策略。
2. 选择“指定会话标签新增”，从已同步标签中选择专用测试标签。入组与退出标签不能相同；安全阻断标签不能用于入组。
3. 时间起点选“本轮入组”；安排第 10 分钟、第 20 分钟、上一组后 10 分钟，填入文字或本地图片/视频。
4. 保存草稿并发布。草稿修改不会改变正在运行的发布版本，修改后要再次发布。
5. 进入 [SOP 时间模拟](http://127.0.0.1:4175/#/playground?mode=sop)，演练起点选择上海时间 10:00，新建隔离演练。
6. 发一条模拟客户消息；等待被动回复处理结束，再应用测试入组标签，或明确点击“首次入组”。
7. 每次推进 10 分钟，检查内容组状态、文字、素材和阻断原因。不要一次跳过太久，超过节点 15 分钟宽限会过期。
8. 模拟人工接管或发送第二条客户消息，确认剩余内容取消。取消人工/移除标签不会自动恢复；选择发布版本后点击“重新入组”验证下一轮。

同一客户上一轮已有模拟发送时，立即重新入组仍会受跨轮次频控影响。要快速独立验证不同场景，可新建一个纯模拟客户；不要通过改真实客户时间来绕过渠道窗口。

### B. 真实 Chatwoot 标签驱动本地演练

1. 保持本机 API、演练 Worker 和 Relay 运行；Chatwoot Webhook 必须订阅 `message_created`、`conversation_updated` 等已配置事件。
2. 老测试账号先给粉专发一条新消息，确保记录新的可信客户入站时间。
3. 确认 Account、Inbox、会话 AI 已开启，无人工/拒绝联系等阻断；选择专用测试策略，时间起点为“本轮入组”。
4. 发布以后，在 **Chatwoot 对应会话** 新增匹配标签。若从未加入此策略，自动创建第 1 轮，不要求新注册或新添加的 Facebook 账号。
5. 在 SOP 的“版本与执行明细”查看实时观察演练，包含客户会话、轮次、计划时间、模拟状态和原因。
6. 该轮结束后，在策略列表点击“重新入组”，来源选“Chatwoot 实时事件”，选客户并确认；反复增删标签不会重开。

**当前结果只写入演练表，不会发送到 Facebook。** 本次仍保持 `APP_PROFILE=evaluation`、`OUTBOUND_MODE=disabled`、`CHATWOOT_WRITE_ENABLED=false`。分组 SOP 实发不在本次验收范围；旧发送器也不会处理新增内容组。不能通过直接打开开关来宣称已完成实发验证。

发布、入组、标签命中、到期执行是四个不同状态。已入组不等于已到期，更不等于允许发送。

## 5. Facebook Messenger 限制核查

核查日期：2026-08-26。以下针对粉专 Messenger API，不使用 WhatsApp 的分级额度代替 Messenger 规则。

### 时间

- 标准窗口为用户互动后 24 小时，窗口内允许包含推广内容。本项目保守地仅依赖可信客户消息，并额外预留 5 分钟。
- 内部打标签、策略入组、管理员修改会话、商家自己发消息，不会替代客户互动打开窗口。
- Human Agent 是人工处理的延长回复机制，可到 7 天；不是 AI/SOP 自动营销的 7 天许可。窗口外的其他专用机制还需要独立适用条件与授权，本项目未接入。
- 用户可以屏蔽或静音企业会话；滥用标签或违规发送可能导致权限受限。

来源：[Meta Messenger Platform policy](https://developers.facebook.com/docs/messenger-platform/policy/policy-overview/)。本地通过官方页面取得正文；不以第三方旧版教程推定本账号具备窗口外营销能力。

### 数量与速率

- Meta 的 Messenger API 配额文档给出的口径为：**滚动 24 小时调用次数 = 200 × 互动用户数**；这里是 API 调用配额，不是“每天能群发 200 个新客户”，也不是“每位客户一定能接收 200 条广告”。
- 限制还依赖 API、消息内容及账号/应用状态。本账号的可用 Send API 瞬时额度未做压测，不承诺某个每秒发送量。Chatwoot Cloud 本身的接口限制也是独立约束。
- 遇到限流要依据错误码、配额响应头和重试提示退避，不能持续重发；API 未超额也不代表窗口或消息内容合规。
- 本平台跨策略/轮次至少 24 小时的主动触达频控是自己的安全规则，不是 Meta 规定“每个客户每天只能一条”。

来源：[Meta Graph API Rate Limiting，Messenger Platform 段落](https://developers.facebook.com/docs/graph-api/overview/rate-limiting/)。本次不进行真实群发或额度压测。

## 6. 修复与审查覆盖

| 原问题 | 修复 |
| --- | --- |
| generation 改变或发布版本后可重复自动入组 | 独立客户策略轮次、唯一索引与显式重新入组 |
| 10/20 分钟节点被每条频控误拦 | 同一轮连续组允许执行，跨轮次/策略继续频控 |
| 任意标签变化均取消 SOP | 只有真实新入站、明确退出或安全阻断终止 |
| 草稿触发条件混入运行时 | 自动入组、范围检查、排期均读取不可变发布版本 |
| 手工入组越过策略 Inbox 限制 | 全批校验发布版本范围与操作员权限后原子提交 |
| 空触发标签、无效标签、入组/退出矛盾可发布 | 标签选择器、服务端发布校验与错误反馈 |
| 旅程阶段和标签入口重复 | 页面合并为实际支持的标签新增；旧 stage 参数兼容归一化 |
| 指标读到旧发送表 | 分开演练轮次/模拟内容组/阻断数，不冒充真实送达 |
| 删除失败上传项后仍不能保存 | 仅校验当前存在的内容项 |
| 重试重排、旧入站误取消 | 请求幂等与旧消息仅补上下文 |

验证结果：92 项后端测试通过；前端构建通过；两组桌面/手机浏览器检查通过。覆盖数据库空库升级与旧数据去重迁移、SQLite 并发入组、重启后幂等、发布版本隔离、标签入组与退出、越权拒绝、图片视频编辑及重新入组页面。依赖产生的弃用警告不影响当前测试结果。

真实库迁移前已备份。迁移后会话 173、历史消息 4578、已有出站记录 2、人工任务 0 均保留，外键完整性检查通过。运行中的 Relay 会继续正常镜像新消息，因此后续会话/历史总数可能自然增长；本次不得新增真实出站。

未验收：真实 Facebook 分组发送、真实客户转化效果、窗口外专用营销能力、账号瞬时发送上限。当前本机关闭或休眠会停止本地调度；Relay 能缓冲事件，不替代本地 Worker 执行策略。
