## 结论

**业务确实不需要复杂的多 Agent、流程分类和多轮话术审核。当前 V3 已采用简单主链，但还没有完成“后台配置—运行时—演练入口—实际执行”的一致性。** 现在继续加提示词，会掩盖配置和事件处理错误。

保留一个主模型、一个通用 Skill、两条线路 Skill、已有图文队列即可。不建议再建 V4，不建议恢复事实/范围审核模型，也不建议为了两个产品增加复杂搜索系统。优先修配置接线与事件处理，再整理原话。

| 要求 | 当前证据与判断 |

| 介绍中普通问题排队，发完再集中回答，最后问缺失信息 | `buffered_questions` 与 `introduction_completed` 已实现；既有连续样本覆盖。发现并发消息到达的一处窄时序可以清掉新问题待办，见下文。 |
| 使用原话，基于线路事实与官网答疑 | Skill 确实被加载，日志保留正文摘要；原话、SOP、事实、素材均来自当前配置。普通答疑仍常用模型重新组织 `text`，不保证逐字引用；数据重复、话术跨度过大仍影响选段。 |
| 主动索取联系方式、停止自动销售并转人工 | 原话与模型决策可留资，沙盒会记录 `handoff` 并停止后续自动接待。实际顾问任务、Chatwoot 分配、手机通知尚未接入 V3。 |
| 沉默三分钟、五分钟按上下文触达 | 已有实际等待与完整上下文重测。但这些样本通过客户明确预约覆盖默认时间，**不能证明后台时间设置对 V3 生效**；当前页面写入与 V3 读取确实不一致。 |
| 停止、改线、人工请求及时打断 | 模型返回 `interrupt` / `handoff` 后取消未发内容；正在等待模型时尚不能执行这一决定，不能解释成客户发送停止后立刻中断。 |

这里按最近已确认的节奏理解：完整介绍后，末尾问尚缺的人数等信息；已知不重复，不将更早的“必须先问完人数才介绍”重新叠加回来。

## 实际执行链

```text
页面创建独立 V3 演练
  → 首条客户消息入库
  → 开场配置生成图文队列，逐条模拟交付
  → 主模型读取通用 Skill、已知线路 Skill、历史和客户资料
  → 按需加载其他线路 / 官网事实
  → 输出 JSON 决策
  → 保存回复或整套介绍队列、客户资料及下次评估时间
  → Worker 逐条模拟交付
  → 介绍完成 / 新消息 / 沉默到期，再调用同一个模型
```

源码入口：[API](../../backend/app/automation_api.py#L1729)、[服务](../../backend/app/reception_v3/service.py)、[主模型](../../backend/app/reception_v3/runtime.py)、[编译与加载 Skill](../../backend/app/reception_v3/skills.py)。

确定的开场/SOP 用程序交付、理解客户和选择原话交给模型，这个分工符合需求。“模型决定业务”并不要求模型重新生成固定 SOP 的每一个字，也不要求每发一张图片再问一次模型。

## 需要优先处理的问题

### 1. 配置页面仍有“保存成功但 V3 不使用”的字段

**已确认并隔离复现。** [AiReceptionStrategy.tsx](../../frontend/src/pages/AiReceptionStrategy.tsx#L179) 写入 `silence.v2_intervals_minutes`；[skills.py](../../backend/app/reception_v3/skills.py#L35) 编译时删除所有 `v2_` 字段；[service.py](../../backend/app/reception_v3/service.py#L159) 使用 `intervals_minutes`。

线上只读检查得到：

```text
页面维护的间隔：[1, 120]
V3 实际间隔： [1, 2, 3, 5, 30, 60, 120, 240]
```

两者都是相邻两次评估的间隔，不是从进入会话累计的绝对分钟数。例如 `[3,5]` 通常表示首次等待 3 分钟，下一次再等 5 分钟。

| 当前页面配置 | V3 实际使用情况 |
|---|---|
| 开场文字、图片、开场间隔 | 交付服务直接使用 |
| 语气、语气说明、其他接待说明 | 编入通用 Skill，影响模型表达 |
| 接待目标 `reply.goal` | **未传入 V3**；使用 Skill 中写定的业务目标 |
| 通用话术与适用场景 | 编入通用 Skill |
| 主动留资开关、允许渠道 | 编入通用 Skill，模型判断时使用 |
| 大团转人工开关和人数阈值 | **未编入 V3，执行服务也没有读取** |
| 目录外需求策略 | **未编入 V3**；Skill 固定了西藏两线路范围 |
| 页面上的沉默间隔 | **编辑 V2 字段，V3 不使用** |
| 允许触达时段、每日次数 | **V3 不执行**；沙盒与生产用途需明确 |
| 线路原话、事实、图片、介绍顺序和间隔 | 从线路包编入 Skill 或队列；新一轮读取新配置，已有队列继续用已保存内容 |

复现：在隔离配置中将可见跟进时间改为 `[3,5]`、大团阈值改为 15、目录外动作改为只说明范围，`compile_skills()` 得到的整个对象完全未变。

**建议：** 当前公共接待页先解决字段生效合同。一个业务概念只维护一个值；暂时保留 V2 时，在编译边界兼容旧字段，不让运营同时维护两套。确实不打算支持的字段从 V3 配置视图移除，不做虚假的可编辑项。时段/次数在沙盒是否模拟要明确，不能默默忽略。

### 2. 有一个新消息可能失去待处理事件的并发窗口

**隔离复现，不代表已确认真实用户遇到过。** [service.py](../../backend/app/reception_v3/service.py#L260) 先建立旧消息上下文并领取任务，提交后在 286–287 行刷新会话，再将刷新后的 `row.generation` 保存为本轮 generation。

如果新消息刚好在领取提交后、刷新前进入，比较基准会变成新 generation，而模型输入仍是旧上下文。旧回答于是可能被标记完成，`apply_decision` 清空新消息的 `buffered_questions` 和 `pending_event`。

复现结果：新消息存在于历史；模型输入没有新消息；运行状态 `completed`；待答问题 `[]`；待处理事件 `null`。

**建议：** 在构造上下文时固定 generation，领取及应用结果都使用这一值（或运行记录保存的 generation），不要重新从刷新后的会话取基准。这是小范围消息一致性修复，不需要增加话术审核。

### 3. 模型失败后，问题可能无人继续处理

**隔离复现。** [service.py](../../backend/app/reception_v3/service.py#L306) 异常分支记录 `last_error`，同时把 `pending_event` 和 `due_at` 清空。客户问题还在缓冲区，既没有自动重试，也没有建立人工任务。

注入一次超时后观察到：`pending_event=null`、`handoff=false`、客户问题仍保留。除非客户再发消息，否则这一轮可能停住。

**建议：** 保留失败事件可重新执行的状态；对临时连接失败作有限重试，耗尽后让演练明确显示“本轮失败／重试”。未来真实渠道复用已有人工任务。仍然不自动发送未经确认的安慰话术，也不重新审核正确回复。

### 4. 模型请求与所有演练消息的计时交付共用同步循环

**代码确认，尚未做多客户压力测量。** [playground_worker.py](../../backend/app/playground_worker.py#L22) 调用 `rehearse_tick`；[automation_service.py](../../backend/app/automation_service.py#L1713) 调用 V3 `tick`；[service.py](../../backend/app/reception_v3/service.py#L291) 同步等待 `run_agent`。

同一 Worker 在等一个客户的模型结果时，不能继续给另一个客户按两秒间隔交付。客户在 SOP 中每插一句普通问题，也可能触发一个模型请求来判断排队或中断。模型主循环预算 60 秒，所以现有单会话的正常时延不能代表多个客户同时测试的体验。

`stream=True` 也不等于用户逐字看到回复：[deepseek_evaluation.py](../../backend/app/deepseek_evaluation.py#L1114) 会收完整个流后才返回 JSON，页面随后轮询消息。它当前有传输流，没有用户界面的文本流，也没有工具参数一完成就执行的提前调度。

**建议：** 将模型执行与交付计时分开，同一会话保序，不同会话受控并发。优先复用项目已有任务执行方式，保持单体。暂时不用为聊天渠道开发复杂逐字流式 UI；先保证固定图文不卡住，以及停止事件能被及时消费。

## 话术和 Skill 的问题，应该怎样改

### 5. “开场原样发”与“已选线不再问选线”目前由配置制造冲突

当前全局开场第二项是图片加「您想先了解哪一條行程呢？」。V3 无条件先发全局开场，再让模型看线路，因此广告首句已经指定 9 日时，客户仍会先收到一次选线问题。

这不是模型没有理解，也不是开场未按配置发送。上一轮 #578 的首句包含 9 日与两位，实际开场仍包含上述问句，正好证明了这一点。

**建议：** 全局原样开场只保留两类入口都适用的品牌问候。选线问题放进“未选线路”场景；已知线路使用对应承接语。若确实要固定两种开场，就提供“已选线／未选线”两组原文，由同一 Agent 选用。不要再写客户文字的正则识别表。

### 6. Skill 结构已经正确，但动态内容仍重复、偏大

标准 frontmatter、索引、原生 `load_skill`、已知线路预加载及加载摘要均存在。不能再说当前只有一个名为 Skill 的字符串，没有真的加载。

真正的问题是 [skills.py](../../backend/app/reception_v3/skills.py#L101) 同时拼入完整 SOP、场景原话、线路事实和素材目录。相同的住宿、价格和介绍信息可能出现多次；多主题原话又要求模型每次自行剪选。上一轮数据：9 日有 33 条场景话术、17 条事实、8 组 SOP；11 日 36 条话术、18 条事实、11 组 SOP。

此前两条连续测试每个 HTTP 请求输入约 4,865–28,906 token。模型请求耗时中位数约 1.5 秒，**没有依据因此断言当前模型本身很慢**；但重复资料提高了维护成本，也让冲突更难发现。当前历史全部带入，最终超过 `deepseek_max_input_characters` 时直接失败，长历史没有压缩策略。

**建议：** 继续保留一个完整线路包，不必拆成十几个 Skill。底层每项信息只有一个维护位置：固定介绍按组、常见问答按单一问题、结构化事实作补充，素材通过 key 引用。优先把“价格＋人数＋房差＋出发日”的长原话拆成可直接复用的小段；模型负责选用和衔接，而不是每次重新写。两条线路暂不需要向量检索或复杂商品搜索。

### 7. 留资语言与真实交接要分别验收

当前 `handoff` 仅设置 `controls.v3.handoff`、`controls.human` 和原因，停止后续模型事件；没有调用实际人工任务创建、顾问分配或通知。

正式决策入口 [decision_service.py](../../backend/app/decision_service.py#L199) 仅接受 V1/V2。直接把真实会话数据库改成 V3，会遇到不支持的引擎；不是切一个开关就接通。

**建议：** 当前先用 V3 演练确认语言与节奏。正式接入时，只将同一个 V3 决策接到现有图文发送、人工任务与 Chatwoot 适配器，不复制一套新引擎。交接摘要使用明确的联系方式字段、线路、人数、日期、待办和已发资料；不要仅以模型说“已请顾问”作为完成。

## 测试为什么仍然漏问题

目前单元测试覆盖了排队、顺序、去重、结束事件等有价值的行为，但不少测试直接构造 `bundle` 或模拟 `run_agent`，不会经过运营页面保存这一层。已有三分钟/五分钟长对话使用明确预约，也绕过了后台默认时间。所以这些测试通过，与“配置时间未生效”可以同时成立。

页面 [AutomationPlayground.tsx](../../frontend/src/pages/AutomationPlayground.tsx#L386) 固定首句为「你好，我想咨询旅行行程」。随后再输入线路，不等于广告第一条消息就含线路：前者已经发过选线开场，后者正是需要验证的差异。

接待状态面板也不能当作模型真实阶段证据：[automation_api.py](../../backend/app/automation_api.py#L639) 对未转人工的 V3 一律显示 `value_building`。应以实际事件、队列及交付记录判断，不能只看状态标签。

建议保留少而完整的验收：

1. 页面允许输入首条消息或选广告入口。分别从“9 日广告”“11 日广告”“未知线路”开始，核对首次开场及认线。
2. 从实际配置页改一段原话、一张图片、SOP 间隔和沉默间隔，再建立新演练。比较保存值、Skill 实际输入、计划内容和送达顺序。测试后恢复配置。
3. 一条至少 12 轮的关联对话：SOP 中插问、补人数、介绍末尾问日期、主动留资、忽略留资继续问、改日期、约定等待、提供联系并交接。检查客户关心的问题最终都被处理。
4. 分别验证“默认沉默三/五分钟”和“客户指定三/五分钟预约”，不要混为一项。到期不必一定发送，但发送应与当前关注点有关；没有新价值应停止。
5. 同时跑两位客户：A 正在介绍，B 模型变慢或失败；A 的交付不被 B 拖住。消息恰好在领取任务时进入，也不能失去待处理事件。
6. 最终由业务读完整对话，判“可直接发送／需改写”，同时看图片、顺序和动作。模型调用成功和程序测试通过不等同于业务满意。

## 建议的实现顺序

1. **修配置生效与待处理事件。** 统一沉默字段，处理无效配置项，固定 generation 比较基准，补失败后可继续处理的路径。这批应很小，不改回复架构。
2. **修测试入口与调度。** 可以从广告原始首句启动；模型请求不阻塞交付计时，验证两个客户同时接待。
3. **整理当前两条线路原话。** 通用开场不夹选线，场景原话拆成可直接选用的段落，删除重复表达和相互冲突的说明。维持最终输出直接使用。
4. **完成同一组业务长对话验收后接实际渠道。** 复用现有发送与交接能力，不先重做日志、配置 UI 风格或新增平台化架构。

本轮只实施演练默认切换与版本标识。以上审查缺陷尚未修复，不能写成已经全部解决。
