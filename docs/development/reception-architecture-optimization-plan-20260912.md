# 接待系统整体优化方案与验收计划

状态：第一阶段核心链路已于2026-09-13实施并部署；统一内容资产、单一执行器、完整人工闭环和全量运营配置追踪仍按本方案继续迁移。
依据：AI.docx、AI(1).docx、历次已确认业务要求、当前源码和已保存的演练结果。
本方案不更改生产配置，不表示现有缺口已经解决。

## 1. 最终目标

不是让机器人把SOP发完，也不是单纯把留资次数提高，而是：在公域聊天的短时间内回答客户真正的问题，以自然、可信、图文一致的方式介绍产品，适时取得客户愿意提供的一种有效联系方式，或把完整需求交给人工继续跟进。

五个可观察目标：

1. 客户问什么先答什么，不以路线介绍、人数问题替代直接回答。
2. 选线后及时按业务批准的顺序介绍，但客户插话、拒绝、换线和人工接管优先。
3. 不确定、已知、暂不愿提供不是同一种状态，不反复问，不把人数日期当留资硬门槛。
4. 图片、文字、追问、沉默消息看起来属于同一个顾问的连续接待。
5. 运营知道配置是否生效、实际发了什么、引用了什么、为什么停止；真实发送始终可控。

转化率必须在真实灰度中衡量。演练不能证明客户愿意留资，也不能证明台湾客户对语气满意。

## 2. 是否需要大改

结论：需要中等规模的核心流程重构，不需要推倒重建整个项目。

### 保留

- Chatwoot接入、Webhook收件、消息幂等和远端标签门禁。
- 当前Python后端、React后台、关系数据库和现有worker，不先引入微服务或新消息中间件。
- 模型理解 → 代码规划 → 受限生成 → 事实/问题核验的职责分工。
- 已有线路包、素材文件、定时任务、人工任务和追踪记录，优先扩展而非全量替换。
- 已审核固定原文的逐字发送，以及版本快照和演练隔离的方向。

### 重构

- 统一即时回复、首轮介绍、尾问和沉默跟进的计划归属。
- 统一实际发送明细、介绍进度和追问状态。
- 统一业务事实、服务知识、固定回答、素材说明的发布与检索入口。
- 统一演练与真实执行，只让发送适配器和时钟不同。
- 把测试从单次返回值提升为整段会话、最终消息序列和业务逐项验收。

不建议新增更多智能体或继续扩大主提示词。当前主要缺陷不是模型数量不够，而是跨模块共享状态与合同不一致。

## 3. 当前不合理之处：证据与影响

| 已观察到的问题 | 当前实现证据 | 工程后果 |
| --- | --- | --- |
| 即时回复不追问，首轮末尾又加人数问题 | route_reply.py的deferred_initial_follow_up在没有问句时根据missing_slots重新决定追问 | 回复规划不再是动作的唯一来源，健康等场景容易机械衔接 |
| 内容覆盖粒度过粗 | realtime_reply_pipeline.py的_covered_groups可通过一个事实或素材的交集认定整个内容组；ConversationJourney主要存sent_groups | 用过一张照片不等于图文介绍全部完成；可能误跳过或重复补发 |
| 演练和真实编排仍有两套实现 | automation_service.py与live_reply.py/live_sop.py都处理首轮、尾问、进度和发送 | 演练通过不必然覆盖真实时序、取消和失败行为 |
| 客户状态有多处解释 | reply_planning、silence_planning及尾问逻辑分别处理missing_slots、阶段、联系方式；沉默规划仍判断“未确定”等文本值 | 后续节点可能忽略前轮决定，新增规则需要改多个地方 |
| 知识存在但不一定可用 | 服务文件、线路事实、固定回答与官网检索分别存在；曾出现未选线路时service事实被过滤 | 页面看到的知识和实际可检索内容不一致，按前缀过滤易漏项 |
| 不同话术来源会互相覆盖 | 固定回答、生成文案、首轮审核文本各有来源与路径 | 只改提示词无法修好固定原文，只改主线无法修好其他回答 |
| 校验兼做改写 | reply_generation._parse仍包含术语归一、追问句删除、转人工过渡语拼接、素材补绑 | 最终文字可能不同于最初生成语义；需要核验真正待发送内容 |
| 审核与核验状态容易混淆 | 固定回答路径把fact_verification_passed设为true，但并未运行在线事实核验 | 看报表会误以为模型独立核验通过，证据不准确 |
| 发送计数与触达计数不清晰 | 消息数、图片数、主线多段发送、每日主动触达处在不同配置层 | 运营难判断一个节点会产生几条消息，易把首轮介绍当多次追销 |
| 测试和业务体验脱节 | #1056及#467出现后续主线衔接问题，技术检查仍通过；旧验收与新复测结论不同 | 通过率被误当成业务完成度，缺少可追溯的逐项验收 |
| 交付文档漂移 | 多份历史文件分别宣称完成，后续又发现缺口 | 运营、研发和业务使用不同的当前状态 |

上述为已读源码与已有结果支持的判断。沉默旧正文拼接的具体入口仍需完整追踪，不仅凭截图断言是某个提示词导致。

## 4. 目标架构：一个接待协调器，两个执行环境

```text
客户消息 / 首轮下一段到期 / 沉默到期 / 控制变化
  → 事件去重和会话版本检查
  → 接待状态快照
  → 客户理解（仅新客户消息需要）
  → 统一接待规划器
  → 版本化事实、固定回答和素材解析
  → 可持久化的本轮消息计划
  → 原文渲染 / 受限文案生成
  → 最终内容与发送合同校验
  → 逐条发送前门禁
  → 实际发送记录及状态推进
```

真实环境用Chatwoot发送适配器；演练用模拟发送适配器。两者执行同一份计划和状态迁移。定时任务只是触发入口，不重新决定业务话术和追问。

在现有单体中增加协调层并渐进迁移，不先另建数据库、事件总线或通用工作流平台。旧EvaluationDecision暂时仅作为接口适配对象，不再继续扩充它承担新的业务状态。

## 5. 统一状态与计划合同

### 5.1 会话状态

- control_state：自动接待、暂停、转交中、人工、停止。
- route_selection：当前确认线路、候选线路、待确认切换和产品版本。
- customer_profile：每个字段保存状态、值、原文证据、来源消息和更新时间。
- question_history：问过什么、何时实际发出、是否回答、未定或拒绝、何时可再问。
- content_progress：按线路、内容版本、内容条目保存完成状态；品牌问候等按全局范围记录。
- lead_state：未邀请、已邀请、已提供、格式待确认、已交接，另记邀请原因及拒绝意愿。
- pending_plan：当前计划、消息代次、已送部分和剩余部分。

人数字段采用明确值或范围结构；日期采用unknown、known、undecided、declined等状态，不再用“未确定”字符串充当日期。先迁移读取兼容，不能直接抹掉历史证据。

### 5.2 本轮计划

本轮计划明确：触发原因、客户待答问题、业务动作、当前目标、内容来源版本、按顺序排列的消息、唯一互动问题、恢复条件和停止条件。

每条消息有稳定ID、类型、来源内容条目、附件哈希、前置条件和间隔。追问可以明确为none，并保存原因；执行层不得将none解释成“根据缺失字段再生成一个问题”。

复杂度控制：优先在现有Journey和Job上增加版本化JSON及必要索引。只有现有Outbounds不能表达独立计划条目时才新增计划/条目表，不为每种状态建表。

### 5.3 完成与去重

- planned不等于submitted，更不等于delivered/read。
- 图文组合必须按本组要求的图、文分别登记；只发图不能自动判定介绍完成。
- 不因一个通用事实被引用就把酒店、车辆等多个组同时覆盖。
- 内容条目完成、客户理解内容及用户阅读是不同概念；没有渠道阅读证据不能写“客户已看”。
- 同图跨线路使用内容哈希去重；文案完成度按事实/用途单元记录，不只比较句子是否一样。
- 客户主动要求重发可建显式重发动作；自动流程不得自行开启重发。

## 6. 客户实际会得到的流程

### 未选线路

发送运营配置的开场消息组及一次清晰选择，不发两条线路的详情图。客户直接问公司、医生服务、手续或付款时先回答，不强迫先选线。后续无新价值则停止，不反复推两个按钮。

### 选线后的首轮

按业务勾选的内容顺序逐条发送：简短问候（已经问候则跳过）→ 4至10人公司定位 → 桃花图与介绍 → 对应行程图和卖点 → 希尔顿 → 11日绒布 → 车辆及设备 → 一个互动问题。

默认间隔2秒，沿用可配置范围。调度依据上一条提交成功时间，尽量维持顺序；Chatwoot提交成功不等于社交平台恰好2秒到达，不对客户承诺精确显示时刻。

首轮短时连续介绍与客户沉默后主动触达是不同类型。首轮本身仍需总消息量预览及发送预算，但不能把每张图都计成一次沉默营销触达。

### 客户插话

收到新入站事件即使旧计划失效，停止未提交消息；已送内容不回滚。先回答当前问题，然后根据同一状态恢复剩余内容。图片已发、说明未发时，只补适当说明，不重发图片。

直接价格问题不再等待介绍完才答。客户表达不适或紧急风险时暂停营销内容；一般行前用药咨询可以回答后自然介绍，但是否继续、最后问什么由一次规划决定，不由尾问执行器自行追加。

换线取消旧线路剩余计划，保留通用人数、日期及已发通用素材。只清除或切换线路专属进度；模糊提到珠峰不直接改选。

### 需求与留资

不把“问齐人数日期”作为目标。已提供价值、客户希望完整资料或后续沟通时，可以邀请一种联系方式，或给两种选择。问过未答与明确不知道分开处理。

计划未定就往下一项价值推进；客户主动补充日期才更新。明确拒绝留资后不反复要，客户愿意继续问产品仍正常回答。只有确实存在且可发送的文件，才用“发完整文件”作为理由。

### 沉默

沉默计时锚点明确显示为“上一轮计划最后一条成功提交后”，同时独立计算渠道允许窗口。旧配置若含其他锚点，迁移预览实际时间，不默默改变原节奏。

主线未完成，选下一项；主线完成，选已批准的景点或有用途的补充；仍无新价值，最多一次有实际帮助的文字收尾，然后停止。时间节点是允许检查的机会，不是必须发满的配额。

客户回复不会清空累计触达和已发历史，从而不能通过不断重置轮次无限触达。每日次数、消息总量、发送时段、拒绝联系、人工状态和渠道规则同时生效。

### 人工接管

保留现有先建任务/打标签、仅当前终止任务发承接说明、最后移除ai的受控流程。普通AI和SOP立即阻断。投诉、退款、合同争议不附营销内容。

增加客服可见待办、原因、人数/日期/线路摘要、客户原话及已发资料，明确任务接收人。验证任务创建失败、标签移除失败和发送未知时的告警，不把“数据库里有一条记录”当成交接完成。

4至10人是公司服务定位，8人是当前转人工阈值，两者不冲突。特定车型及报价不能从品牌人数范围自动推导。

## 7. 统一内容与知识，不让业务维护事实ID

### 7.1 一份内容，多种用途

统一内容资产结构：ID、作用范围、主题、适用条件、批准文本、结构化事实、图片/视频/文件、使用模式、来源证据、版本及状态。

三种使用模式：

1. 固定发送：业务批准的客户原文逐字发送；图文顺序保持配置。
2. 受限表达：只根据指定事实与素材叙事生成短回复。
3. 待核对：不进入自动回答，只在后台显示缺口与来源。

官网原始HTML和原始话术作为不可变来源留档；只有一份“客户实际收到的批准内容”，不让运营同时维护两份几乎一样的文本。修改原文后标为运营批准，并保留来源差异。

主线、固定问答、沉默节点引用相同内容资产，而不是复制相同文案到三处。发布编译器可生成旧线路包/SOP结构以兼容执行器；编译产物不再由运营手工维护。

### 7.2 来源与适用范围

- 全局服务：公司品牌、服务方式、一般手续/付款/健康边界。
- 线路事实：该线路价格、团期、酒店、车型、景点及费用。
- 后台规则：转人工阈值、留资偏好和触达规则。
- 原始官网与历史顾问聊天：证据和话术样本，未经审核不直接成为事实。

已批准业务文件是业务内容的权威更新来源，不因旧网站仍写旧口径就一再要求确认。只有文件未给出的具体数字、范围或存在安全边界时才说明不能推导。业务优先不等于将个体医疗结论或效果保证自动发布。

选择事实依据领域和适用条件，不依靠web./service.前缀决定准入。固定答案与素材同步校验版本依赖，事实修改时提示哪些问答和主线受影响。

### 7.3 官网与健康资料

将现有service知识纳入同一后台可见、可审核模块，消除运行文件已加但页面看不到的情况。迁移时保留已有使用范围，不意外将演练限定资料放到真实环境。

更新资料按钮继续禁用，直到抓取、编码、页面范围、变化对比和审核闭环通过。公开页面与受保护页面均限授权域名和SSRF边界；遇访问验证不能绕过，允许授权浏览器采集后导入来源快照。

以文字模块为主：公司与服务、手续、付款及费用规则、交通住宿、行前准备、健康与就医协助、联系渠道。全站抓取不等于全站启用：具体线路、过期资料、重复导航及风险说法分开归档。

新增/变化页面产生候选版本，不自动覆盖已发布内容。图片不经审核不升级为正式素材。高原注意事项文件必须真实存在、经过内容审核和下载检查后才能成为留资后的交付资料。

### 7.4 固定问答准确性

先识别问题主题、限制条件和否定，再检索可用答案；直接命中后逐字渲染。多主题问题可以组成多个明确答案块，但不把无关整段旧脚本拼到新话题。

范围不符、多个冲突候选或缺少事实时不强行套固定答案。保留疑难问法用于下一次审核，不承诺任意自然语言99%或100%准确。固定文本保持率可以100%，意图匹配率必须在独立数据集上测。

## 8. 提示词与文案层

- 理解节点保持客观结构化，使用繁体说明但不要求“软萌”提取结果。
- 客户可见生成节点使用台湾繁体、自然礼貌、短句；运营语气描述仅控制表达，不控制事实或门禁。
- 业务批准的固定话术不用模型再改；想改语气必须编辑批准文本，页面明确显示影响范围。
- 不主动强调技术身份，不冒充具名真人；客户直接询问身份时如实回应并可转人工。
- 只保留一套最终追问结构，正文不夹带多个隐含问题。
- 逐步移除改变语义的正则删句与拼接；结构和编码归一可以保留。内容不合格时有限重写，不能默默删掉客户答案再继续发。
- 核验对象是全部处理后真正待发送的最终文本与素材计划。业务事实安全和问题相关性分别记录，固定审核通过不标成模型核验通过。
- 失败链路有上限：固定内容可确定性发送；动态内容核验失败后有限重写，仍失败则阻止该回复并记录待办，不以营销内容顶替答案。
- 不每轮增加一个“风格评分模型”。先用批准样本、人工盲评和离线评测，避免为语气无限增加延迟。

## 9. 后台信息结构与配置生效

保留现有入口，做职责收敛而非再次全站改版：

- AI接待策略：开场消息组、顾问表达、互动/留资、沉默时间、人工规则与安全状态。
- 线路管理：基本产品信息、可增删的内容资产、首轮/后续顺序、固定问答、素材与版本。
- 全局知识：按大模块查看批准文本、来源、适用范围及引用记录，不展示一大段网页垃圾文本。
- 会话/演练：客户消息时间线与独立接待状态面板，能看到待发内容、最后一个问题、停止原因和版本。

所有可编辑控件必须满足：修改 → 保存/校验 → 发布版本 → 有效配置 → 计划消费 → 实际执行 → 追踪显示。不能生效或只为旧客户端保留的字段不伪装成可调选项。

发布前提供最终消息预览、预计数量和间隔、事实/素材缺口；数字限制单位明确为每条文字、每次回复图片、一次连续介绍总量、每日主动触达轮次。保存失败显示具体字段原因，不只显示422。

使用现有抽屉编辑器、列表、预览和组件样式，清理小字、遮挡和空气泡。文件加载失败、发送失败、去重跳过分别展示。禁用动作说明原因，不放可点但无效按钮。

## 10. 观测与验收证据

每次计划记录：会话/入站/事件ID、环境、产品/策略/知识/提示词版本、客户问题、语义证据、决策理由、允许及采用内容、唯一追问、最终消息顺序、每条提交与回执、取消原因、耗时与模型次数。

知识状态区分：未启用、未检索、无命中、命中未选、已选未发、已提交；不能把命中视为客户已经收到。

验证状态区分：人工批准原文、确定性系统通知、模型核验通过、核验失败、未运行。失败结果与重试结果都保留，不覆盖失败后只报最新通过率。

业务需求建立稳定编号：原文位置 → 配置/实现 → 测试案例 → 最近证据 → 当前状态。历史发布文档标明当时版本，只有一份当前验收矩阵。含客户隐私的样本权限隔离，分享报告脱敏。

运营指标：新客首答完成率、直接问题覆盖率、首轮中断/恢复率、重复问询率、有效留资率、拒绝/投诉率、人工任务接收率。观察客户回复只能说明相关性，不能直接把某句话标成“有效转化原因”。

## 12. 开发顺序与交付门槛

### 阶段A：冻结基线并补真实失败用例

保留当前运行版本和真实发送关闭状态。将#461、#467等原问题变成失败可复现测试，梳理已有状态/表/任务边界，确定迁移映射。创建需求编号及证据表。

交付：可重复的失败基线、状态合同、数据迁移方案。未通过基线必须保留，不能修改断言让旧实现“全绿”。

### 阶段B：统一规划、发送进度和执行入口

先提取共享规划与条目渲染，在演练中运行；真实链路先影子规划，只比较计划，不创建可发送任务。迁移首轮/尾问，再迁移沉默规划；移除旧路径的业务裁决权限。

交付：U01至U04、U12的核心能力；客户输入、时间和发送回执驱动同一个状态机。确定性取消、幂等和门禁测试全部通过。

### 阶段C：统一内容来源和运营发布

建立内容资产适配层与编译器，迁移两条线路、服务知识、固定回答及素材叙事，提供后台预览和来源展示。处理U05至U09、U11、U13；同期完成文件审核与顾问表达样本。

交付：运营一处修改，预览和实际发送一致；不能发布断链、缺图、超限或无来源的必发内容。

### 阶段D：人工闭环、观测和全量验收

完成U10、U14、U15；跑完整场景、浏览器和受控渠道测试，业务按矩阵签收。仅技术通过的条目不升级成业务完成。

### 阶段E：受控真实灰度

部署演练版仍保持真实发送关闭。业务复测通过后单独授权：先#26且有ai标签，随后少量明确标记会话。扩大前确认没有越权、严重错答、复读或交接遗漏。

每阶段独立可回滚。不把未完成的影子流程直接切成生产默认；不让新旧执行器同时拥有同一会话的发送权。

## 13. 迁移与发布安全

- 数据库做加法迁移，先双读兼容；影子计划可写审计但不可发送。
- 对每个会话明确唯一执行版本，已有待发任务按旧快照完成或明确取消，不在同轮混用版本。
- 内容修改影响新计划；安全停发/移除标签等控制对全部计划立即生效，不受旧版本豁免。
- 新入站将generation递增，旧任务在提交前核对；已交给渠道的消息无法撤回，不承诺绝对零毫秒中断。
- 标签移除与发送之间仍存在外部系统竞态，逐条新鲜读取、缩短间隙并记录时间，不谎称有跨系统原子事务。
- 发送状态不明先对账，不盲目重发；幂等记录与计划条目ID绑定。
- 转人工终止任务使用窄范围授权、有效期和仅一次完成状态；其他任务看见人工阻断立即停止。
- 回滚优先切回旧执行版本并取消新未发计划，保留已发生的发送/客户信息；有新客户数据后不得简单回滚整库丢数据。
- 备份代码、数据库和有效配置，部署/演练前后核对真实出站不变；灰度阶段则核对每条新增消息均属于明确授权会话。

## 14. 测试与验收方案

### 自动化分层

1. 单元/合同：Profile状态、唯一追问、范围人数、内容依赖、配置投影、知识范围和固定原文。
2. 状态序列：随机生成插话、标签变化、任务重试、进程重启和部分发送回执；验证不可越权、不能重复推进等不变量。
3. 适配器一致性：同一输入事件和时钟，演练与模拟Chatwoot适配器生成同一消息顺序、进度及取消原因。
4. 真实模型回放：保留现有68条历史基线，补充本次未覆盖问法；结果保存首试、重试和最终输出。
5. 全流程演练：每个适用场景包含实际消息记录、首轮发送、至少两个沉默节点或到终止；不得只检查模型返回对象。
6. 桌面/移动浏览器：编辑发布、配置错误、图文/视频/文件预览、长图滚动、去重与加载错误、接管待办和日志。
7. 渠道集成：在单独授权的#26测试图片、视频、消息顺序、标签移除和回执。模拟不能替代实际渠道效果验证。

### 明确通过标准

- 门禁、幂等、错误线路图、转人工后普通AI发送：测试集零违规，任一失败阻断发布。
- 固定原文、消息顺序、最后唯一互动问题：适用批准场景100%符合配置；例外必须是显式安全/取消原因。
- 日期未定后重复问日期、同一自动图片重复、沉默复制旧正文：定义场景中零发生。
- 所有直接问题在回复中已回答或明确指出哪一项需核对，不能以转介绍掩盖未答。
- 业务文档每项都有明确结论和会话证据，未完成不隐藏在总通过率内。
- 台湾语气及衔接采用业务人员盲评：初始建议至少60条覆盖即时、固定、沉默、交接，至少两位评审，90%以上达到4/5且无严重答非所问；评分标准在跑测试前确认，不事后放宽。
- 性能先记录当前固定/生成/核验P50、P95及失败率，新版不得未经说明显著退化；具体秒数以部署环境基线确定，不凭空承诺响应时间。

上述是受控验收集的目标，不表示所有未来对话100%正确。没有客户数据和对照实验时不承诺提高多少留资率。

## 15. 给业务的最终效果说明

客户看到的是同一位顾问连续接待：简短开场，选线后顺序看图文；一提问就先回答；已知或未定的信息不会被反复追问；介绍完成后只推进一个动作；沉默时得到新的相关内容，没有内容就停止；愿意留资或需要人工时，资料和责任交接完整。

运营看到的是一套可预览、可发布、可追溯的内容和流程，而不是多处相同文案；研发维护的是一个接待计划及执行合同，而不是多个模块互相补规则。

实施前无需业务重复确认文档已经明确的口径。真正需要共同完成的是固定文案/文件审核、语气评分和灰度验收，不是把系统执行缺口转嫁成需求不清楚。
