# 架构改进第一轮交付记录

## 实施结果

沿用单体业务服务、Chatwoot Cloud、中继和 SQLite。本轮改动集中在正式执行可靠性及模块边界，没有引入新框架或修改业务报价、模型提示词。

| 审查发现 | 本轮处理 |
|---|---|
| 正式进程没有消费通知及超时任务 | 独立维护执行线程持续消费，与 AI 生成解耦 |
| 手机通知仅有一次性测试 | 新增正式 Chatwoot 私密提及渠道及设置页面，保留 Webhook 渠道 |
| 单个客户拖住其他工作 | 默认最多两个会话任务并行，同一会话的回复与 SOP 串行 |
| 持续回复积压可能使维护任务饥饿 | 维护独立调度；回复和 SOP 按到期时间竞争执行名额 |
| 过期消息缺少人工兜底 | 激活后未回答的过期消息建立 P1 人工任务，不自动补发 |
| 演练心跳掩盖正式进程停止 | 按职责检查必要心跳，增加 readiness 503、队列年龄和通知失败计数 |
| 执行层依赖 API/旧进程 | 提取 `chatwoot_service`、`conversation_mirror`、`notification_dispatch`、`runtime_health` |
| 私密通知回调可能覆盖人工状态 | 活跃人工任务优先，镜像消息不重新启用本地 AI 状态 |
| 测试继承本机正式配置 | 导入应用前强制测试环境、禁写和独立内存数据库 |
| 测试断言落后于现有业务版本 | 同步话术/规划器版本，以及已批准的标准六人团定价断言 |

## 发送与并发约束

- Chatwoot 手机通知只发私密备注，并要求 AgentBot 身份回执，避免顾问自我提及导致漏提醒。
- 私密备注可以在客户“全局停发”时提醒顾问；环境级禁写和演练禁写依然生效。
- 发送意图先入库。私密通知结果不确定时标记 `submission_unknown`，不能自动重复发送；Webhook 带稳定幂等键并按原有上限重试。
- 原有客户发送前二次检查、人工接管、资料批准、渠道窗口和回执保护仍保留。
- 并发名额在单个进程内管理，SQL 原子领取与单机文件锁继续保留；不支持通过多个正式进程共享 SQLite 扩容。
- 手机提醒依赖实际顾问、机器人、App 权限与通知偏好。本轮未改生产设置，也没有重复向真实顾问或客户发通知。
