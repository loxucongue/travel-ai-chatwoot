# V2 代码架构与业务要求复核

复核日期：2026-09-20。结论：V2 已有可用的问答、事实工具、素材选择和受控交付基础，但尚未达到最初约定的完整状态编排、可持续沉默唤醒和全量业务验收要求。适合继续隔离演练，不应据现有通过记录宣布全面达标。

本次只做审查与测试，不改生产配置、不部署、不发客户消息。审查重点为自有后端、V2、共享交付与调度、运营配置、前端相关入口及中继关键边界；不声称逐行审完第三方 Chatwoot、依赖包或完成渗透测试。重新读取 AI.docx、AI(1).docx、AI(2).docx 正文；截图相关细项结合之前的逐图复核记录。本轮未重新逐张检查所有旧截图。生产实际运行版本和真实渠道收件效果未验证。

依据：原始 V2 共存方案、三份业务文档、9月15日业务复核、9月20日整改记录及原始模型输出、当前代码和本轮离线检查。原始文档中新旧冲突按最新明确反馈处理：行程图先于风景照片；普通首次沉默约一分钟。AI(2) 的“针对问题回答”不意味着新客完整介绍的所有旧要求自动作废，应区分首次索要完整介绍与后续单点追问。

**实际架构与评价**

渠道事件经中继和后端进入持久化任务；会话选择 V1 或 V2。V2 把近期历史、客户资料和旅程摘要提供给主模型，预载通用/线路 Skill，由模型调用事实和素材工具，再生成结构化决策。决策经过结构校验、素材约束、事实核验和有限重写，交给共享留资、人工交接、交付计划及发送保护。沉默任务先检查资格，再复用 V2 决策。

优点是模型没有直接发送权限，产品事实和素材有受控入口，版本切换会取消旧任务，渠道发送还有最新状态、人工接管、幂等和不确定送达保护。应保留这些设施。

不足在决策与状态层：模型给出的阶段标签缺少语义证据约束；“未解决问题”没有形成完成闭环；主动跟进仍由关键词与少量固定候选决定；业务规则分散在主提示词、Skill、Python、产品包和旧话术中。整体更接近具备工具的两线路接待 Agent，尚不是完整的业务旅程编排系统。

**需要优先处理的发现**

1. **P1：阶段转换缺少事件依据，错误状态会停止有效跟进。**

   `backend/app/reception_v2/journey_state_machine.py:23` 对所有非终态开放全部阶段；`guard_decision_stage` 只校验转换集合，没有检查客户是否真的要求考虑、是否确实留资或是否存在交接任务。历史真实模型回放 `output/business-feedback-20260920/multiturn-final.json` 中，`ask_meeting` 的输入是“那在哪集合呢？”，却写入 `considering`，且 `structural_issues=[]`。

   `proactive_policy.py:44` 将考虑状态直接判为不跟进；`runtime.py:320` 映射为 skip。因此问集合可能意外变成停止本轮唤醒。此次离线调用也确认，从 value_building 提交 considering 不会被阶段校验拒绝。

   需要让语义理解输出有客户消息证据的事件，服务端按事件更新状态；产品问答不能无证据改为“客户需要考虑”。应保留自由跨主题能力，不能退回按关键词强锁销售漏斗。

2. **P1：第二次正常唤醒时间与发送窗口冲突，延后也会消耗节点。**

   `backend/app/reception_config.py:357` 固定间隔为 `[1, 1440]`，后续节点基于前一节点。正常无新回复且没有 defer 改写时间的路径下，第二次至少约在登记后1441分钟；`backend/app/live_sop.py:128` 在最后客户消息后1435分钟关闭自动发送窗口。因此正常第二次节点到期已无法发送。不能通过删除窗口保护来修复，应让计划在渠道可用条件内可执行，无法自动联系则明确结束或转人工待办。

   `live_sop.py:926` 将 defer 的当前节点标为 skipped 并推进后继，再改后继时间。最后节点没有后继时无法真正延后复评。`considering` 又在进入模型前被一律 skip，不能表达“先讨论，明天下午联系我”与“不要再联系”的区别。

   需要持久化约定联系时间、等待原因、复评时间；defer 重新安排当前意图，不能等同消耗一次跟进。

3. **P1：运营配置与 V2 实际行为脱节。**

   前端 `frontend/src/pages/AiReceptionStrategy.tsx` 提供开场、语气、自定义要求和跟进间隔。V2 的 `runtime.py:123` 组装消息时没有读取运营的 reception_policy 配置；本轮把开场和 custom_guidance 从甲改为乙，生成的模型消息完全相同。

   V2 调度在 `live_sop.py:223` 和 `automation_service.py:1360` 使用固定的 v2_silence_intervals，而非界面发布的间隔。不是所有配置都失效：发送开关、时段等仍在共享执行层生效。但界面没有把这些作用范围区分清楚。

   需要明确 V2 支持的配置契约、传入决策/交付层，并让界面显示生效引擎和版本；不支持的选项不能让运营误以为已生效。

4. **P1：旧业务要求没有完整进入 V2 的事实检索结果。**

   本轮直接调用 get_route_facts：price 返回9,980元/人、包含不含和范围，没有“6人小团9980起”的完整限定，也没有返回已存在的多人优惠事实。hotel 返回“除地区条件有限的住宿点外”，没有明确业务要求的珠峰、波密例外。有效资料源为 `data/knowledge/china2go/route-packages/peach-9d-2027/route-package.json`；不能只看 backend/data 中未必生效的同名包。

   多人优惠事实已存在于有效产品包，线路 Skill 也提到它，但 `backend/app/reception_v2/tools.py:80` 的定向筛选未将该事实纳入普通价格主题；这属于资料选用断层。酒店事实本身也需要补全。仅增加“说得更自然”的提示词不能解决事实缺失。

   修复应统一已批准业务事实，并建立主题到相关条件、例外、优惠事实的映射；公司4–10人定位与特定报价/车型适用人数必须保持区别。

5. **P1：沉默候选仍受关键词硬门禁限制，问题解决记录不可靠。**

   `journey_memory.py:25` 将识别到的当前主题直接写为 unresolved，不判断上轮是否已经答完；`route_profiles.py:19` 每条线路仅有四个候选。本轮探测发现，“多少钱”即使历史已经回答价格及不去珠峰/纳木错，缺少内容组记录时仍将 scope 作为新价值；“还有什么好玩的”“布达拉宫”识别为 general，无法获得候选。

   单轮问答的 Flow 关键词已经降级为提示，这是进步；但主动跟进仍会在模型理解之前被词面匹配挡住。布达拉宫、八廓街、扎基寺的独立文化介绍，并未成为该候选体系中的完整跟进路径。

   应记录带证据的问题、答案、是否解决和实际提供的事实；候选选择依据客户目标与已交付事实，不要求恰好命中少数字词。

6. **P1：行程必须交付的约束仍依赖模型自报意图。**

   `runtime.py:267` 缺少 delivery_intent 时默认为 none；`runtime.py:297` 仅在该字段为 itinerary 时补全交付。离线检查中，即使客户请求行程且素材可用，模型没有该字段时，执行约束仍保留空素材列表。

   已测几个真实模型表达确实选对了素材，不能据此推断所有表达都受硬约束保护。需要将客户请求识别为独立、可验证的交付义务，最终检查是否已计划交付、此前已交付且无需重发，或明确交人工处理。资料缺失时也要有可见的处理结果，不能只抛异常。

7. **P1：当前业务验收脚本不能作为全量上线门禁。**

   `backend/scripts/evaluate_v2_business_feedback.py:124` 记录 verified 却没有将核验失败统一加入验收失败；检查主要为素材、非空回复、少数越题词及 silence action。年龄边界、报价限定、多人优惠、酒店例外、客户阶段正确性等没有完整业务断言。末尾捕获错误并写结果，没有以失败退出码阻止流水线继续。

   多轮测试将计划素材模拟记为送达，适合测决策连续性，不等同真实接收验证。24项汇总来自各场景最后复测的不同批次，也不是最终同一个冻结发布版本下的一次完整验收。已有结果可以证明局部改进，不能证明三份文档全部满足。

   应建立“原文要求—场景—状态—回复—素材—时间—交接结果”的验收表；关键失败必须使门禁失败；每次记录模型、代码、Skill、产品包和配置摘要。增加复述、否定、省略追问、话题打断和多条件组合，不能只测试原句。

8. **P2：Skills 已落地，但新增线路仍需多处改代码；快回复目标缺少证明。**

   主提示词 `runtime.py:83` 继续堆积桃花产品的具体约束，工具枚举 `tools.py:28`、线路预载映射、route_profiles 等处硬编码两条线路。新增产品不是增加一个已批准产品包和 Skill 就能接入。

   主模型最多多轮工具交互，通常还串行调用事实核验，必要时重写再核验；`runtime.py:201` 有单次超时，没有整个回合的总耗时预算。历史24项有效回答耗时中位数约11.64秒、最大26.22秒；这不是本轮性能测试，也没有同条件 V1 对照或足够样本的 P95。不能据此认定“比原来快”或“达到体验很快”。

   应将产品特定规则迁回已版本化产品包/Skill，由注册表生成工具能力；在不削弱事实保护的前提下，按实际调用链减少冗余调用，设置总时限并做同场景性能比较。

**建议收敛顺序与上线条件**

第一步先修状态事件、约定联系时间、defer和窗口冲突；否则单轮文案再好也会丢失后续接待。第二步统一事实来源并补齐价格、酒店、文化跟进和附件，打通运营配置。第三步补上独立交付义务和完整介绍计划。第四步把三份文档逐项变成业务验收门禁，在同一冻结版本下做多轮、打断、改线、考虑、拒绝、留资、人工交接与故障场景，再比较速度。

不建议再做一轮无边界的大重构，也不建议继续逐句增加主提示词补丁。保留发送与交付设施，集中修上述有证据的断点。

上线判断应以关键业务项零失败、同一发布版本可重放、真实模型重复测试记录、模拟渠道完整执行及明确性能目标为依据；人工通知和真实渠道链路的验证必须与“不向真实客户发测试消息”约束兼容。当前尚不满足全量业务验收结论。

**本轮验证记录**

- V2专项：60项通过；前端现有测试：1项通过；中继测试：5项通过；前端TypeScript编译通过。
- 离线直接检查：错误considering阶段被接受；该阶段阻断唤醒；漏报交付意图时空素材保留；正常第二节点1441分钟晚于1435分钟窗口；已回答主题仍作为未解决主题；运营开场/custom_guidance变化未进入模型消息；有效价格/酒店工具返回存在上述资料缺项。
- 本轮没有重新调用真实模型；真实模型回复和耗时引用9月20日原始结果，明确属于历史证据。
- 本轮全量后端回归：1166项通过、4项跳过、13条依赖/迁移配置弃用警告，耗时460.93秒。专项60项与全量集合重叠，不能相加作为独立测试数。通过说明已有断言成立，不会消除本次已复现而未被业务断言覆盖的缺陷。
