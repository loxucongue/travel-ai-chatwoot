1. 整个系统怎样分工

这是一个“资料和计算提供事实、模型理解和组织回复、程序执行动作”的系统。它不是一个接上模型就自动聊天的单体程序。

Facebook / LINE / Instagram↓Chatwoot 汇总会话↓API 接收与记录事件↓接待引擎：读上下文 → 理解意图 → 取资料与核价 → 生成回复计划↓Worker 执行文字、图片、标签、跟进、内部转人工↓Chatwoot 返回发送回执，写入数据库与运营记录
组成通俗解释实际职责
线路包每条产品的资料夹价格、季节、FAQ、图片索引、介绍顺序、跟进配置。
Skill给模型的接待工作指引什么时候介绍，怎么回答，哪些条件需要核算，怎样简洁承接。不是训练模型权重。
模型理解客户的接待人员理解“改成六位”“先比较”“不用再问月份”，选择合适事实、模板和动作。
执行引擎负责落实的操作员排队发送、取消未发送项、记录状态、加标签、建立顾问任务、防重复。
SQLite 数据库工作记录本会话历史、客户资料、配置、模型运行记录、待发项、发送状态和顾问任务。
管理后台业务与运维操作台线路配置、公共接待、渠道启停、知识资料、顾问规则和运营指标。

2. 一条客户消息，从进入到回复

  1. 收消息并去重。Chatwoot回调进入系统，记录消息ID、会话、收件箱、文字或附件。重复回调不是一条新咨询。
  2. 确认当前谁在接待。核对全局发送开关、渠道AI、会话标签、人工接管、拒绝联系和渠道发送权限。这是执行权限，不是判断模型答案好不好。
  3. 读取客户卡与已发生的对话。客户卡保存人数、日期、偏好和联系方式；已发送的文字/图片才算客户看到。草稿和失败消息不能冒充已沟通。
  4. 专用语义模型理解这一轮。区分选线、询问、比较、拒绝、致谢和歧义；看最近历史及本轮连续消息，用原话证据定位。正常询问不该强迫选线。
  5. 准备事实。加载公共指引与涉及线路Skill、路线包和素材；需要时调用报价、日期、旅行天数计算等工具。价格计算与客人表达方式分开。
  6. 生成结构化计划。模型不只是返回一句话，还返回回复/等待/交接、线路、文字或模板ID、图片ID、客户卡更新、是否中断旧介绍、跟进节点。
  7. 记录并执行。程序展开模板和素材，建立待发送队列。若客人改线或人工接管，取消尚未发送的旧内容；已经发出去的历史消息保留。
  8. 发送前再次核对权限。防止模型生成期间顾问已接管、客户拒绝联系或渠道窗口关闭。检查消息幂等键，避免同一条提交两次。
  9. 收回执。submitted、sent、delivered、read不同。请求成功不等于客户已读；回执不明确时不能盲目重发。

“一个回复”可能含数条文字和图片，也可能需要多次模型调用。模型完成时间、第一条消息提交时间、整套介绍发完时间，不应混作同一个耗时指标。

客户行为系统做法为什么
“西藏不去了，改看北京五天，先介绍。”选择北京，停止旧的未发介绍，开始北京介绍。客户明确要求改变介绍对象。
“顺便比较北京多少钱，还没决定换。”保留西藏主线，记录北京为讨论对象，从北京取价，不自动播五日。比较不等于同意换线，更不等于报名。
“明年三月呢？”更新当前对话的月份，继续原线接待；核对原产品季节是否适用。补月份本身不代表选另一个产品。
原产品不适用，存在符合明确限制的替代产品按已配置业务指引，模型可以说明差异后直接介绍替代线路，不再多问一句“要看看吗”。不把客户挡在介绍前。但不能冒称客人已确认出发或报名。
对多个候选只回“好”确实无法确定对象时问一个简短确认问题。不能猜最后提到的产品就是客人选的。
“北京只包车一天，不要五日。”定制咨询，了解需求与安排顾问；不套标准5日价格/介绍。有北京咨询能力不等于只有北京5日一种需求。
半技术说明：系统保存的几个不同字段
  • route_variant：当前运行或介绍的产品。
  • route_choice：unchanged保留、recommend讨论推荐、selected选择介绍对象。
  • profile.discussion_route：正在讨论但尚未正式切过去的另一条线。
  • _route_dialogue：最近语义理解结果和证据。
  • introduction_route、待发队列：目前介绍进度，防止把两套介绍串起来。
  • beijing_request_kind：本次北京咨询类别，不等于选中北京五日产品。

仍有架构债务：业务允许“直接介绍合适替代线”后，route_variant也承担介绍目标的含义，不能在报表里把它直接当成购买意向或成交选择。未来应把“当前介绍产品”和“客户明确选择产品”彻底拆开。

上传ZIP、文档或网页不等于立刻生效。必须经过提取、对照来源、绑定到正确线路、配置启用、素材可解析、加载进本轮上下文，以及模型与执行测试。网页后续改动也不会自动变成模型已知，更不是重新训练模型。

北京目前使用6档已计算成人价格：淡季2–3位5780、4–5位5580、6位5380；旺季对应6280、6080、5880。模型不应把西藏“独团加价/早鸟”再扣到这些最终金额上。儿童、1位、7位以上或非5日等未明确标准的情况另行核算。

西藏采用另一组经业务确认的结构化规则。例如基准10480时，4人独团10480+400−200=10680；4人拼团10480−200=10280；6人独团10480−400=10080。这里是说明计算机制，不是说所有西藏月份都用10480。

5. 哪些能配置，哪些配置了也不一定生效

位置/层次可调整内容生效条件
线路配置 /products产品资料、价表、介绍段落、素材及相关产品字段线路已启用；运行包校验通过；没有更高优先级运行配置覆盖。
公共接待 /ai-strategy语气、公共接待目标、素材规则、跟进设置当前V3实际读取该字段。旧版本遗留字段不能仅凭页面可保存就认定生效。
系统设置 /settings渠道AI、标签映射、顾问通知、连接配置还需满足全局发送开关、会话接待状态、渠道权限。
顾问分配 /advisor-assignment参与分配人员、触发条件、固定/轮流策略通知名单和分配名单是两套职责；通知某人不代表把会话分配给他。
知识资料 /knowledge业务来源与服务资料要被当前知识版本及产品加载链路引用，不能只存了文件。
专属Skill与线路包配置业务流程、示例、条件、价格适用范围部分复杂字段仍需开发发布，不是后台都已有完整编辑入口。

不适合做成任意业务开关的东西：消息幂等、数据库事务、并发任务租约、回执核对、发送权限、损坏引用处理。这些是系统能否正确执行的基础。可以设计受控参数，但不能让业务随意关掉，否则会重复发消息或冒充发送成功。

保存成功但没按预期执行的常见原因：改了未启用的线路；客户仍处在另一条主线；已有资料导致跳过问题；素材被停用/没有绑定；跟进被人工接管或拒绝联系停止；价格不适用于儿童/节假日；指引和另一处事实矛盾。遇到这种情况应查实际加载内容与执行轨迹，而不是再加一段更强硬的提示词。

6. 业务提出特殊场景时，我怎样改

  1. 先复原现场。找客户原话、前文、当时线路、人数日期、已发送内容、模型调用及发送回执。截图能说明表现，但不一定能说明失败发生在哪层。
  2. 把反馈变成可以检验的要求。例如“不要啰嗦”转成“改月份追问只说新价和差额，不重复包含不含”；“急件”转成“14天内定制被识别、写字段、真正加标签、内部交接，不误播标准介绍”。
  3. 定位哪一层有问题。资料错改资料；指引冲突改指引；计算错改前置计算；模型没理解则补最少必要上下文和示例；执行没落实则改执行映射。不能全部归因于模型。
  4. 从同类场景测试。北京这次同时测不同人数、淡旺季、儿童、节假日、单人、跨线比较、改线、包车、急件、已留资等；不能只拿一条原句通过就结束。
  5. 分层验收。配置/算术/素材检查 → 真实模型回复 → 实际渲染和动作执行 → 与线上原始代码做回归对比 → 持锁备份、精确发布 → 线上回读。
本轮例子根因修复层次
“3月6位”变成3月6日程序把人数当日期，并写回客户卡前置日期提取收紧：中文必须明确日/号；不明确的保留原话给模型理解。不是事后拦截回复。
急件有识别却没标签标签执行依赖标准产品已选中；一日包车没有选标准五日允许本轮更新的线路专属字段直接映射标签。只接受配置中唯一归属，不依城市关键词、不拿陈旧字段重复贴标签。
不占床被说成免房费把客人需求当作已确认计费规则补清资料边界，明确需要家庭核价；不编儿童优惠。
改月份仍回一大段首次完整报价和后续差异问答的指引混用让模型区分回答阶段；追问只答差异。没有用程序截断正文。
本轮实际输出：11月4位成人，每位優惠價人民幣5,580元，兩人一房，比8月每位少500元～

7. 主备模型、重试、转人工怎样工作

线上当前主模型是 deepseek-flash，备用是百炼 qwen-plus。配置字段仍有历史名称gemini，但实际备用供应商已经是百炼，不能仅看变量名字判定供应商。

  • 一轮处理通常先做线路语义理解，再生成回复；必要时读Skill、核价、读取素材会产生更多模型调用。
  • 一次调用优先主模型，主模型探测上限目前20秒。超时、HTTP错误、空输出、截断或不完整协议可切备用，仍共用总时间预算。
  • 主模型跨轮冷却目前0秒；下一轮会再尝试主模型。同一轮已经成功切到备用时，后续工具续写可继续备用，避免一轮中反复等待失败主模型。
  • 备用失败的冷却目前300秒；失败备用不能一直挡住已经恢复的主模型。
  • 线路理解节点最多修复3次，无法确认时降级，让后面的回复模型直接读原始上下文继续答，不因这一辅助节点失败就直接转人工。
  • 回复计划中的结构/素材引用无法定位，仍需修正，因为程序无法发送不存在的图片或模板。这不是用正则评判答案语义正确与否。
  • 整轮未完成的客户回复会有限重试，当前最多3次；持续无法生成可执行回复才异常转人工。可选的沉默跟进失败可跳过本次，保留AI接待，避免制造大量无意义转人工。
  • 业务转人工还包括客户明确要求、需要人工核价/确认和配置要求；渠道失败或回执不明属于发送问题，换模型未必能解决。

线上代码保留了一些旧的语义检查函数，但不能看到函数存在就说它仍在拦截。当前主生成路径没有再调用旧的route_choice语义否决；仍有真实存在的执行权限、协议引用、素材规则撤销和渠道回执控制。转人工动作本身采用内部交接，不发送模型附带的告别段落。

慢回复不只取决于模型：连续消息合并等待、前置语义节点、约十万token级别上下文、工具续写、重试、队列节奏和渠道回执都占时间。本轮12段隔离回放为7.39–26.17秒，不能作为线上客户端P95。全量线上耗时查询本次未取得完整结果，不编造统计。

9. 更上层的改进方向

优先级应该由实际风险决定，不应不断堆叠“遇到这句话就怎样”的特例。

  1. 事实只维护一个权威来源。价格、儿童规则、季节边界不要散落在多个相互冲突的提示段里；按产品适用范围组织。
  2. 彻底拆分当前介绍、讨论候选、客户明确选择和定制咨询。本轮先修了定制标签依赖标准线路的问题；完整状态字段重构仍需跨线路验收，未在这次顺手大改。
  3. 减少模型每次无关资料输入。当前会同时附带多线路事实，有大上下文与重复风险。应该在不遗漏比较路线的前提下精确取相关资料，先做质量与时延对照再替换。
  4. 建立长期场景集。每条反馈先归为价格、时间、切线、资料边界、交接或执行问题，沉淀变体与反例。测试同时看数字、表达、客户卡、队列和回执，不能只看回答字符串。
  5. 运维统计要轻量化。数据库增长与重查询本次已显露压力；应单独优化日志保留、聚合指标和索引，避免后台统计扫描大量模型上下文。本次没有仓促删除历史日志或大表VACUUM。

这些方向是后续架构改进，不等于已经全部完成。已经完成的改动、测试和上线范围以本报告首段与发布清单为准。
