# #572：确认线路后接待中断

## 原始问题

正式演练 #572 的消息为：客户“你好，我想咨询旅行行程”→配置开场与选线图片→客户“桃花+珠峰11日”→仅收到“預計幾位一起去？”。运行2124已经正确绑定11日，运行2125沉默处理也没有发介绍。

这次不是线路识别失败。`runtime._prepare_route_introduction` 在人数未知时把模型回复替换为短问句，并提前返回；两条线路 Skill 同时要求“等待回答，不同时开始介绍或发图”。此前把“先问人数”实现为“没有人数不能介绍”，造成接待中断。

## 参考原文及取舍

重新读取用户指定的 `output/chatwoot-transcripts-20260927/transcripts.json`：297段会话，提取293个线路接待片段，人工查看相关开场及后续原话。

- 会话7：客户发9日广告名称，接待询问人数后继续说明小团、发送行程图和桃花介绍。
- 会话8：客户发11日广告名称，接待问人数后继续“我先將行程圖發您～您可以看看”，再介绍11日景点。
- 会话31：客户发11日广告名称，后续接待继续介绍公司、桃花秘境和酒店。
- 会话32：问人数后继续品牌介绍、“我先把行程傳給你看”和林芝低海拔安排。

因此人数是逐步收集的信息，不应阻挡线路资料。参考的是这组完整接待动作和有用的衔接方式，没有照抄顾问姓名、旧价格和所有销售承诺。导出文件本身注明发送者归属限制；很多记录为unknown，不能声称每一句都经证实是人工撰写，更不能把测试会话26当作人工范例。

## 修改

- 删除人数为空时覆盖整条回复并直接结束的代码。
- 模型根据客户意图选择完整介绍：确认线路正常开始；客户明确暂不介绍、仅比较或仅问单项时保持答疑。沿用已有 `delivery_intent`，没有新增审批或审核模型。
- 两条线路 Skill 去掉等待人数和等待一分钟的阻塞说明。人数已知走原有分支，未知使用配置中的 `entry_question` 作为第一段，后续继续行程图和主体介绍。
- 两份线路配置同步更新 `entry_question` 与对应场景话术，后台内容仍是唯一可编辑文案来源；没有把客户文案硬编码到运行函数里。
- 保留介绍期间普通问题排队、停止/改线/人工中断机制，已交付的介绍不因客户补人数重新发送。
