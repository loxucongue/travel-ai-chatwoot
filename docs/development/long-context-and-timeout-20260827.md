## 2. 完整历史的定义与实现

真实回复在生成前执行以下只读流程：

1. 查询当前会话与联系人。
2. 查询同一 Chatwoot 联系人的会话，只纳入同一授权 Inbox。
3. 对每个会话按 `before` 游标持续读取，直到返回有效空页。
4. 以本轮第一条客户消息为时间截点，只使用该消息之前的公开客户及顾问消息。
5. 将完整历史、当前问题、已确认记忆、线路及审核素材目录一起传入 DeepSeek。
6. 生成后再次读取最新客户消息、标签、人工状态、渠道窗口和分配，过时草稿不发送。

不再用 20/30 条数量截断。短页不代表已经到底；未知响应格式、缺失消息身份/时间、游标不前进、超过 250 页均视为历史不完整，不冒充完整记录继续回复。

每个真实任务记录 `context_complete`、`context_messages`、`context_characters`、`context_hash`、首末消息 ID、抓取会话数及抓取总记录数。请求另存哈希，不在普通日志重复保存完整提示词。

**边界：**

- “完整”只指 Chatwoot API 当前能返回的历史，不包含接入 Chatwoot 以前未导入的数据、已删除内容或其他无权限 Inbox。
- 私密备注、系统活动不作为客户对话传入。附件保留类型信息，不声称已经读取其图片文字、音频或视频内容。
- 全输入超过 300,000 字符时明确失败，不静默删掉较早内容；该限制是保护阈值，不是模型 Token 容量声明。
- 人数、月份由有客户原话证据的信息重建；前次成功决策的其他记忆仅在其证据仍存在于客户历史时沿用。客户的新纠正应覆盖旧值。
- 普通本地数据集不自动标注“云端完整”；只有已完成全量只读同步的本次回放作此标记。

测试账号 #26 实际只读核验：29 条原始记录，当前问题前 14 条公开上下文；未调用发送接口。另有 79 条历史与跨会话 113 条上下文的隔离回归测试，确认旧信息保留且未来消息、私密消息、其他 Inbox 被排除。

## 3. 超时处理

- 每个调用线程复用 HTTP 连接，减少重复连接成本。
- 常驻消息中转 Worker 也复用轮询连接，不再每秒重新建立连接；中转健康接口连续 10 次只读探测均返回 200。
- 使用流式协议接收结果，但仅在完整 JSON 校验通过后使用，不发送半截回复。
- 记录连接/响应头、等待首字、生成和完成阶段。兼容 SSE 保活、使用量与结束标记。
- 每次请求至多 20 秒，一次生成周期至多 30 秒、最多 3 次请求；限流、临时网络及服务端失败才重试。
- 真实回复在一个周期失败后，可持久化排队再试一次，间隔 3 秒；每次都重新检查客户新消息、人工接管、标签及有效期。
- 两个周期仍失败，则创建本地人工跟进任务，不发送错误占位消息。此前已经失败的旧任务不会因重启自动补发。
- 已调用 Chatwoot 发送但结果未知的记录仍为 `submission_unknown`，不能用模型重试规则再次发给客户。

这降低瞬时故障影响，但不是“外部服务绝不超时”的保证。生成周期之外还包含历史抓取与渠道提交耗时，页面端到端延迟不能直接等同于模型耗时。

## 4. SOP 入组边界

- `environment=shadow`：跟随真实 Chatwoot 事件推进的本地演练。
- `environment=playground`：隔离副本演练。
- 两者都只创建演练记录，不创建真实 SOP 出站消息，不受被动 AI 的全局实发开关影响。
- 真实回复 Worker 会同步观察标签/客户新消息并推进演练时钟，但不启动主动发送器。
- 首次入组与重新入组继续保留幂等及进行中轮次保护。
- 错误只在操作区域显示；重新打开入组窗口清除旧错误。

因此，修复截图中的错误后可以成功入组并观察规则结果，但不意味着这组 SOP 已经可以在 Facebook 实发。

```text
OUTBOUND_MODE=disabled
CHATWOOT_WRITE_ENABLED=false

```

在 backend 目录运行 `python -m app.long_context_replay run`。任务可恢复，结果与请求用量落库；只处理本次 run，不混跑之前的评测。`report` 子命令重新导出结果，不调用模型。

`retry-failed` 仅复测独立真实历史案例中的失败项，保留原请求记录与失败原因，不重跑已成功案例。连续 AI 会话不能只替换中间答案，否则后续上下文将与结果不一致；这类修复应重新回放该会话的受影响后续轮次。
